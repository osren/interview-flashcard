# 商旅 H5 / 小程序性能监控与体验优化

## 项目介绍

商旅列表页和星河小程序菜单曾出现首屏等待、切换卡顿等体验问题，而原有监控难以区分网络等待、页面更新和内容绘制耗时。项目在业务仓建设 `perf-monitor.js`，统一 H5 与星河小程序的采集方式，再根据监控结果优化列表日期切换、首屏非关键逻辑和菜单排序。

**30 秒概述：** 我通过 Adapter 收敛双端性能采集，监控跨页链路、LCP/FCP 和关键接口；将列表耗时拆成 fetch、render、paint，定位重复请求与渲染开销，并针对性优化。项目材料记录列表 LCP 从约 1400ms 降至 1160ms，星河菜单切换卡顿改善约 27%，同时沉淀性能分析 Skill。

## 背景与目标

列表页承载日期选择、查看产品和继续预订。原统计把请求和页面重渲染混在一起，无法判断用户等待究竟来自网络还是视图更新。星河小程序底部菜单切换也有卡顿反馈。

项目目标是建立跨端可比较的监控，把端到端耗时拆成可定位的阶段，再以同一口径验证优化效果。

## 监控设计

- **跨页链路：** 例如首页到列表完成耗时，反映用户从入口到目标页的整体体验。
- **页面指标：** LCP、FCP 等页面呈现指标。
- **关键接口：** 例如首页 `getHomeData` 的耗时。

H5 使用 Web Performance 能力，小程序侧使用 `wx.getPerformance`；采集层通过 Adapter 统一业务埋点，并经 Omega 上报。各平台能力并非完全等价，缺失指标需要单独处理。跨页和接口耗时属于业务自定义指标，不统称为 Web Vitals。

## 关键优化

1. **日期数据复用：** 同一页面会话按日期缓存列表数据。命中当前日期时跳过请求并直接渲染；未命中时正常请求。快速切换时用请求序号和当前日期校验，避免旧响应覆盖新选择。
2. **耗时拆分：** 分别观察 fetch（数据可用）、render（视图更新）和 paint（内容可见），同时保留切换日期到列表可见的交互耗时。切日期属于页内交互，不当作新一次页面 LCP。
3. **延后非关键逻辑：** `getHomeData` 保留在首页关键路径；隐私弹窗列表 `privacyPopList` 从首屏等待链路中移出，通过 defer 延后执行。目标是让主体内容先就绪，不是丢弃隐私提示；仍需符合业务要求的展示时序。
4. **菜单排序：** 星河底部菜单切换时用 `useMemo` 缓存排序结果，避免输入未变时重复排序。它减少重复计算，不会把排序移出主线程，也不代表组件完全不渲染。

## 工程化沉淀

`page-performance-analysis` Skill 按加载、交互和数据监听等阶段分析源码，帮助发现请求瀑布、重复请求、监听连锁和渲染风险。它用于缩小排查范围，不能代替运行时 profiler；最终仍用 PerfMonitor/Omega、浏览器或小程序性能工具验证。简历中的 `perf-debug-loop` 与该 Skill 的名称关系需核实后统一。

## 结果与口径

- 列表 LCP：约 1400ms → 1160ms，减少 240ms，约下降 17%。
- 星河底部菜单切换卡顿：项目材料记录改善约 27%。

现有资料没有完整提供样本量、设备/网络分层和统计定义。面试时应将其描述为项目记录的观测结果，不扩展成严格 A/B 因果结论，也不推导未记录的 FPS、P95、SEO 或 TTI 收益。
