# 商旅 H5 / 小程序性能监控与体验优化

## 速览事实卡

| 项 | 事实 |
|---|---|
| 双轨 | 运行时真测 = `src/utils/perf-monitor.js` + Omega；静态分析 = `page-performance-analysis` Skill |
| 监控内容 | 跨页 `home_to_list_complete`、同页 LCP/FCP、关键接口 `getHomeData`；H5 与星河双端 |
| 采集差异 | H5 用 Web Performance，小程序用 `wx.getPerformance`，能力不等价，缺失指标单独处理 |
| 关键数字 | 列表 LCP 约 1400ms → 1160ms（↓17%）；星河底部菜单切换卡顿改善约 27% |
| 口径要点 | fetch/render/paint 拆开；切日期不算新 LCP；缓存直渲与接口返回两条路径都要上报 |
| 首页手段 | 剥离 `privacyPopList` 出首屏等待链路（defer，不是取消隐私提示） |
| 列表手段 | 按日期缓存 + 请求序号与当前日期双重校验，防旧响应覆盖新选择 |
| 卡顿手段 | 菜单排序 `useMemo` 缓存，减少重复计算（不等于移出主线程） |
| 边界 | 数字是项目记录的观测结果，无样本量/设备网络分层，不宣称 A/B 因果；Skill 估算不替代 DevTools 真测 |

## 一句话定位

性能工程拆成两条互补轨道：**运行时真测轨**（`src/utils/perf-monitor.js` + Omega 上报，把跨页链路、同页 LCP/FCP、关键接口耗时打点，改完代码用数字验收）与**静态分析轨**（`page-performance-analysis` Skill，读源码估耗时、找瓶颈、出 P0/P1/P2 建议）。闭环是「Skill 估瓶颈 → 改业务代码 → PerfMonitor / Omega 验数字 → 再迭代」。

## 业务背景与痛点

商旅列表页承载日期选择、查看产品、继续预订；星河小程序底部菜单切换有卡顿反馈。原来的统计把请求和页面重渲染混在一起，无法回答"用户到底在等网络还是在等视图更新"，优化没有抓手。痛点还有：多个初始化接口互相 `await` 形成串行瀑布、一处状态变更触发多处 watch / setData 连锁重渲染、经验只存在于"看过这个页"的同学身上、指标数字与具体函数对不上。

## 监控体系

| 层 | 内容 |
|---|---|
| 跨页链路 | `home_to_list_complete`（首页 → 列表完成），反映入口到目标页的整体体验 |
| 同页指标 | LCP / FCP 自采集，H5 与星河双端都能出数 |
| 关键接口 | `getHomeData` 等关键接口耗时 |
| 上报 | 统一经 Omega，便于看板与前后对比 |

采集端用 Adapter 收敛：H5 走 Web Performance 能力，小程序走 `wx.getPerformance`。两端能力并不等价，缺失的指标要单独处理，不能假设同名指标能直接对齐。跨页耗时和接口耗时属于业务自定义指标，不统称为 Web Vitals。

## 指标口径（这是最容易被追问的部分）

- **拆 fetch / render / paint**：分别观察数据可用、视图更新、内容可见三个时刻；同时保留"切换日期 → 列表可见"的交互耗时。合成一个数字时看不出是网络慢还是渲染慢，拆开才能定位到底是重复请求还是渲染开销。
- **切日期不是新的 LCP**：切日期属于页内交互，不能当新一次页面 LCP 计入，否则指标会被自己的操作污染。
- **缓存直渲与接口返回是两条不同关键路径**：两条都要上报，漏一条就会出现"明明优化了却看不出收益，或者看错数"。
- **双端不可比**：H5 与小程序底层能力不同，跨端比较只比趋势与同口径阶段耗时，不比绝对值。

## 首页优化

- 自建 LCP / FCP 采集，不依赖单一端能力；封装环境判断，H5 与星河双端均能输出指标。
- 接入 `getHomeData` 关键接口耗时埋点。
- 定位并剥离拖长 LCP 的非关键路径：`privacyPopList`（隐私弹窗列表）从首屏等待链路移出，用 defer 延后执行。目标是让主体内容先就绪，**不是丢弃隐私提示**，仍要满足业务要求的展示时序。
- 可讲的判断：LCP 应对"用户感知的最大内容"，隐私弹窗类请求不应计入首屏关键路径。

## 列表优化

1. **日期数据复用**：同一页面会话按日期缓存列表数据，命中当前日期就跳过请求直接渲染；未命中正常请求。
2. **防旧响应覆盖新选择**：快速切换日期时用请求序号 + 当前日期双重校验，回来的旧响应直接丢弃。
3. **耗时拆分**：fetch / render / paint 三段分别埋点，保留端到端交互耗时。
4. **双路径覆盖**：接口返回与缓存命中直渲两条进入路径都上报，并修正切日期重渲场景的统计口径。

量化收益：列表页首屏 **LCP 约 1400ms → 1160ms，减少 240ms，约下降 17%**。

## 卡顿与稳定性

- **星河底部菜单切换卡顿**：排查到排序逻辑在每次切换时重复执行，用 `useMemo` 缓存排序结果，输入未变时不再重算。它减少的是重复计算，既没有把排序移出主线程，也不代表组件完全不渲染。项目材料记录卡顿改善约 **27%**。
- **flight-detail-refactor**：修复 `reportRender` 报错，补充"最长进入耗时"埋点，稳定性与可观测性一起补。

## 静态分析 Skill（page-performance-analysis）

- 形态：Agent Skill + 可选脚本，**没有常驻服务**，不是 APM，也不插桩生产流量。
- 规程七步：识别页面（路径 / 技术栈 / 业务场景）→ 读主文件 + mixin / hooks + store + API → 按三阶段（加载 / 交互 / 监听）列函数与依赖边 → 套耗时估算表 → 找瓶颈 → 出 P0/P1/P2 → 写固定五段报告。
- 耗时估算表（类型级，不是测量）：简单查询 100–300ms、复杂查询 300–600ms、聚合/大数据 500–2000ms；简单赋值 1–10ms、数组遍历 10–50ms、复杂计算/递归 50–500ms；简单状态更新 5–20ms、列表渲染 20–100ms、复杂组件/整页 50–500ms。
- 梯队：🔴 >500ms 优先优化、🟡 200–500ms 中期、🟢 <200ms 通常可接受。
- 瓶颈清单四类：串行请求瀑布（无依赖却 await 串行 → Promise.all / 分批并行）、频繁触发（watch / scroll 过密 → 合并更新、节流）、防抖节流配置（debounce 过长反而拖慢体感）、重复请求（同参多次打接口 → 去重 / 缓存 / 共享 Promise）。
- 建议分级：P0 体验关键且易落地、P1 收益明显但有开发成本、P2 架构级（虚拟列表、组件懒加载、缓存体系）。
- Web Vitals 对照：FCP 良好 <1.8s、LCP <2.5s、TTI <3.8s、FID <100ms、CLS <0.1；报告中未经真测的"当前值"必须标为估算或待测量，不许伪精确。
- `analyze.sh` 只做骨架：校验页面存在、按扩展名猜技术栈、统计行数与函数数、写出带"待深度分析"占位的 Markdown；它不解析 AST、不测真实耗时、不给 P0 建议。深度结论必须由 Agent 读源码补。
- 支持 MPX / Vue / React / 微信与支付宝小程序 / H5 / 原生 JS；同一套三阶段模型映射到不同钩子名（Vue 看 lifecycle/watch/computed/mixin，React 看 hooks/effect/memo/重渲染边界，小程序看页面生命周期、setData 粒度、分包）。

## 两轨如何拼成闭环

| 阶段 | 谁做 | 产出 |
|---|---|---|
| 定位嫌疑 | Skill 静态分析 | 函数耗时梯队、串行瀑布、P0 建议 |
| 度量基线 | PerfMonitor + Omega | FCP/LCP、跨页链路、接口耗时 |
| 落地改造 | 业务代码 | 剥离非关键接口、修正口径、优化排序 |
| 验收 | PerfMonitor 前后对比 | 列表 LCP ↓17%、菜单卡顿 ↓27% |

## 结果口径与诚实边界

- 数字来源是项目材料记录的观测结果，没有完整提供样本量、设备 / 网络分层与统计定义。
- 因此面试时应表述为"项目记录的观测结果"，不扩展成严格 A/B 因果结论，也不推导未记录的 FPS、P95、SEO 或 TTI 收益。
- Skill 的估算是为了排优先级，不替代 DevTools / Performance 面板 / 真机 profiler；Skill 包内不内嵌 APM 是有意的边界，业务仓的 PerfMonitor 才是真测轨。

## 常见追问与易错点

- **为什么不用现成 APM？** 需要业务自定义的跨页链路与关键接口口径，通用 APM 给不到；自建采集更贴近列表页的两条进入路径。
- **缓存会不会让用户看到旧数据？** 缓存键带日期与页面会话，命中只限当前日期；快速切换用请求序号 + 日期校验，旧响应不会覆盖新选择。
- **defer 隐私弹窗会不会违规？** 只是移出首屏等待链路，提示仍按业务时序展示，不是取消。
- **useMemo 缓存排序就等于不卡了吗？** 不是。它只消除重复计算，渲染与更新仍会发生；卡顿改善要结合真测数字说话。
- **LCP 17% 是怎么算的？** (1400−1160)/1400 ≈ 17%，是单指标前后对比，不是全链路收益。
- **Skill 的报告能直接当线上数据吗？** 不能，估算值是排优先级用的，必须用 PerfMonitor / DevTools 复测校准。
- **两轨会不会重复建设？** 不重复：一轨回答"该改哪里"，一轨回答"改完到底快了多少"。
