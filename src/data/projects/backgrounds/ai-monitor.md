# 商旅 AI 告警智能降噪判定服务

## 项目介绍

商旅机、酒、火车票接口告警中，存在无票、已退改、重复提交等正常业务拒绝；它们与真实技术故障一起上报，容易让值班噪音淹没重要问题。项目在告警派发前增加智能判定：接收告警、按 URL 路由到业务类别、组合公共与类别 Prompt、调用 LLM，输出是否上报、严重级别、错误类型、原因和置信度。

**30 秒概述：** 系统采用通用引擎加可插拔 Domain。HTTP 与 Kafka 入口复用同一处理流程；模型超时或结果无法解析时保守上报 P2，避免降噪链路吞掉告警。项目同时建设 judge/eval 与本地回归评测，以漏报为重点调优 Prompt。

## 业务目标与原则

需要区分业务正常拒绝与真实服务故障，减少低价值告警占用值班注意力，同时避免过度过滤造成漏报。核心取舍是**宁可误报不可误杀**：误报增加噪音，漏报可能使主链路故障无人处理。

每条判定输出包括：

- `should_report`：是否进入上报流程。
- `severity`：P0–P3 严重级别。
- `error_type`、判定原因及置信度。

## 架构与处理流程

```text
HTTP / Kafka → handleAlarm → URL 路由 → Domain Prompt → LLM 判定 → 兜底 → dispatch
```

- **入口层：** HTTP 和 Kafka 收到告警后复用 `handleAlarm`，避免核心行为分叉。
- **Router：** 归一化 URL pathname，按有序规则匹配业务类别；可用 `ownedPrefixes` 区分自有接口，未命中时进入 fallback。
- **Triage：** 组合公共 `_base.md` 与类别 Prompt，调用模型并解析结构化结果。
- **LLM 适配：** 将网关调用封装在模型适配层，避免接入细节侵入业务判定。
- **Domain：** 以 `rules.js` 和 `prompts/` 保存各团队路由与业务语义；接入新业务主要补配置，不把业务知识写进通用引擎。
- **评测：** 单条 judge 或批量 eval 路径只判定、不触发真实派发；离线数据集按 gold 关注 FN、误报、严重度和错误类型。

## 安全兜底与评测

模型超时、网关异常、输出解析失败或最低字段不合法时，系统按 `should_report=true, severity=P2` 保守上报，避免降噪服务故障导致告警被静默丢弃。信息不足时也应保持保守。

评测不能只看笼统准确率：正常业务拒绝占多数时，“全部不报”可能得到表面高分，却漏掉真故障。项目优先关注 FN（应该上报却被过滤），并用冻结的 gold 数据集回归 Prompt；train 用于调优，holdout 用于检查泛化。

## 当前进度边界

现有项目资料显示 train Domain 已接入，flight/hotel 仍处于接口清单阶段；真实 IM、电话或工单派发尚未接入，dispatch 当前是日志占位。资料描述了 judge/eval 能力，但具体 HTTP endpoint 是否在当前分支实现需以代码为准。没有可靠的线上降噪百分比，因此应描述为判定服务、业务配置和评测链路建设，不表述为已全量生产降噪。
