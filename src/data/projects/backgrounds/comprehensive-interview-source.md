## 三、JavaScript / 浏览器基础

### Q4：`var`、`let`、`const` 有什么区别？什么是暂时性死区？

**答：** `var` 是函数作用域，存在变量提升，重复声明允许；`let` 和 `const` 是块级作用域，不能在同一作用域重复声明。它们会被创建但在声明语句执行前不能访问，这段区域叫暂时性死区。`const` 限制变量绑定不能重新赋值，但对象内部属性仍可修改。默认优先 `const`，需要重新赋值时用 `let`。

### Q5：闭包是什么？举个前端场景和需要注意的问题。

**答：** 函数可以访问其定义时词法环境中的变量，即使外层函数已经返回，这种保留外部变量引用的现象叫闭包。可用于封装状态、创建函数工厂或防抖。闭包会延长变量生命周期；若长期持有 DOM、大对象或定时器回调，可能造成内存无法回收。使用后应解除监听、清理定时器并避免不必要的大对象引用。

### Q6：Promise、`async/await` 如何处理错误？并行请求怎么写？

**答：** Promise 表示异步操作结果，`async/await` 是基于 Promise 的语法形式。串行依赖可以逐个 `await`；互不依赖的请求用 `Promise.all` 并行，任意一个 reject 会使整体 reject；若需要收集所有结果而不短路，可用 `Promise.allSettled`。错误可用 `try/catch` 捕获并转为 UI 可理解状态，不能静默吞掉。并行前要确认请求之间没有数据依赖。

### Q7：事件循环是什么？微任务和宏任务的顺序如何？

**答：** JS 主线程先执行当前同步任务；调用栈清空后处理微任务队列，通常包含 Promise reaction、`queueMicrotask`；之后浏览器可能进行渲染，再执行下一个宏任务，如计时器、部分事件回调。微任务持续产生时可能推迟渲染。不要把浏览器事件循环简化为“固定每次宏任务后一定绘制”，渲染时机由浏览器调度。

### Q8：浏览器输入 URL 到页面显示，主要经历什么？

**答：** 解析 URL、缓存检查和 DNS/连接建立（复用连接时可能跳过部分步骤）、TLS（HTTPS）、发送 HTTP 请求、服务端响应、解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合成渲染树，布局、绘制和合成。HTML 解析遇到脚本时可能受同步脚本阻塞；图片、字体、JS、CSS 加载策略会影响关键路径。实际流程会被缓存、预加载、HTTP/2 或 HTTP/3 等优化改变。

### Q9：重排和重绘有什么区别？怎样减少布局抖动？

**答：** 修改影响几何布局的属性可能触发布局（重排），布局后像素变化还需要绘制；只改颜色等视觉属性通常可能只触发绘制。连续读写布局属性会反复强制同步布局，形成 layout thrashing。可先批量读取，再批量写入；使用 transform/opacity 做动画；缩小 DOM 变更范围。不能绝对说某个 CSS 属性在所有浏览器都只触发某一步，应以性能工具实际观测为准。

### Q10：防抖和节流的区别？搜索框和滚动场景怎么选？

**答：** 防抖是事件停止一段时间后执行，适合输入搜索、窗口 resize 这种只关心最终状态的场景；节流是在固定时间窗口内最多执行一次，适合滚动监听、拖拽位置更新。搜索请求还应考虑取消旧请求或用请求序号避免旧结果覆盖新结果。

### Q11：浏览器缓存的强缓存和协商缓存分别是什么？

**答：** 强缓存通过 `Cache-Control` 等响应头判断是否直接使用本地缓存，不发请求；协商缓存通过 `ETag`/`If-None-Match` 或 `Last-Modified`/`If-Modified-Since` 向服务端验证，未变可返回 304。静态带 hash 的资源适合长缓存，HTML 通常需较快重新验证，避免入口文件长期指向旧资源。

## 四、HTML / CSS / 布局

### Q12：Flex 与 Grid 的适用场景是什么？

**答：** Flex 主要解决一维布局，适合导航栏、工具栏、卡片内部对齐；Grid 适合二维行列布局，如复杂仪表盘、规则网格。实际项目可以组合使用，优先根据布局关系而非“新旧”选择。

### Q13：CSS 选择器优先级如何判断？`!important` 应该多用吗？

**答：** 同一来源下比较重要性、层叠层、选择器优先级和源码顺序；常见优先级可粗略理解为 inline、ID、class/属性/伪类、元素/伪元素逐级增强。`!important` 会增加覆盖困难，不应作为常规修复方式。更好的做法是控制样式作用域、组件边界和设计 token。

### Q14：什么是 BFC？它能解决什么问题？

**答：** BFC 是块级格式化上下文，内部布局有独立规则。它可以隔离浮动影响、避免部分外边距折叠等。现代布局通常用 Flex/Grid；是否创建 BFC 取决于具体问题，不要为了“清除浮动”机械添加 `overflow:hidden`，因为它可能裁剪阴影或弹出内容。

### Q15：如何处理移动端适配和横竖屏？

**答：** 先使用 viewport 配置、相对单位/弹性布局和断点适配；交互控件保证可点击区域；考虑安全区、软键盘、横竖屏和字体缩放。H5 与小程序的容器、滚动和尺寸 API 有差异，公共布局和平台适配应分层。需要在真实设备或开发者工具验证，不能只看桌面模拟。

## 五、React / Vue 与组件工程

### Q16：React 中 state 更新为什么是异步/批处理的？如何避免旧状态问题？

**答：** React 会批量处理更新以减少重复渲染；具体批处理范围与版本、更新上下文有关，不应简单说所有 setState 永远异步。若新状态依赖旧状态，使用函数式更新，如 `setCount(c => c + 1)`，避免闭包读取到旧值。副作用放在合适的 Effect 中，并处理清理、依赖和竞态。

### Q17：`useEffect` 常见错误有哪些？

**答：** 依赖数组漏项会读到旧闭包；依赖对象每次重建会反复触发；Effect 内发请求未取消可能在组件卸载后更新状态；把可在渲染中计算的派生值放进 Effect 会增加状态同步复杂度。应尽可能纯计算派生状态，Effect 只同步外部系统，并提供清理函数。

### Q18：React 为什么需要 key？列表用 index 当 key 有什么风险？

**答：** key 帮助 React 在更新时识别元素身份。列表可插入、删除或重排时使用 index，节点状态可能被错误复用，造成输入值或子组件状态错位。优先用稳定且唯一的业务 ID；静态且永不变化的列表才可考虑 index。

### Q19：Vue `computed` 和 `watch` 区别是什么？

**答：** `computed` 表示基于响应式依赖缓存的派生值，适合可由现有状态计算出来的结果；`watch` 监听变化并执行副作用，如请求、持久化或异步同步。不要用 watch 维护本可直接 computed 得出的状态，否则容易引入重复状态和时序问题。

### Q20：Vue 组件更新和响应式数据大致如何工作？

**答：** Vue 通过响应式系统追踪组件渲染过程读取的依赖，依赖变化时调度组件更新并重新渲染。Vue 2 主要通过 `Object.defineProperty`，Vue 3 使用 Proxy 等机制；具体边缘行为和 API 要看版本。优化重点是避免不必要的大范围响应式依赖、稳定组件边界和合理使用列表 key。

### Q21：受控组件与非受控组件是什么？表单如何选？

**答：** 受控组件的值由框架状态驱动，每次输入更新状态，适合需要实时校验、联动和统一提交的数据；非受控组件主要由 DOM 管理值，通过 ref 读取，适合简单表单或降低频繁状态更新。选择取决于交互和复杂度，不能只按性能口号决定。

### Q22：组件拆分的原则是什么？

**答：** 按职责、复用边界和状态所有权拆分。组件应该有清晰输入输出，业务逻辑、数据获取和展示职责不要无意义耦合。不是越小越好；过度拆分会增加状态传递和理解成本。公共组件需要稳定 API、类型约束和可验证的边界。

## 六、接口联调、兼容性与测试

### Q23：前后端联调前应该确认什么？

**答：** 确认请求方法、路径、参数位置和类型、必填/可选字段、响应 schema、分页约定、错误码、鉴权方式、幂等要求和环境地址。用接口文档或 mock 先并行开发，联调时覆盖成功、空数据、业务错误、网络超时、权限失效和重复提交。接口变化要同步更新类型与调用方。

### Q24：一个接口请求失败，前端应该怎么处理？

**答：** 区分网络错误、HTTP 状态错误、业务错误和取消请求；提供用户能理解的提示与重试策略；避免重复点击造成重复提交；必要时记录 request id 等诊断信息。是否自动重试要看请求是否幂等，不能对支付、创建订单等写操作盲目重试。敏感信息不能写入日志。

### Q25：如何处理异步请求竞态？

**答：** 比如搜索“a”后又搜“ab”，较早的请求可能更晚返回并覆盖新结果。可用 AbortController 取消旧请求，或为每次请求分配序号，仅应用最新序号结果。组件卸载时也应取消请求或忽略过期响应。

### Q26：你如何验证浏览器/小程序兼容性？

**答：** 先根据目标用户和产品支持矩阵确定范围；检查 API 支持、CSS 差异、滚动/键盘/安全区及生命周期差异；通过特性检测或 Adapter 做能力降级；再用目标浏览器、真实设备和小程序开发者工具验证核心路径。兼容问题要记录环境、复现步骤和影响面，避免只凭 UA 猜测。

### Q27：你会怎样设计一个前端功能的测试？

**答：** 先拆纯逻辑、组件交互和端到端主流程。纯函数测边界和异常输入；组件测加载、空态、成功、失败及用户操作；关键路径做集成/E2E 回归。对性能改造增加指标埋点或前后对比验证。测试应覆盖业务风险，不是单纯追求覆盖率数字。

## 七、构建、Git、Linux、Docker 与云平台基础

### Q28：Vite 和 Webpack 的开发体验差异是什么？

**答：** 传统 Webpack 开发时通常先打包依赖和应用，再提供开发服务；Vite 利用原生 ESM 提升开发启动和按需更新体验，生产构建仍需打包优化。选型还要看生态、插件、项目结构和构建需求。不要说 Vite 生产完全不打包。

### Q29：Code Splitting 和懒加载有什么区别与收益？

**答：** Code Splitting 将代码拆成多个 chunk；懒加载是在需要时才加载某个 chunk，常用于路由和低频模块。可以降低初始下载和解析执行量，但拆得过碎会增加请求和运行时开销，公共依赖抽取也需避免重复下载。用构建分析和真实指标验证效果。

### Q30：Git 遇到冲突怎么处理？

**答：** 先看冲突文件和双方意图，不直接选择 ours/theirs。理解基线与变更范围，手动合并后检查上下文、格式和行为；运行相关验证，查看 diff，确认没有误删或把密钥提交，再提交合并结果。团队协作时及时同步冲突解决方案。

### Q31：Linux 常用哪些排查命令？

**答：** `pwd/ls/cd` 看路径，`grep/rg` 查内容，`ps/top` 看进程，`ss` 看端口，`curl` 检查 HTTP，`tail` 看日志，`df/du` 看磁盘。先收集证据再操作；涉及删除、重启或权限变更要确认目标和影响。

### Q32：Docker 镜像和容器有什么区别？

**答：** 镜像是只读的应用模板和依赖层，容器是镜像运行时创建的实例，包含可写层和进程。Dockerfile 描述构建步骤；容器环境应通过环境变量或密钥管理注入配置，不把 token 写进镜像。岗位只要求基础概念，若没有生产部署经历应坦诚说明。

### Q33：云平台上部署一个前端或 AI 服务要关注什么？

**答：** 前端静态资源需配置构建产物、域名、HTTPS、缓存和回滚；AI 后端需管理密钥、鉴权、超时、限流、日志和成本。网络访问、跨域、环境变量、监控告警和权限最小化也要考虑。不同云平台产品不同，我会先按团队现有平台规范完成，不假称熟悉没使用过的产品。

## 八、AI 辅助开发与 AI 工程问题

### Q34：你平时如何把 AI 编码工具用于真实开发？

**答：** 我把任务拆成小步骤，先提供目标、相关文件、技术约束和验收条件；让 AI 先解释现状或提出方案，再生成局部改动。随后我检查 diff、类型、边界和安全性，运行项目要求的验证并用实际页面/接口复现。对业务规则、权限、数据迁移和高风险逻辑不直接接受生成结果。AI 提高探索和样板代码速度，但责任仍由开发者承担。

### Q35：怎样写一个有效的代码任务 Prompt？

**答：** 包含背景、目标、相关代码/接口、约束、非目标、预期输出和验收方式。比如：“在 React 搜索框中防止旧请求覆盖新结果；使用现有 API 封装，不加依赖；保留加载/错误态；说明改动文件并补充边界处理”。复杂需求先让模型复述理解和列方案，再分块实现。

### Q36：AI 给出代码后如何审查？

**答：** 看是否符合真实需求和仓库约定；检查类型、异常路径、空值、竞态、资源清理、权限和敏感信息；关注 API 是否真实存在、依赖是否新增、代码是否改动范围过大；看 diff 并做针对性验证。生成的测试也要判断断言是否真正覆盖需求，不能只看测试通过。

### Q37：如何防止把公司代码或秘密泄露给外部 AI？

**答：** 先遵守公司工具和数据分级制度；不上传凭证、个人信息、生产数据和未经授权的代码；使用批准的企业账号/模型，必要时脱敏并缩小上下文；密钥放服务端密钥管理，不放前端或 Prompt。即使工具有隐私承诺，也以组织规则为准。

### Q38：AI 生成的代码出现 Bug，你如何定位？

**答：** 先稳定复现，记录输入和预期/实际结果；检查调用链、状态和网络请求；将问题缩小到最小复现，再对照代码与 API 契约。可以让 AI 基于最小上下文列假设，但逐个验证，不让模型一次性大改。修复后检查回归范围，并补能稳定复现该问题的验证。

### Q39：你如何衡量 AI 工具是否真正提效？

**答：** 不只看生成代码行数，而看从任务开始到正确交付的总时间、返工率、缺陷率、审查成本和安全风险。对重复样板任务可比较前后耗时；对复杂功能要统计人工验证和修复成本。个人简历中若提效率百分比，需要明确样本和统计方法，否则只描述定性收益。

### Q40：什么情况下不该使用 AI？

**答：** 需求边界不清、涉及敏感数据但工具未获批准、需要严格确定性或强安全保证、上下文不足且无法验证、生成结果会直接影响支付/权限/数据删除等高风险场景时，不应让 AI 自动决策或直接合入。可以用它整理资料或生成候选方案，但必须由工程规则和人工审核兜住。

### Q41：Prompt 注入是什么？前端 AI 产品如何减轻风险？

**答：** 用户输入或检索内容试图覆盖系统规则、诱导模型泄露信息或调用不当工具，就是 Prompt 注入风险。Prompt 不是安全边界。服务端要做鉴权和权限检查，工具调用要白名单化、最小权限，检索内容视作不可信数据，输出也要校验和转义；不要把密钥或不该暴露的系统提示交给模型。高风险动作需要明确用户确认或确定性规则控制。

### Q42：RAG 与微调有什么区别？

**答：** RAG 在推理时检索外部知识并把相关片段交给模型，适合知识频繁更新、需要引用来源的场景；微调通过训练改变模型参数，更适合稳定的格式、风格或特定任务行为，不适合频繁注入最新事实。RAG 要关注切块、召回、排序、权限过滤和过期；微调需要高质量训练数据和评测。

### Q43：模型幻觉如何控制？

**答：** 限定任务和输出 schema，提供可信上下文，要求信息不足时明确拒答或标记不确定；对关键事实做检索或代码校验；使用评测集和人工抽检观察错误类别。不能只靠一句“不要幻觉”，也不能把模型置信度字段当作校准过的概率。

### Q44：你在 InterviewFlash 中如何接入 LLM？

**答：** 按简历，Explain/Follow-up Prompt 会注入闪卡和候选人项目上下文，通过 SSE 流式输出，会话在本地缓存；模型经 Edge Function 代理，JWT 鉴权并用 RPC 做日额度原子扣减，避免 API Key 暴露前端。JD 解析和简历定向优化也走服务端能力。面试时我会展示一个真实调用链，并说明断流、超时、额度耗尽、重试和内容安全如何处理；无法确认实现的细节不夸大。

### Q45：SSE 与 WebSocket 有什么不同？为什么这里用 SSE？

**答：** SSE 基于 HTTP 单向服务端到客户端文本流，浏览器 EventSource 有自动重连等机制，适合模型逐 token 输出；WebSocket 是双向全双工连接，适合高频双向实时交互，但连接管理更复杂。若客户端需要中途发送多条控制消息，可选 WebSocket；单向生成流常用 SSE。仍需处理代理缓冲、断连、结束标记和取消生成。

### Q46：为什么额度扣减要原子化？

**答：** 若先查询剩余额度、调用模型后再扣减，多个并发请求可能同时读到余额充足并都通过，造成超额。数据库 RPC/事务内用原子条件更新或锁保证“检查并扣减”作为一个不可分操作。还应考虑幂等请求 ID，避免客户端重试重复扣费。

## 九、AI 告警项目深挖：与岗位 AI 工具能力结合

### Q47：告警降噪为什么用 LLM？如何避免“模型说了算”？

**答：** 业务拒绝语义依赖接口、错误码和状态上下文，纯规则维护成本高；LLM 可结合 Domain Prompt 处理语义。模型只提供判定候选，工程负责 URL 路由、输入约束、结构校验、失败保守上报和 gold 评测。真实派发在当前材料中是日志占位，不能说模型已直接控制生产告警通道。

### Q48：评测为什么重点关注 FN，而非只看准确率？

**答：** 告警中正常拒绝可能占多数，全部过滤也可能有很高 accuracy，但会把真故障全部漏掉。FN 是应该报却被判不报，风险最大，所以用 gold 数据和 holdout 关注漏报，再看误报、等级和类别切片。数据集要冻结，避免每次改 Prompt 同时换题导致结果不可比较。

### Q49：模型超时或 JSON 解析失败怎么办？

**答：** 当前实现的原则是保守上报，`should_report=true`、severity P2，避免降噪服务故障吞告警。解析器有最低字段校验，但并非完整 Schema 验证。生产接入前还应完善枚举校验、超时和限流监控，并确认 P2 的派发策略。

### Q50：告警项目当前真实进度是什么？

**答：** 仓库材料显示通用 HTTP/Kafka 引擎和 train Domain 已接入，flight/hotel 有 URL 清单但 Domain 待接入；dispatch 仍为日志占位，没有真实 IM/电话/工单通道，也没有可支持的线上降噪百分比。我会把它描述为判定引擎、配置和评测链路建设，而不声称全量生产降噪。

## 十、现场情景题

### Q51：产品希望“页面打开后立刻展示 AI 生成内容”，但模型首字延迟高，你怎么办？

**答：** 先确认用户真正等待的是什么，采集请求、首字时间、完整生成时间和页面关键指标；把不依赖 AI 的页面骨架先渲染，展示清晰的加载状态；使用 SSE 流式输出，必要时缓存可复用结果或提供非 AI 回退。再评估模型、Prompt 长度和网络链路。不能只让页面无限转圈，也不能未经验证把旧结果当新结果展示。

### Q52：测试发现某小程序页面偶发白屏，你如何排查？

**答：** 先收集机型、系统、客户端版本、网络、入口和复现路径；看白屏时的 JS 错误、资源加载和接口日志；区分启动失败、路由失败、数据异常和渲染异常；在对应设备复现并缩小到最小步骤。修复后对核心路径做设备回归，同时加上错误边界或监控以观察是否复发。

### Q53：后端接口字段改名，前端联调被阻塞，你怎么办？

**答：** 先和后端确认新契约、兼容期和上线顺序；前端用类型/适配层隔离字段差异，必要时基于确认后的 schema mock 开发；保留向后兼容处理并加测试。避免静默用 `any` 掩盖契约不一致，联调后再移除临时 mock。

### Q54：AI 建议改动很多文件，但你只想修一个 Bug，怎么控制范围？

**答：** 先要求 AI 解释根因和最小修复方案，限制可修改文件或模块；检查工作区 diff，撤销无关变化；用最小复现验证修复，再跑相关回归。若根因确实需要重构，先单独提出影响和风险，不把大规模重写混进紧急修复。
