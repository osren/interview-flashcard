### 2. 现在平安的话，已经80%代码都是ai，ai编码应用的多不多？

- 1. AI 编码现在落地已经比较普遍，定位是**开发提效工具，不会替代研发**。
- 2. 我的使用方式：把任务拆小，给 AI 明确目标、技术约束和验收条件，让 AI 输出方案或局部代码改动；产出后我会人工核对代码差异、边界、类型和安全问题，并且做验证复现。
- 3. AI 比较适合写样板代码、单测草稿、整理文档、提供排查思路。但核心业务规则、权限、数据迁移这类高风险逻辑，AI 生成的代码不能直接上线，必须人工深度审查。
- 4. 判断 AI 的提效，不看生成代码行数，重点看交付总耗时、返工率和缺陷率。
- 5. 如果团队 80% 代码都有 AI 参与，核心重点不是追求写代码速度，而是要建立完善的代码审查规范、上下文管理和验证闭环。

### 3. 日常开发中使用过哪些skill？

- 1. Claude Code Agent Skill：用来研读代码库、拆解方案、局部代码修改、文档梳理。
- 2. Cursor：日常代码补全、代码重构、定位报错。
- 3. 自研 page-performance-analysis 性能分析 Skill：从加载、交互、数据监听三个阶段分析源码，定位请求瀑布、重复请求、响应式连锁渲染等问题，输出 P0/P1/P2 分级优化建议；它只是静态分析找可疑点，最终性能结论需要线上性能工具实测确认。
- 4. 其他场景：AI 辅助调试 Prompt、评测用例归因、接口文档整理。
- 5. 总结：Skill 主要是把重复排查、审查流程模板化，代码质量与业务责任最终还是由开发者负责。

### 4. AI智能降噪那个skill大概的设计流程？

**1. 输入与路由**：告警从 HTTP 或 Kafka 进入，先统一走 `handleAlarm`。用 URL 归一成 pathname，去掉 token、签名等 query，再按有序规则路由到业务 category，区分自有接口和 non-core。

**2. Prompt 组装与判定**：读取启动时缓存的公共 `_base.md` 和类别 Prompt，拼成完整输入，把告警 JSON 交给 LLM，输出 `should_report`、severity、error_type、reason 和 confidence。URL 路由只决定业务类别，**severity 由模型按 Prompt 判定**，不是路由表直接映射。

**3. 安全兜底**：模型超时、网关报错或 JSON 解析失败时，保守返回 `should_report=true`、P2、unknown，避免降噪服务故障吞掉真告警。当前解析只做最低字段校验，不是完整 Schema。

**4. 评测闭环**：真实告警去重成 case，人工标 gold，切 train 和 holdout 并冻结；评测走只判定不派发路径，输出 FN、误报和等级偏差，**优先压 FN 漏报**，再归因改 Prompt 并回归。

**5. Domain 接入**：新团队主要加路由和 Prompt 配置，不改通用引擎。当前 train Domain 已接入，flight/hotel 待接，真实 dispatch 仍是日志占位。

### 5. 除了skill和rpompt，还有ai什么其它工具？sdb这些有了解吗？

除了 Skill 和 Prompt 之外，我还使用过多类 AI 工具，主要分为下面几类：

1. **编码类工具**：Claude Code、Cursor。用于代码库探索、局部代码修改、代码重构以及报错定位。
2. **模型与 API 类**
   - 使用 Supabase Edge Function 代理 LLM，实现 SSE 流式输出、JWT 鉴权、RPC 原子额度扣减，防止前端直接暴露 API Key；
   - 了解 RAG 的检索与评测思路。
3. **调试与评测类**：借助 AI 生成测试草稿、问题失败归因、gold 数据对比；但断言是否覆盖业务需求，必须人工判断。
4. **文档与协作类**：利用 AI 整理接口文档、面试材料、项目复盘记录。
5. **探针工具**：`discover-triage-urls`，结合 grep、源码探索、AST 扫描来发现接口，结果需要人工确认。
6. **SDB（Supabase）**
   - 平台定位：属于开源后端云平台，封装了 PostgreSQL，偏向后端基础设施能力；
   - 前端侧实践点：
     - 鉴权：直接使用 Supabase 自带 Auth 体系，管理用户登录、会话、JWT 令牌；
     - Edge Function：作为中间层代理 LLM 请求，把 API Key 保存在服务端，避免密钥泄露到前端，同时实现 SSE 流式返回；
     - RPC：调用数据库自定义函数，完成原子化操作，比如 LLM 调用额度扣减；
     - 密钥与权限：管控数据库行级安全 RLS，区分前端客户端权限和服务端权限；
   - 工程价值：可以快速搭建带数据库、鉴权、服务函数的 AI 应用原型，减少后端重复基建；但数据库 Schema 设计、RLS 权限策略、SQL 性能风险依然需要人工把控。

### 6. 对AI的约束主要是提示词吗？

不完全是，提示词只是其中一层。我通常还会做几件事：

- 一是上下文管理，只给相关文件和接口契约，避免把整个仓库和敏感信息丢进去；

- 二是工具约束，用 Claude Code、Cursor 这类带仓库读写和终端能力的工具，让 AI 先读代码再改，而不是凭空生成；

- 三是工程约束，通过 ESLint、TypeScript、测试和 CI 把错误挡在合入前；

- 四是流程约束，让 AI 先解释现状和方案，再分块实现，改完看 diff、跑验证、做回归；

- 五是安全约束，密钥放服务端密钥管理，工具调用白名单化、最小权限，敏感数据脱敏。

项目里降噪也是类似：Prompt 约束输出 schema，URL 路由和代码规则做确定性判断，评测集和 FN 指标做回归，失败时保守兜底。所以提示词只是入口，真正起作用的是上下文、工具、工程校验和安全边界一起配合。

### 7. 你在项目里有没有用过 OpenSpec /spec 这类规范？说说实践

- 1. 我理解 OpenSpec，是把需求做成 AI 可读的工程规范，让 AI 编码前对齐接口、边界和验收标准，避免 AI 自由发挥写代码。
- 2. 项目里做过轻量 spec 实践，但没有完整落地 OpenSpec 平台。我会先写任务 spec：目标、入出参、边界、非目标、验收标准，先和 AI 对齐理解，再分块开发。同时把 spec 转为 TS 类型、接口 schema、单测、ESLint 这类可自动化校验规则。
- 3. 类似实践在告警降噪模块：公共 Prompt 固定输出结构，类别 Prompt 注入业务语义，搭配路由规则、gold 数据、FN 指标做回归校验，失败走兜底逻辑。
- 4. 这套是 Prompt + 评测 + 工程校验的组合，缺少完整的 spec 变更追踪和归档。如果团队落地，优先高风险模块试点，把 spec 绑定测试和 CI，再逐步推广。
- 5. 在我看来 OpenSpec 核心就是规范先行、约束可执行、验证可回归，Prompt 只是其中一环。
