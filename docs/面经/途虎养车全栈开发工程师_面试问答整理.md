## 一、基础知识与 AI 工程化

### 1. 什么是栈（Stack）？

#### 1) 核心特点

栈是一种遵循后进先出（LIFO）的线性数据结构，只能在栈顶插入和删除，分别称为入栈（Push）和出栈（Pop），通常时间复杂度为 O(1)。

#### 2) 函数调用栈

函数调用时会创建栈帧，保存参数、局部变量和返回地址等信息；函数结束后栈帧弹出。

#### 3) 典型应用

括号匹配、表达式求值、撤销操作等。浏览器前进后退也可以用双栈思路实现。

### 2. 如何使用栈判断括号是否匹配？

#### 1) 遍历与入栈

遍历表达式，遇到左括号 `(`、`[`、`{` 时入栈。

#### 2) 匹配与出栈

遇到右括号时先检查栈是否为空，再检查栈顶左括号是否与当前右括号对应；不匹配则返回 false，匹配则出栈。

#### 3) 判断结果

遍历结束后，栈为空表示全部匹配。

#### 4) 复杂度

时间复杂度 O(n)，空间复杂度最坏 O(n)。例如 `{[()]}` 合法，`{[(])}` 不合法。

### 3. 为什么无限递归会导致栈溢出？

#### 1) 调用过程

每次函数调用都会创建新的栈帧，保存局部变量、参数和返回地址等信息。

#### 2) 溢出原因

无限递归或递归深度过大时，栈帧持续入栈；超过调用栈容量就会发生栈溢出。

#### 3) 处理方式

设置明确的终止条件，确保递归逐步接近终止条件；深度过大时可以改用循环或显式栈。JavaScript 中常见报错为 `RangeError: Maximum call stack size exceeded`。

### 4. Function Calling、MCP 和 Skills 有什么区别？

#### 1) Function Calling

模型生成结构化的函数调用参数，由程序执行 API、数据库查询等具体操作。

#### 2) MCP

为 AI 应用连接外部工具和数据源提供标准化协议，减少重复接入工作。

#### 3) Skills

通过指令、脚本和资源沉淀领域知识、任务流程和最佳实践，让复杂任务更容易复用。

#### 4) 总结

Function Calling 侧重“如何调用工具”，MCP 侧重“如何标准化连接”，Skills 侧重“如何组织任务流程”。三者可以组合使用，并非相互替代。

### 5. 如果只接入一个内部报销查询工具，选 Function Calling 还是 MCP？

#### 1) 单一内部工具

优先考虑 Function Calling。需求明确、工具数量少，可以直接定义参数 Schema 并调用内部 API，开发链路简单。

#### 2) 多工具场景

如果未来要共享报销、机票、酒店、审批等多个工具，可以考虑 MCP 标准化封装，降低重复接入和维护成本。

#### 3) 安全边界

无论采用哪种方案，都需要在服务端做身份认证、数据权限校验和敏感信息保护。

#### 4) 总结

单应用、单工具优先 Function Calling；多应用、多工具且需要统一治理时，可以考虑 MCP。

### 6. 什么情况下应该把 Function Calling 的流程封装成 Skill？

#### 1) 两者分工

Function Calling 适合执行具体原子操作，例如查日志、查接口数据或运行测试；Skill 负责组织完整任务流程、判断标准和最佳实践。

#### 2) 适合封装的情况

当任务涉及多个步骤、条件分支和领域知识，并且需要重复使用时，适合封装成 Skill；单次查询通常直接调用函数即可。

#### 3) 项目示例

性能排查可以组织成“定位慢接口—分析瓶颈—实施优化—效果验收”的流程，再调用日志查询、性能分析等工具。

#### 4) 总结

Function Calling 解决“能做什么”，Skill 解决“应该怎么做、按什么流程做”。

## 二、滴滴实习：性能优化项目

### 7. 这个项目最核心的技术难点是什么？

我认为最核心的难点是准确定位跨端性能瓶颈，并在优化 LCP 的同时兼顾 SEO、TTI 等指标。

#### 1) 建立监控

通过 Adapter 适配 H5 的 `PerformanceObserver` 和小程序的 `wx.getPerformance`，统一采集性能指标。

#### 2) 定位瓶颈

将耗时拆分为 `fetch`、`render`、`paint`，区分网络请求和渲染问题。

#### 3) 针对性优化

对重复请求做缓存复用，对非首屏逻辑延后执行，并优化菜单计算逻辑。

#### 4) 结果

材料记录列表页 LCP 从约 1400ms 降至 1160ms，下降约 17%；底部菜单切换卡顿降低约 27%。排查流程沉淀为 `perf-debug-loop` Agent Skill。

### 8. 你在这个项目中的具体职责是什么？

#### 1) 监控方案

负责跨端性能监控方案落地，包括 H5 和小程序的 Adapter 兼容、性能指标采集和瓶颈定位。

#### 2) 页面优化

参与列表页和底部菜单的针对性优化，重点处理重复请求、非首屏逻辑阻塞等问题。

#### 3) 效果验证

通过优化前后的监控数据对比，并回归日期切换、数据更新和菜单交互等场景验证结果。

#### 4) 流程沉淀

将排查、优化和验收流程沉淀为 `perf-debug-loop` Agent Skill，便于后续复用。

### 9. 优化目标是怎么确定的？

#### 1) 目标来源

优化目标来自真实用户反馈和业务性能数据，例如列表页加载慢、底部菜单切换卡顿。

#### 2) 指标依据

监控发现列表页 LCP 约为 1400ms，因此把降低首屏加载时间作为重点，同时关注 SEO、TTI，避免影响关键内容展示。

#### 3) 验证路径

先确认监控口径，再定位重复请求和非首屏逻辑阻塞，最后用优化前后数据对比验证效果。

### 10. 当时考虑过哪些备选方案？为什么选择最终方案？

#### 1) 备选方案

包括增加缓存以减少重复请求、通过防抖降低请求频率、延迟非关键任务，以及优化组件渲染和计算逻辑。

#### 2) 方案评估

主要看性能收益、改造成本和业务正确性，判断方案是否真正减少关键路径耗时，以及是否影响数据实时性、首屏展示和 SEO/TTI。

#### 3) 方案选择

对日期切换场景，采用缓存命中后跳过重复请求并直接渲染；对非首屏逻辑延迟执行；对底部菜单优化排序计算。

#### 4) 效果验证

通过分阶段耗时、LCP 和核心交互回归验证，记录的结果为 LCP 从约 1400ms 降至 1160ms，菜单切换卡顿降低约 27%。

### 11. 项目中最大的卡点是什么？你如何推动解决？

#### 1) 初始问题

最大的卡点是监控数据不准确，初期无法判断性能瓶颈，优化方向一度不明确。

#### 2) 修正口径

重新梳理监控链路后，发现部分渲染耗时被误统计为接口耗时，于是把耗时拆分成 `fetch`、`render`、`paint` 三个阶段。

#### 3) 推进优化

根据重新分析的数据，针对重复请求和非首屏逻辑阻塞实施优化，并通过前后数据对比和业务回归验收。

#### 4) 结果

材料记录的结果是 LCP 降低约 17%，菜单切换卡顿降低约 27%。

### 12. 你遇到过什么挫折？当时怎么调整？

#### 1) 遇到的问题

前期性能监控把部分渲染耗时误算成接口耗时，导致针对网络请求做优化后页面性能没有明显改善。

#### 2) 调整方法

意识到继续盲目改代码效率不高后，先验证监控口径和数据准确性，再重新拆分 `fetch`、`render`、`paint` 阶段。

#### 3) 后续行动

找到重复请求和非首屏逻辑阻塞后，再进行针对性优化。

#### 4) 复盘

排查问题不能只看表面数据，要先确认数据是否可靠，再制定方案。

### 13. 项目时间节点如何安排？最后是否按计划完成？

#### 1) 阶段拆分

将任务拆成三阶段：完善跨端性能监控、定位瓶颈并实施优化、通过性能数据和业务回归验证效果。

#### 2) 优先级调整

前期定位较慢时，及时调整优先级，先修正监控口径，再集中处理重复请求和非首屏逻辑阻塞。

#### 3) 完成结果

材料记录的核心优化结果是列表页 LCP 从约 1400ms 降至 1160ms，底部菜单切换卡顿降低约 27%。

### 16. 学习 Supabase 时遇到的主要困难是什么？

#### 1) 主要难点

比较有挑战的是 RLS 权限控制和 Edge Functions 的鉴权机制，因为需要理清用户身份、数据访问权限和接口调用之间的关系。

#### 2) 解决方法

通过官方文档和 AI 辅助理解 RLS，结合需求明确用户只能访问自己的学习记录和投递数据；AI 请求统一经 Edge Functions 处理，在服务端校验 JWT 并保护 API Key。

#### 3) 验证重点

检查用户是否只能访问自己的数据，以及未登录或无效 Token 是否会被拒绝。

#### 4) 总结

全栈开发不只是功能跑通，还必须关注身份认证、数据隔离和接口安全。
