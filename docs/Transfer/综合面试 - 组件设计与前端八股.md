# 综合面试 - 组件设计与前端八股

## 1. 如何平衡组件通用性和特殊业务的逻辑？

## 答案

**核心原则：通用能力下沉，业务差异上浮；约定优于配置，扩展优于修改。**

### 分层策略

| 层级 | 职责 | 示例 |
|------|------|------|
| 基础 UI 组件 | 纯展示、无业务 | Button、Input、Modal |
| 模式组件 | 可配置的业务模式 | Form、Table、SearchBar |
| 业务组件 | 特定场景封装 | OrderList、UserProfileCard |
| 页面 | 编排与路由 | OrderPage |

### 平衡手段

1. **Props + Slots 组合**：通用行为用 props 控制，特殊 UI 用 slot/render props 注入
2. **Headless 模式**：逻辑与 UI 分离（如 TanStack Table + 自定义渲染）
3. **配置驱动**：JSON Schema / 配置表描述差异，而非 if-else 堆叠
4. **策略模式 / 插件化**：特殊逻辑注册为 plugin，不污染核心代码
5. **Composition API / Hooks**：复用逻辑，UI 各自定制

### 反模式

- 在通用组件里写 `if (business === 'order')` 分支地狱
- 过早抽象：只有一个使用场景就强行通用化
- 过度抽象：API 复杂到没人会用

### 实践口诀

> 三次重复再抽象；抽象到「变化点」而非「页面级」；业务组件可以依赖通用组件，通用组件绝不依赖业务模块。

## 2. 如何去开发一个高可复用的组件？需要考虑哪些方面？整个流程是什么？

## 答案

### 需要考虑的维度

| 维度 | 要点 |
|------|------|
| API 设计 | 单一职责、Props 语义清晰、默认值合理、受控/非受控一致 |
| 可组合性 | 支持 children、slot、compound components |
| 可扩展性 | className/style 透传、ref 转发、事件回调钩子 |
| 无障碍 a11y | 键盘导航、ARIA、焦点管理 |
| 样式方案 | CSS 变量 / Tailwind / CSS Modules，主题可定制 |
| 类型安全 | TypeScript 泛型、Discriminated Union |
| 性能 | memo、虚拟列表、懒加载、避免不必要 re-render |
| 测试 | 单元测试 + 交互测试 + 视觉回归 |
| 文档 | Storybook / 示例 / API 表格 / 变更日志 |

### 开发流程（8 步）

```
1. 需求调研 → 收集 2~3 个真实使用场景，找共性
2. API 设计 → 写 RFC/Design Doc，评审后再写代码
3. 原型验证 → Storybook 快速搭交互原型
4. 核心实现 → Headless 逻辑 + 默认 UI 分离
5. 边界处理 → 空态、加载、错误、超长文本、RTL
6. 测试覆盖 → Vitest + Testing Library + a11y 检测
7. 文档示例 → 每个 prop 有示例，常见组合有 Recipe
8. 发布迭代 → semver 版本管理，Breaking Change 写迁移指南
```

### API 设计示例

```tsx
// 好的 API：语义清晰 + 可扩展
interface DataTableProps<T> {
  data: T[];
  columns: ColumnDef<T>[];
  loading?: boolean;
  onRowClick?: (row: T) => void;
  renderEmpty?: () => ReactNode;  // 扩展点
}
```

### 验收标准

- 新场景接入成本 < 30 分钟
- 无业务代码侵入通用组件
- 文档 + 类型提示能自助完成集成

## 3. 从 0 到 1 开发一个新系统，选型怎么做？完整开发流程是什么？

## 答案

### 选型决策矩阵

| 维度 | 考量因素 | 常见选择 |
|------|----------|----------|
| 框架 | 团队熟悉度、生态、招聘、长期维护 | React / Vue |
| 组件库 | 设计规范匹配、定制成本、体积 | Ant Design / shadcn / 自研 |
| 状态管理 | 复杂度、DevTools、服务端状态 | Zustand + TanStack Query |
| 路由 | SSR 需求、嵌套路由 | React Router / Next.js |
| 打包工具 | 开发体验、构建速度、生态 | Vite（新项目首选） |
| 编译 | TS 严格模式、路径别名 | tsc + Vite / SWC |
| CSS | 设计系统、原子化 | Tailwind CSS |
| 测试 | 单元/集成/E2E | Vitest + Playwright |
| CI/CD | 预览环境、自动化 | GitHub Actions + Vercel |

### 选型原则

1. **团队优先**：选团队最熟悉的，而非「最新最潮」
2. **需求驱动**：ToB 重表格表单 → Ant Design；ToC 重体验 → 自研 + Tailwind
3. **渐进式**：MVP 阶段少引入中间件，验证后再加
4. **可替换性**：核心逻辑与框架解耦（Hooks / 纯函数）

### 从 0 到 1 完整流程

```
Phase 1 立项（1~2 周）
├── 需求梳理、用户故事、MVP 范围
├── 技术选型评审、架构设计文档
└── 设计系统 / UI 规范定稿

Phase 2 基建（1 周）
├── 脚手架：Vite + TS + ESLint + Prettier + Husky
├── 目录规范、路由、布局、主题
├── CI/CD 流水线 + 预览环境
└── 组件库 / 工具函数库初始化

Phase 3 核心开发（迭代）
├── 按模块拆分 Feature，前后端联调
├── Code Review + 单测覆盖关键路径
└── Storybook 维护组件文档

Phase 4 质量保障
├── E2E 测试核心流程
├── 性能基线（LCP、Bundle Size）
├── 安全审计（依赖扫描、XSS/CSRF）
└── 监控接入（Sentry、埋点）

Phase 5 上线
├── 灰度发布 → 全量
├── 运维文档、回滚方案
└── 复盘迭代
```

### 新项目推荐栈（2025 参考）

- React 18 + TypeScript + Vite 5
- Tailwind CSS + shadcn/ui（或 Ant Design）
- Zustand（客户端状态）+ TanStack Query（服务端状态）
- Vitest + Playwright
- Vercel / Netlify 部署

## 4. JS 的数据类型有哪些？存储方式有何不同？为什么？

## 答案

### 数据类型（8 种）

| 类型 | 分类 | 示例 |
|------|------|------|
| Number | 原始 | `42`, `NaN`, `Infinity` |
| String | 原始 | `'hello'` |
| Boolean | 原始 | `true`, `false` |
| Undefined | 原始 | 未赋值 |
| Null | 原始 | 空对象指针 |
| Symbol | 原始 | `Symbol('id')` |
| BigInt | 原始 | `100n` |
| Object | 引用 | `{}`, `[]`, `function` |

(typeof null === 'object' 是历史 bug)

### 存储方式

**原始类型**：栈（Stack）中存值本身（引擎实现可能优化，但语义上是按值传递）

**引用类型**：栈中存堆（Heap）地址指针，实际对象在堆中

```javascript
let a = 1;       // 栈：a = 1
let b = a;       // 栈：b = 1（拷贝值）
b = 2;           // a 仍为 1

let obj1 = { x: 1 };  // 栈：obj1 → 堆地址 A
let obj2 = obj1;      // 栈：obj2 → 同一地址 A
obj2.x = 2;           // obj1.x 也变为 2
```

### 为什么这样设计？

1. **性能**：原始类型固定大小，栈分配/回收 O(1)；对象大小不定，堆更灵活
2. **内存效率**：引用传递避免大对象拷贝
3. **不可变性**：原始类型不可变，保证 predictable 行为
4. **GC**：堆对象由垃圾回收器管理生命周期

## 5. ES6 中箭头函数和普通函数的区别？应用场景？

## 答案

### 核心区别

| 特性 | 普通函数 | 箭头函数 |
|------|----------|----------|
| this | 动态绑定，调用时决定 | 词法绑定，继承外层 this |
| arguments | 有 | 无，用 rest `...args` |
| new | 可作为构造函数 | 不能 new |
| prototype | 有 | 无 |
| yield | 可作为 Generator | 不能 |
| 写法 | `function() {}` | `() => {}` |

### this 差异示例

```javascript
const obj = {
  name: 'test',
  normal() { console.log(this.name); },    // 'test'
  arrow: () => { console.log(this.name); }, // undefined（继承外层，如 window）
};
```

### 应用场景

**适合箭头函数：**
- 回调函数（setTimeout、数组 map/filter）
- React 函数组件、Hooks 内回调
- 需要保持外层 this 的场景
- 单行表达式简写

**适合普通函数：**
- 对象方法（需要 this 指向对象）
- 构造函数 / Class 方法
- 需要 arguments 对象
- 需要动态 this 的场景（如 EventEmitter 回调）

## 6. 如何理解 React 的数据驱动？

## 答案

**核心思想：UI = f(state)，状态变 → 视图自动更新，开发者只关心「数据是什么」，而非「DOM 怎么改」。**

### 对比命令式 vs 声明式

```javascript
// 命令式：手动操作 DOM
countEl.textContent = count;
btn.disabled = count >= 10;

// 声明式（React）：描述 UI 与 state 的关系
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <>
      <span>{count}</span>
      <button disabled={count >= 10} onClick={() => setCount(c => c + 1)}>+</button>
    </>
  );
}
```

### 数据驱动的工作机制

1. **State 变更** → setState / dispatch
2. **调度更新** → React Scheduler 优先级调度
3. **Re-render** → 组件函数重新执行，生成新 Virtual DOM
4. **Diff** → 对比新旧 VDOM 树
5. **Commit** → 最小化更新真实 DOM

### 本质价值

- 降低心智负担：不用追踪 DOM 状态与数据的一致性
- 可预测：相同 state 产生相同 UI
- 组件化：数据与 UI 封装在一起，便于复用和测试

## 7. React 的演进思路是什么？

## 答案

**主线：解决「组件化 → 性能 → 并发 → 全栈」四个阶段的问题。**

### 演进时间线

| 阶段 | 版本 | 核心变化 |
|------|------|----------|
| 组件化 | React 0~15 | Virtual DOM、JSX、单向数据流、生命周期 |
| Fiber 架构 | React 16 | 可中断渲染、Error Boundary、Hooks 铺垫 |
| Hooks 时代 | React 16.8+ | 函数组件 + Hooks 替代 Class，逻辑复用 |
| 并发模式 | React 18 | Concurrent Rendering、Suspense、useTransition |
| 全栈框架 | React 19 / Next.js | Server Components、Actions、编译优化（React Compiler） |

### 演进核心思路

1. **抽象升级**：Class → Hooks → Server Components，每层减少样板代码
2. **性能优化**：Virtual DOM Diff → Fiber 可中断 → 选择性 Hydration → 编译时优化
3. **体验优先**：Suspense 统一加载态、Streaming SSR、渐进式 Hydration
4. **生态整合**：React DOM → React Native → React Server Components

### 设计哲学不变

- 单向数据流
- 声明式 UI
- 组合优于继承
- Learn once, write anywhere

## 8. JS 里的 Map 和 Set 有什么区别？怎么用？

## 答案

### 对比

| 特性 | Map | Set |
|------|-----|-----|
| 存什么 | 键值对 | 唯一值集合 |
| 键类型 | 任意类型 | — |
| 有序 | 插入顺序 | 插入顺序 |
| 大小 | `.size` | `.size` |
| 迭代 | `.entries()` `.keys()` `.values()` | `.values()` |
| 性能 | O(1) 查找 | O(1) 增删查 |

### Map 用法

```javascript
const map = new Map();
map.set('name', 'Alice');
map.set({ id: 1 }, 'obj key');  // 对象也可做 key
map.get('name');                 // 'Alice'
map.has('name');                 // true
map.delete('name');

// 初始化
const m = new Map([['a', 1], ['b', 2]]);
for (const [key, val] of m) { /* ... */ }
```

### Set 用法

```javascript
const set = new Set([1, 2, 2, 3]);  // {1, 2, 3}
set.add(4);
set.has(2);       // true
set.delete(1);

// 数组去重
const unique = [...new Set(arr)];

// 集合运算
const union = new Set([...setA, ...setB]);
const intersect = new Set([...setA].filter(x => setB.has(x)));
```

### 何时用 Map/Set 而非 Object/Array？

- 键不是字符串/Symbol → Map
- 频繁增删键值 → Map（Object 有原型链干扰）
- 需要去重 → Set
- 需要 O(1) 存在性判断 → Set

## 9. Vite 为什么比 Webpack 好用？怎么分包的？

## 答案

### Vite 更快的原因

| 对比项 | Webpack | Vite |
|--------|---------|------|
| 开发启动 | 全量打包后启动 | 利用浏览器 ESM，按需编译 |
| HMR | 模块越多越慢 | 精确到单模块，毫秒级 |
| 依赖预构建 | 每次打包 node_modules | esbuild 预构建，缓存复用 |
| 生产构建 | Webpack 自身 | Rollup（Tree-shaking 更优） |

**开发时流程：**
```
浏览器请求 /src/main.tsx
  → Vite 拦截，esbuild 转译 TS/JSX
  → 返回 ESM 模块
  → 浏览器原生 import，按需加载
```

### Vite 分包策略

**1. 默认行为（Rollup manualChunks 自动分割）**
- node_modules 按包自动拆分
- 动态 import 天然代码分割

**2. 手动分包配置**

```javascript
// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          'vendor-react': ['react', 'react-dom'],
          'vendor-ui': ['antd'],
          'vendor-charts': ['recharts'],
        },
      },
    },
  },
});
```

**3. 动态 import 路由级分包**

```javascript
const Home = lazy(() => import('./pages/Home'));
const Dashboard = lazy(() => import('./pages/Dashboard'));
```

**4. 分析工具**

```bash
npm i -D rollup-plugin-visualizer
# 生成 stats.html 查看 chunk 构成
```

## 10. 3 种优化 Vite 构建速度的方法 + 3 种优化打包体积的方法

## 答案

### 优化构建速度（3 种）

**1. 依赖预构建优化**
```javascript
optimizeDeps: {
  include: ['react', 'react-dom', 'lodash-es'],  // 强制预构建
  exclude: ['your-local-package'],                // 排除不需预构建的
}
```

**2. 减少 TS 检查阻塞**
- 开发环境不做 tsc，用 ESLint + IDE 检查
- 生产构建用 `vite-plugin-checker` 并行检查
- 或用 SWC 替代 Babel 转译

**3. 缩小构建范围**
- 路由懒加载，减少单次构建模块数
- `build.target: 'es2020'`，减少 polyfill 转译
- 多线程：`build.minify: 'esbuild'`（比 terser 快 10~20 倍）

### 优化打包体积（3 种）

**1. Tree Shaking + 按需引入**
```javascript
// ❌ import _ from 'lodash'
// ✅ import debounce from 'lodash-es/debounce'
import { Button } from 'antd';  // 配合 babel-plugin-import 或 unplugin
```

**2. 代码分割 + 动态加载**
```javascript
// 路由级、组件级、重型库按需加载
const Editor = lazy(() => import('@uiw/react-md-editor'));
```

**3. 压缩与依赖替换**
- `build.rollupOptions.output.manualChunks` 分离大依赖
- 用轻量替代：`moment → dayjs`，`lodash → lodash-es`
- 图片压缩、Gzip/Brotli（Vercel/Nginx 开启）
- `rollup-plugin-visualizer` 定位体积大户

## 11. 如何监控打包构建速度和体积？可以用什么工具和方法？

## 答案

### 构建速度监控

| 工具/方法 | 说明 |
|-----------|------|
| `vite build --debug` | 输出各阶段耗时 |
| `DEBUG=vite:* vite build` | 详细 debug 日志 |
| `vite-plugin-inspect` | 可视化插件执行耗时 |
| CI 计时 | GitHub Actions `time npm run build` 记录趋势 |
| `bundler-speed-measure-webpack-plugin` | Webpack 专用，Vite 可用自定义插件 |

**CI 示例：**
```yaml
- name: Build with timing
  run: |
    START=$(date +%s)
    npm run build
    END=$(date +%s)
    echo "Build took $((END - START))s"
```

### 打包体积监控

| 工具 | 用途 |
|------|------|
| `rollup-plugin-visualizer` | 生成 treemap 分析报告 |
| `vite-bundle-visualizer` | Vite 专用体积可视化 |
| `bundlesize` / `size-limit` | CI 中设置体积阈值，超限 fail |
| `source-map-explorer` | 分析 source map 定位大模块 |
| Lighthouse CI | 运行时性能 + 资源体积 |
| Vercel Analytics | 部署后真实用户加载性能 |

### 体积预算（Size Budget）实践

```json
// package.json
{
  "size-limit": [
    { "path": "dist/assets/*.js", "limit": "500 KB" }
  ]
}
```

```javascript
// vite.config.ts
import { visualizer } from 'rollup-plugin-visualizer';

plugins: [
  visualizer({ open: true, gzipSize: true, brotliSize: true }),
]
```

### 持续监控流程

```
每次 PR → CI 构建 → 记录 build time + bundle size
  → 与 main 分支对比 diff
  → 超出阈值 10% 则 CI 警告/失败
  → 定期（每周）Review visualizer 报告，清理无用依赖
```

### 推荐组合

- 开发阶段：`rollup-plugin-visualizer`
- CI 门禁：`size-limit` 或 `bundlesize`
- 生产监控：Sentry Performance + Web Vitals（LCP/FCP/TTI）
