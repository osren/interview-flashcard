**滴滴出行 · 企业版商旅** | 前端开发实习生 | 2026.01 — 2026.07

### 项目一：商旅 H5/小程序性能监控与体验优化

- **问题背景**：商旅列表页 LCP 约 1400ms，星河底部菜单切换卡顿，用户体验待优化，但此前缺少函数级性能数据
- **我的工作**：
  - 在业务仓搭建 `perf-monitor.js`，提供 `mark/measure/report` 三段式 API，H5/星河双端通过 `Adapter` 模式抽象统一上报，监控跨页链路、LCP/FCP 和关键接口耗时
  - 列表页优化（三项）：
    1. **请求去重**：切换日期时缓存已加载的当天数据仍会触发请求；新增 `cacheHit → skipFetch → directRender` 状态机，命中缓存时跳过请求直接渲染
    2. **上报口径修正**：原统计将"重渲染耗时"误计入"接口耗时"，无法定位网络瓶颈还是渲染瓶颈；按 `render/fetch/paint` 三桶拆分上报
    3. **非关键路径延后**：定位到 `privacyPopList` 等非首屏逻辑延长 LCP，通过 `defer()` 包装改为延后加载
  - 星河底部菜单：定位到切换时排序计算开销大，通过 `useMemo` 缓存已排序结果，避免重复计算
- **结果**：列表页 LCP **1400→1160ms（↓17%）**；星河底部菜单切换卡顿约 **↓27%**
- **沉淀**：将「定位 → 诊断 → 优化 → 验收」的性能排查流程固化为可复用 Agent Skill（`perf-debug-loop`），为后续性能问题提供函数级监控基础设施
- **重难点**：跨端上报在 H5 Web 与星河小程序两套环境下的抽象兼容方案（`Adapter` 层抹平 `PerformanceObserver` / 小程序 `wx.getPerformance` 差异）；首屏关键路径与非关键路径的取舍策略（平衡 LCP 优化与 SEO/TTI 指标）

### 项目二：商旅机酒火接口告警智能降噪

- **问题背景**：机酒火线上接口告警量大，业务正常拒绝（无票/已退改/超时未支付）占比高，真故障被淹没，值班容易漏看
- **我的工作**（基于 LLM 的告警智能降噪）：
  - **接口清单**：以 `api/` 目录及 axios 实例声明为线索做 AST 扫描，自动生成各品类核心接口清单，替代人工维护
  - **severity 路由**：按接口类型配置优先级基线（`severity[routes['/api/order']] = 'P1'`），确保核心链路告警直接触发告警通道
  - **业务正常拒绝规则**：在 Prompt 中通过 `business_reject` 字段约束"可拒绝"场景（无票/已退改/重复提交），模型仅对符合规则的告警执行降噪，防止误过滤
  - `**safeFallback()**`：模型超时/解析异常时统一降级为保守结论（severity=P2），保证降噪链路异常时不吞告警
  - **评测闭环**：`/judge` 接口负责单条 case 判定，`/eval` 接口负责批量回归，以 `FN_rate` 为核心评估指标，持续监控降噪召回率
- **重难点**：LLM 判定结果与业务认知存在偏差时的对齐机制（评测集构建 + gold 标注 + 差异 case 反哺 Prompt 迭代）；新增业务品类接入时
