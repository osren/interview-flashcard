## 完整回答（段落形式，2000 字以内）

在实习和项目开发中，我深度使用了多种 AI 工具，包括日常开发中的 Claude Code、GitHub Copilot、ChatGPT，以及基于 Claude API 自建的智能化工作流。其中最具代表性的案例是在滴滴实习期间，我主导设计并实现了一套 **AI 驱动的告警智能降噪引擎**，将日告警量从 500+ 降低到 50-80，准确率达到 94%，显著改善了值班体验和故障响应效率。

这个项目源于火车票业务面临的严重告警噪音问题。当时系统每天产生 500 多条告警，但真正需要处理的故障不到 10%，大量「无票」「已退改」等正常业务结果被误判为异常，值班同学被噪音淹没，既影响工作效率，也存在真故障被掩盖的漏报风险。传统规则引擎虽然确定性强，但面对数百个接口和动态变化的业务逻辑，规则维护成本极高且难以覆盖长尾场景。为此，我提出用大模型替代传统规则引擎，通过语义理解和上下文推理来进行告警分类。

在架构设计上，我采用了 Domain 架构模式，按业务域拆分配置。每个域（如火车票、酒店）包含独立的路由表和判定话术，新业务接入只需添加新 Domain，不影响现有配置。核心流程分为四步：首先根据 URL 进行路由识别，将告警归类到查询、支付、订单等不同类别；然后拼装 Prompt，包含全局规则（什么是噪音、如何定级）、分类细则（查询类的无票是正常业务拒绝）和具体案情（当前这条告警的 URL、错误码、错误信息）；接着调用 Claude API 进行判定，返回结构化输出（是否上报、严重等级、判定理由）；最后根据判定结果过滤噪音或推送真故障。

Prompt 工程是这个项目的关键技术点。我设计了三层 Prompt 结构：system-global 定义全局规则，system-category 针对不同分类提供细则，user 提供具体案情。通过不断迭代优化，从最初的直接提问（准确率 76%）到给出规则说明（准确率 89%），再到加入 Few-shot 案例（准确率 94%），每次改进都基于 gold 标注数据集的评测结果。我还建立了多模型对比验证机制，测试了 Claude Sonnet 3.5、GPT-4、Qwen 等模型，最终选择了准确率和成本平衡最好的 Claude Sonnet 作为主力模型。

为保证生产可靠性，我设计了完善的兜底机制：当信息不全或 AI 返回异常时，系统会倾向保守上报而非直接丢弃，遵循「宁可误报、绝不漏报」的原则，因为生产故障的代价远高于告警噪音。同时，我实现了性能优化和可观测性：通过批处理（积累 10 条或 200ms 后批量请求）和缓存（相同 URL + errorCode 缓存 1 小时），将 P99 延迟从 800ms 降到 150ms，调用成本降低 60%；建立了完整的监控体系，记录每次 AI 调用的延迟、token 消耗、决策结果和成本，按天汇总分析。

为降低接入成本，我还开发了 Claude Code Skill 实现自动化接入流程。用户只需一句话「帮我接入酒店业务的告警降噪」，Skill 就会自动扫描业务代码提取所有 API 接口，生成路由表初稿，根据接口特征推荐分类，生成 Prompt 模板，输出接入清单供人工确认。这将新域接入时间从 2 天缩短到 2 小时，大幅提升了工程效率。

项目上线后取得了显著成效：日告警量从 500+ 降到 50-80，噪音过滤率达到 85%，准确率达到 94%，漏报率控制在 1% 以内。值班同学反馈从「每天被吵 500 次」到「只看 50 条真问题」，工作体验显著改善；P0 故障平均发现时间从 30 分钟缩短到 5 分钟，没有发生因噪音导致的漏报事故；新业务接入成本降低 75%，规则维护成本降低 80%。

这个项目让我深刻理解了 AI 在实际工程中的定位和应用方法。首先，AI 不是万能的，需要明确边界：它适合需要理解业务语义、规则动态变化的场景，但不适合需要 100% 准确或性能极致敏感的场景。我们的策略是让 AI 做决策辅助（告警分类），传统代码做执行保障（兜底机制、监控告警）。其次，Prompt 工程是关键能力，同一个问题用不同 Prompt 准确率差异巨大，需要明确任务边界、提供充分上下文、设计兜底策略。第三，评测体系是从 demo 到生产的必经之路，没有 gold 数据集和持续迭代就是在"瞎改"，每次优化都需要数据支撑。

这个案例提炼出的方法论也被我应用到了其他场景。在页面性能分析项目中，我设计了 Claude Code Skill 通过读源码估算函数耗时、识别性能瓶颈、输出优化建议，配合运行时 PerfMonitor 监控验证，实现了列表页 LCP 下降 17% 的优化成果。在日常开发中，我也持续使用 GitHub Copilot 进行代码补全，将重复性代码编写时间缩短 60%；使用 ChatGPT 进行技术方案调研，快速了解业界最佳实践。

总的来说，我认为 AI 是强大的生产力工具，但从 demo 到生产需要工程化能力：准确性靠评测体系和持续迭代保障，可靠性靠兜底机制和异常处理保障，可观测性靠全链路监控保障，可维护性靠配置化和文档化保障。Prompt 工程正在成为软件工程师的新必备技能，就像写代码需要编程能力一样，用好 AI 需要掌握如何清晰描述任务、提供有效上下文、设计输出格式、处理不确定性。我会持续关注 AI 能力边界和最佳实践，在新项目中不断探索 AI + 工程的更多结合点。

## 二、典型案例：用 AI 解决告警噪音问题

### 问题背景

在滴滴实习期间，火车票业务的告警系统面临严重的**噪音问题**：

**现状数据**：
- 每天接收 **500+ 条告警**
- 真正需要处理的故障 < 10%
- 值班同学被大量「无票」、「已退改」等正常业务结果淹没
- 漏报风险高：真故障被噪音掩盖

**核心矛盾**：
```
传统规则引擎                 实际业务
  ↓                           ↓
固定规则难以覆盖     ←VS→    数百个接口 × 动态业务逻辑
人工维护成本高       ←VS→    新接口快速迭代
```

---

### 解决方案：AI 驱动的智能降噪引擎

我主导设计并实现了一套 **AI 告警分类系统**，用大模型替代传统规则引擎：

#### 核心架构

```
告警输入（接口错误）
    ↓
路由识别（按 URL 分类）
    ↓
Prompt 拼装（说明书 + 案情）
    ↓
LLM 判定（Claude API）
    ↓
结构化输出（报/不报 + 等级 + 理由）
    ↓
过滤噪音 / 推送真故障
```

#### 关键技术决策

**1. Domain 架构设计**

按业务域拆分配置，每个域独立维护：
```
domains/
├── railway/           # 火车票域
│   ├── routes.yaml    # 路由表：URL → 分类
│   └── prompts/       # 判定话术
│       ├── system-global.md
│       ├── system-query.md
│       ├── system-payment.md
│       └── user.md
└── hotel/             # 酒店域
    └── ...
```

**优势**：
- 新业务接入只需添加新 Domain，不影响现有配置
- 各域独立演进，避免「一个模板管所有」

**2. Prompt 工程**

设计了三层 Prompt 结构：

```yaml
system-global.md:     # 全局规则
  - 什么是告警噪音
  - 如何定义严重等级
  - 信息不全时的兜底策略

system-{category}.md: # 分类细则
  - 查询类：无票/无座是正常业务拒绝
  - 支付类：订单已支付是业务reject
  - 订单类：已取消/已退改是正常状态

user.md:              # 案情模板
  - URL: {url}
  - errorCode: {code}
  - errorMsg: {message}
```

**实际案例**：

输入告警：
```json
{
  "url": "/esapp/railway/train/queryLeftTicket",
  "errorCode": "1",
  "errorMsg": "当前查询无票"
}
```

AI 输出：
```json
{
  "should_report": false,
  "severity": "P3",
  "business_reject": true,
  "reason": "余票查询返回无票是正常业务结果，不应告警"
}
```

**3. 多模型对比验证**

为保证准确性，我设计了评测体系：

| 模型 | 准确率 | 成本 | 选型 |
|------|-------|------|------|
| Claude Sonnet 3.5 | 94% | 中 | ✅ 主力 |
| GPT-4 | 92% | 高 | 备选 |
| Qwen | 87% | 低 | 探索 |

使用 **gold 标注数据集**（100+ 条人工标注的告警）进行评测。

**4. 兜底机制设计**

AI 判定不确定时的保守策略：
```javascript
// 兜底规则
if (信息不全 || AI返回异常) {
  return {
    should_report: true,  // 倾向上报
    severity: "P2",       // 中等级别
    reason: "信息不足，保守上报"
  };
}
```

**原则**：宁可误报，绝不漏报（生产故障 > 告警噪音）

### 技术实现细节

#### 1. 接入流程自动化（Claude Code Skill）

设计了 `ai-monitor-接入` Skill，自动化新域接入：

```bash
# 用户只需一句话触发
"帮我接入酒店业务的告警降噪"

# Skill 自动执行
1. 扫描业务代码，提取所有 API 接口
2. 生成 routes.yaml 初稿
3. 根据接口特征推荐分类
4. 生成 Prompt 模板
5. 输出接入清单供人工确认
```

**核心价值**：接入时间从 **2 天缩短到 2 小时**

#### 2. 性能优化

**问题**：每条告警都调 LLM，延迟 300-800ms

**方案**：
- **批处理**：积累 10 条或 200ms 后批量请求
- **缓存**：相同 URL + errorCode 缓存 1 小时
- **异步**：告警判定不阻塞主流程

**效果**：
- P99 延迟：800ms → 150ms
- 成本：每天调用 500 次 → 200 次（缓存命中率 60%）

#### 3. 可观测性

实现了完整的监控体系：
```javascript
// 每次 AI 调用记录
{
  url: '/esapp/...',
  model: 'claude-3-sonnet',
  latency: 245,
  tokens: 856,
  decision: 'filtered',
  cost: 0.0023
}

// 按天汇总
- 总调用量、成本
- 各域调用分布
- 准确率（抽样人工复核）
```

### 关键学习与思考

#### 1. AI 的定位

AI **不是万能的**，需要明确边界：

| 适合 AI | 不适合 AI |
|---------|----------|
| 需要理解业务语义 | 需要 100% 准确（如支付金额） |
| 规则动态变化 | 确定性逻辑（如配置开关） |
| 长尾场景多 | 性能极致敏感（<10ms） |

我们的策略：
- AI 做**决策辅助**（告警分类）
- 传统代码做**执行保障**（兜底、监控）

#### 2. Prompt 工程的重要性

**同一个问题，不同 Prompt 准确率差异巨大**：

```
V1（直接问）: 准确率 76%
"这个错误需要告警吗？"

V2（给规则）: 准确率 89%
"根据以下规则判断..."

V3（给案例 + Few-shot）: 准确率 94%
"以下是正常业务拒绝的例子...
 以下是真故障的例子...
 现在判断这条..."
```

**经验**：
- 明确任务边界（要什么输出格式）
- 提供充分上下文（业务规则、案例）
- 设计兜底策略（不确定时怎么办）

#### 3. 评测驱动迭代

没有评测体系就是"瞎改"：

```
建立 gold 数据集（100+ 条人工标注）
    ↓
每次 Prompt 改动后跑评测
    ↓
对比准确率、召回率、F1
    ↓
case-by-case 分析错误原因
    ↓
针对性优化 Prompt
```

**效果**：
- V1 → V2：准确率 76% → 89%（增加规则说明）
- V2 → V3：准确率 89% → 94%（Few-shot 案例）

### 可复用的方法论

这个案例提炼的**通用 AI 应用框架**：

```
1. 明确问题边界
   - AI 擅长什么？不擅长什么？
   - 准确率要求？容错空间？

2. 设计 Prompt 工程
   - 全局规则 + 分类细则 + 具体案情
   - Few-shot 案例提升准确率

3. 建立评测体系
   - gold 数据集
   - 准确率、召回率、F1
   - case-by-case 错误分析

4. 工程化落地
   - 兜底机制（AI 失败时怎么办）
   - 性能优化（缓存、批处理）
   - 可观测性（成本、延迟、准确率）

5. 持续迭代
   - 收集线上 badcase
   - 补充到 gold 数据集
   - 优化 Prompt
```

这套方法论后续应用到了**页面性能分析**等其他场景。

## 四、对 AI 工具的理解

### 1. AI 是工具，不是替代

**AI 擅长**：
- 处理大量文本信息（读代码、分析日志）
- 模糊匹配与语义理解（告警分类）
- 生成样板代码（减少重复劳动）

**人的价值**：
- 定义问题和边界
- 设计架构和策略
- 审核 AI 输出
- 处理 corner case

### 2. 工程化是关键

AI 从 demo 到生产的鸿沟：
- **准确性**：评测体系 + 持续迭代
- **可靠性**：兜底机制 + 异常处理
- **可观测**：成本、延迟、准确率监控
- **可维护**：配置化、文档化

### 3. Prompt 工程是新能力

就像写代码需要编程能力，用好 AI 需要 **Prompt 工程能力**：
- 如何清晰描述任务
- 如何提供有效上下文
- 如何设计输出格式
- 如何处理不确定性

这是软件工程师的新必备技能。
