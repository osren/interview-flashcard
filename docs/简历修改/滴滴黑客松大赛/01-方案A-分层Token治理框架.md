## 一、问题理解与方案构想

### 1.1 真实业务背景：AI 已落地，Token 成规模化瓶颈

滴滴企业版商旅业务中，机票 / 酒店 / 火车票线上接口错误告警量大、噪音占比高。典型噪音包括：

- 业务正常拒绝（无票、已退改、重复提交）
- 低价值展示类错误（NPS、公告、分享页配置）
- 信息不全的原始告警
- 三方 / 非自有接口异常

后果：真故障被淹没，值班被刷屏，漏看风险上升。

我们已落地 **AI 监控降噪系统**（error-triage / ai-monitor-deposer）：告警到达值班前，由大模型判定是否上报（`should_report`）、严重等级（P0~P3）、错误类型与中文依据。系统遵循「**宁可误报，不可误杀**」，判定质量优先，因此**每条告警仍需走一次 LLM**——降本不能靠「少调模型」，而要靠「调得更省」。

随着机票、酒店 domain 陆续接入，以及向出行侧客服判责、需求理解等场景扩展，Token 正从「试点可接受成本」变为「规模化部署瓶颈」。这正是赛题所说的：**完成同样任务，花了不必要的 Token**。

### 1.2 问题本质：六类 Token 浪费根因

| 浪费类型 | 在商旅告警场景的具体表现 | 严重度 |
|----------|--------------------------|--------|
| 上下文过长 | payload 携带完整 response 大段 JSON、无关 trace 字段 | 高 |
| Prompt 冗余 | 10 个 category 规则被全量拼入 system，而非按路由 key 按需加载 | 高 |
| RAG / 检索不精准 | 接入阶段 discover 全量扫描项目，token ∝ 项目大小 | 中 |
| 模型路由不当 | 简单归属判别（自有/三方）本可走规则，却与大模型判定混在同一链路 | 中 |
| 输出不受控 | `reason` 偶发超长 markdown，增加 output token 与解析失败率 | 中 |
| 失败重试 | JSON 解析失败时反复原样重调，而非 fallback 保守上报 | 低~中 |

**核心洞察**：业务不允许「少调模型」来降本（漏报 ≈ 0），因此主战场是：

1. **单次调用瘦身**（上下文 + Prompt + 输出）
2. **工程链路零 LLM 化**（路由 / 漂移检查 / 增量接入）
3. **结果复用**（指纹 / 语义缓存）

### 1.3 方案构想：分层 Token 治理框架（Tiered Token Governance）

将 Token 优化从「靠感觉砍 Prompt」升级为「可度量、可验证、可复用的 AI 工程能力」：

```
告警 / 请求入站
    → ① 路由层（Router First）        — 零 LLM 完成分类与归属
    → ② 上下文层（Context Trim）      — 字段裁剪、增量处理
    → ③ Prompt 层（Dynamic Assembly） — 按场景模块化拼装
    → ④ 模型层（Model Tiering）       — 复杂度分级选模型
    → ⑤ 输出层（Output Constraint）   — JSON Schema + 长度约束
    → ⑥ 缓存层（Result Reuse）        — 指纹 / 语义缓存复用判定
    → LLM 调用（仅在必要时、用最小上下文）
```

#### 三大创新点

**创新点 1：Router First —— 先分类，再决定「用什么 Prompt、调什么模型」**

pathname 归一 → 自有前缀归属判别 → 有序规则匹配 → 得到 prompt key。非自有前缀直接路由至 `non-core`，无需加载核心业务 category 的 prompt。这是**零 Token 的路由决策**，已在火车票 domain 验证。

**创新点 2：Dynamic Prompt Assembly —— 按需拼装，不全量加载**

```
system prompt = _base.md（全局原则，~200 token）
             + <key>.md（当前 category 规则，~100~300 token）
```

改造前全量加载可达 3000+ token；改造后单次约 800 token 量级。

**创新点 3：Eval 驱动降本 —— 降本不能牺牲「宁可误报不可误杀」**

| 门禁指标 | 阈值 |
|----------|------|
| input token | ↓ ≥ 40% |
| 准确率 / F1 | 下降 ≤ 1% |
| 漏报率 | 不升（目标 ≈ 0） |

### 1.4 与滴滴更大 AI 版图的关系

| 场景 | 复用方式 |
|------|----------|
| 赛题 01 需求理解 | 路由层识别场景，Prompt 层按场景加载规则 |
| 赛题 02 路线信任 | 上下文层只注入当前路段关键信息 |
| 赛题 03 纠纷判责 | 简单节点小模型，复杂推理上大模型 |
| 客服 FAQ | 语义缓存命中则跳过 LLM |

## 二、实现路径与 Demo 规划

### 2.1 现状与改造基线

| 资产 | 状态 | Token 相关价值 |
|------|------|----------------|
| error-triage 通用引擎 | ✅ | 路由 + 动态 prompt 骨架已有 |
| 火车票 domain | ✅ | 可跑真实告警 replay |
| `/judge` `/eval` API | ✅ | 可量化 before / after |
| discover sync / drift-check | ✅ | 接入增量；维护零 LLM |

**Hackathon MVP**：字段裁剪 middleware、Token 埋点看板（P0）；指纹缓存、模型分级（P1）。

### 2.2 改造清单

| 优先级 | 改造项 | 预期节省 |
|--------|--------|----------|
| P0 | 字段裁剪 | input ↓ 40~60% |
| P0 | 动态 Prompt 强制化 | system ↓ 60~70% |
| P0 | 输出约束 + fallback | output ↓ 20%，重试 ↓ |
| P0 | Token 埋点 + gold baseline | 可度量 |
| P1 | 指纹缓存（仅噪音判定） | 重复告警近似零 LLM |
| P1 | 模型分级 | 成本进一步 ↓ |

### 2.3 四阶段路径

| 阶段 | 时间 | 交付 |
|------|------|------|
| 一 | 第 1 周 | 埋点 + gold 50 条 + baseline 报告 |
| 二 | 第 2~3 周 | P0 改造 + eval 对比 |
| 三 | 第 4 周 | 缓存 + 模型分级 |
| 四 | 第 4~5 周 | 灰度 → 全量 +《Token 治理手册》 |

### 2.4 Demo（约 5 分钟）

**主题**：「同一条告警，Token 从 4700 → 1350，判定结论一致」

| 环节 | 内容 |
|------|------|
| Before | 全量 response + 全量 system → **4700 token** |
| 六层讲解 | router → `_base`+key → 5 字段 → JSON 约束 |
| After | 最小上下文 → **1350 token**，结论一致 |
| Eval | token ↓ 71%，准确率下降 ≤ 0.5%，漏报 0 |

## 三、预期价值

### 3.1 量化预估（日告警 10 万次）

| 指标 | 改造前 | 改造后 | 变化 |
|------|--------|--------|------|
| 单次合计 token | ~4700 | ~1350 | ↓ 71% |
| 日 LLM 成本（¥0.07/1K 粗算） | ¥32,900 | ¥9,450 | 节省 ¥23,450/天 |
| 月节省 | — | — | **约 ¥70 万/月** |

> 单价为估算，以网关账单为准。

### 3.2 业务与组织价值

- **成本**：告警降噪可规模化部署
- **性能**：上下文更小 → P95 延迟下降
- **稳定性**：Eval 门禁守住漏报底线
- **组织**：Token 可观测 + Eval 可门禁 + 框架可复用

### 3.3 风险与对策

| 风险 | 对策 |
|------|------|
| 准确率 / 漏报恶化 | Eval 硬门禁；漏报 > 0 回滚 |
| 缓存误判复用 | 仅缓存 `should_report=false` |
| 模型分级误路由 | 不确定时走大模型 |

## 四、答辩话术（30 秒）

> 我们不是让模型「少干活」，而是让模型「少干无效活」。通过 Router First、动态 Prompt、Eval 驱动，在商旅告警降噪上实现 Token ↓ 约 71%、准确率几乎不变、漏报为 0——这不是 Prompt 技巧，是可复用的 AI 工程能力。
