## 一、问题理解与方案构想

### 1.1 场景选择：为什么不做「再砍一次告警 Prompt」

方案 A 已覆盖单次结构化判定的降本路径。但滴滴内部还有一类更高频、更「费 Token」的用法：

**研发知识问答 / 多轮 Agent**（含客服知识库、内部文档助手）：

- 用户一句话 → Agent 反复搜文档、读代码、调 API → 再生成长答案
- 历史对话全量回传，第 5 轮起 input 爆炸
- RAG top-k 一次塞入多篇长文，大半与问题无关
- 工具超时/空结果时原样重试，中间「思考」过程也进上下文

这类场景的浪费结构与告警判定不同：**调用次数可变、上下文随轮次膨胀、检索与工具是主成本源**。需要另一套治理思路——**任务级 Token 预算编排（Token Budget Orchestrator）**。

### 1.2 问题本质：从「单次调用浪费」到「任务生命周期浪费」

| 浪费类型 | 在多轮知识问答 / Agent 中的表现 | 严重度 |
|----------|--------------------------------|--------|
| RAG 不精准 | top-5 各 2k token 正文全塞入；重复段落、目录噪音 | 高 |
| 历史重复携带 | 每轮把完整 history + 全部工具日志回传 | 高 |
| 工具失败重试 | 同一检索/API 连续失败仍原 prompt 重调 3 次 | 高 |
| 模型路由不当 | FAQ / 指代消解 / 简单抽取也上大模型 | 高 |
| 无意义中间输出 | Agent 长篇 chain-of-thought、冗长 tool 叙述进下一轮 | 中 |
| Prompt 冗余 | 每次注入全套工具说明与长示例 | 中 |

**核心洞察**：省 Token 的最高杠杆不是「把某次 prompt 砍短 20%」，而是：

1. **能短路就短路**（缓存 / 规则 / 小模型命中则结束任务）
2. **能少召回就少召回**（分层 RAG，按预算配额取正文）
3. **能增量就增量**（稳定上下文缓存，只传变化）
4. **给任务设预算上限**（超预算强制收敛，禁止无限工具循环）

### 1.3 方案构想：Token Budget Orchestrator（TBO）

把每一次用户请求视为一个**带预算的任务**，而不是一串无约束的 LLM 调用：

```
用户问题
  → ① 预算初始化（按意图分配 input/output/工具次数配额）
  → ② 级联短路（规则 → 精确缓存 → 语义缓存 → 小模型）
        └─ 任一命中且置信足够 → 直接返回（零或极少大模型 Token）
  → ③ 分层 RAG（摘要召回 → 相关性过滤 → 按剩余预算拉正文）
  → ④ Agent 执行环（规划 → 工具 → 截断结果 → 滚动摘要）
        └─ 工具失败：分类处理，禁止盲目原样重试
  → ⑤ 大模型终答（仅复杂合成时启用；输出受长度约束）
  → ⑥ 记账与回写（消耗归因；高质量结果写入语义缓存）
```

#### 三大创新点

**创新点 1：任务级 Token 预算，而不是「调完再算账」**

按意图模板分配预算，例如：

| 意图类型 | input 预算 | 工具次数上限 | 是否允许大模型 |
|----------|------------|--------------|----------------|
| FAQ / 政策查询 | 800 | 1 | 优先缓存/小模型 |
| 排障（多文档） | 2500 | 3 | 允许 |
| 代码定位 / 改造建议 | 4000 | 5 | 允许 |
| 开放闲聊 | 500 | 0 | 小模型或拒答 |

执行中实时扣减；剩余预算 < 阈值时：停止新工具调用，改为「基于已有证据作答」或「请用户缩小范围」。

**创新点 2：分层 RAG —— 相关性优先于「多塞一点」**

```
Stage 1  向量/关键词召回标题+摘要（每条 ~50 token）→ 取 top-20
Stage 2  小模型或重排器打分，滤到 top-3~5
Stage 3  仅对入选文档拉正文 chunk；单 chunk ≤ 300 token
         且 Σ(chunk) ≤ 当前剩余 input 预算的 60%
```

对比「一次塞 5×2000 token」：同样覆盖 3 篇有效文档，input 可从 ~10k 降到 ~1k 量级，且噪音更少。

**创新点 3：Agent 工具环的「失败分类器 + 结果闸门」**

| 工具结果 | 策略 | Token 效果 |
|----------|------|------------|
| 成功且相关 | 截断至 N 字写入工作记忆，原文不进下一轮全量 history | ↓ 历史膨胀 |
| 空结果 / 无命中 | 换查询改写 **至多 1 次**，禁止同参重试 | ↓ 无效重试 |
| 超时 / 4xx | 记失败原因，切换备用工具或直接降级回答 | ↓ 盲目重试 |
| 低相关 | 不写入上下文，扣一次工具配额 | ↓ 噪音上下文 |

中间推理默认 **不回传** 给下一轮（仅保留结构化「已确认事实」列表）；需要解释时再生成，避免 CoT 污染上下文。

### 1.4 与方案 A、与滴滴场景的关系

| 维度 | 方案 A | 方案 B（本方案） |
|------|--------|------------------|
| 典型场景 | 告警单次判定 | 知识问答 / 多轮 Agent |
| 降本主杠杆 | 单次瘦身 | 短路 + 检索 + 增量 + 预算硬顶 |
| 能否少调大模型 | 基本不能（漏报约束） | 大量可以（FAQ/缓存命中） |
| 可组合性 | 可作 TBO 中「复杂判定」叶子节点 | 可调度方案 A 的引擎做子任务 |

落地样板可落在：**商旅/企业版内部文档助手、研发 oncall 知识库、客服标准问答**；与出行侧需求理解、纠纷判责的「多跳工具」形态同构。

## 二、实现路径与 Demo 规划

### 2.1 架构组件（MVP）

| 组件 | 职责 | 优先级 |
|------|------|--------|
| Intent Router | 规则/小模型识别意图 → 选预算模板 | P0 |
| Semantic Cache | 问题 embedding 命中历史高置信答案 | P0 |
| Hierarchical Retriever | 摘要索引 → 重排 → 按预算拉正文 | P0 |
| Working Memory | 滚动摘要 + 事实列表；工具结果闸门 | P0 |
| Tool Governor | 次数上限、失败分类、禁同参重试 | P0 |
| Cost Meter + Eval | 任务级 token/质量/时延；gold 回归 | P0 |
| Model Cascade | 小模型试答 → 置信不足再升级大模型 | P1 |

### 2.2 改造 / 建设清单

| 优先级 | 改造项 | 针对方向 | 预期效果 |
|--------|--------|----------|----------|
| P0 | 意图 → 预算模板 | 多模型路由 / 评估 | 简单任务默认低预算 |
| P0 | 语义缓存（高置信直出） | 缓存 | 命中请求大模型 Token ≈ 0 |
| P0 | 分层 RAG + 预算封顶 | RAG | 检索相关 input ↓ 70%+ |
| P0 | 会话滚动摘要 + 增量消息 | 上下文 / 增量 | 第 N 轮 input 接近常数 |
| P0 | 工具失败分类器 | Agent | 无效重试 ↓ 80%+ |
| P1 | 小模型先答、大模型兜底 | 多模型路由 | 大模型调用占比 ↓ 40~60% |
| P1 | Prompt 工具 schema 按需注入 | Prompt 精简 | system ↓ 30~50% |

### 2.3 四阶段路径

| 阶段 | 时间 | 交付 | 验证 |
|------|------|------|------|
| 一 | 第 1 周 | 埋点（任务级）+ FAQ gold 100 条 + baseline | 报告可复现 |
| 二 | 第 2 周 | 语义缓存 + 分层 RAG | 命中率、检索 token、答案质量 |
| 三 | 第 3 周 | Working Memory + Tool Governor | 多轮 token 曲线变平；重试率 ↓ |
| 四 | 第 4 周 | 小模型级联 + 预算硬顶灰度 | 总成本 ↓、满意度不降 |

### 2.4 Demo（约 5 分钟）

**主题**：「同一道排障问题，从 6 次大模型 + 1.2 万 token → 1 次小模型检索合成 + 2.1k token」

| 环节 | 内容 |
|------|------|
| 场景 | 「火车票 transferLeftTicket 报参数错误怎么排查？」多轮追问 |
| Before | 全量 history + top-5 长文 + 工具失败重试 2 次 → **~12k token / 任务** |
| TBO 讲解 | 预算模板 → 缓存未命中 → 摘要召回 20 → 重排取 3 → 正文按预算拉取 → 工具 1 次成功截断 |
| After | **~2.1k token**，答案含 3 条可点击文档依据 |
| 第二问 | 相似追问命中语义缓存 → **大模型 0 次**，端到端 < 200ms |
| Eval | 100 条 FAQ：Token ↓ ≥ 65%，采纳率下降 ≤ 2%，P95 时延不升 |

## 三、预期价值

### 3.1 量化预估（示意：日均 2 万次知识问答任务）

| 指标 | 改造前（估） | 改造后（估） | 变化 |
|------|--------------|--------------|------|
| 单任务合计 token | ~8000 | ~2200 | ↓ 72% |
| 大模型调用占比 | ~100% | ~35% | 65% 被缓存/小模型短路 |
| 日总 token | 1.6 亿 | 0.44 亿 | 节省 1.16 亿/天 |
| 月成本（¥0.07/1K 粗算） | ~¥33.6 万 | ~¥9.2 万 | **约省 ¥24 万/月** |

> 量级示意，需用真实埋点替换；缓存命中率越高，节省越大。

### 3.2 业务与组织价值

| 维度 | 价值 |
|------|------|
| 成本 | 高频问答可规模化，不再「越用越贵」 |
| 体验 | 缓存命中秒回；检索更准，幻觉与跑题下降 |
| 工程 | 预算硬顶遏制 Agent「失控循环」 |
| 组织 | 提供可复用的「任务级成本操作系统」，可挂到客服、判责、研发助手 |

### 3.3 风险与对策

| 风险 | 对策 |
|------|------|
| 缓存答错被复用 | 仅缓存人工/高置信样本；带版本与失效策略 |
| 预算过紧答不全 | 意图分级预算；关键排障模板给足配额 |
| 分层召回漏掉关键文档 | 召回阶段宁多勿少（摘要便宜）；正文阶段再砍 |
| 小模型误判短路 | 置信阈值 + 用户「不满意再升级」按钮；eval 盯误短路率 |

## 四、答辩话术（30 秒）

> 方案 A 教系统「每次调用怎么瘦」；方案 B 教系统「整件任务怎么少调用、少检索、少回传」。我们给每个问题发一笔 Token 预算，先走缓存和小模型短路，再用分层 RAG 按预算取正文，并用工具失败分类器打断无效重试——让 Agent 在效果不降的前提下，把 Token 花在真正需要推理的那一步。
