### 版本 A：精简版（1 段，空间有限时用）

面向赛题「如何让大模型在完成相同任务时更节约 Token」，针对「完成同样任务却因上下文过长、Prompt 全量加载、路由不当产生无效 Token」的问题，提出并落地分层 Token 治理：路由先行（零 LLM 分类）→ 字段裁剪 → `_base`+场景 Prompt 按需拼装 → 输出约束与 Eval 门禁。以商旅 AI 告警降噪为样板，在「宁可误报不可误杀、每条仍需调模型」约束下，将降本主战场定为单次调用瘦身与工程链路零 LLM 化；预估单次 Token ↓ ~70%，并抽象为可复用到客服 / 判责等场景的 AI 工程能力。

### 版本 B：标准版（3–4 条 bullet，推荐）

**2026 滴滴黑客松大赛 · 赛题 04「如何让大模型更节约 Token」** | LLM / Prompt / Eval

- 针对商旅告警降噪等 LLM 规模化场景中「任务不难、调用方式低效」导致的 Token 浪费，设计 **六层治理框架**：路由 → 上下文裁剪 → 动态 Prompt → 模型分级 → 输出约束 → 结果缓存，覆盖赛题上下文压缩、Prompt 精简、分阶段路由与评估框架等方向
- 在 error-triage 实战中落地 **Router First + Dynamic Prompt Assembly**：pathname 规则零 Token 分类后只加载 `_base` + 当前 category Prompt；规划 user 字段裁剪与 reason 长度约束，避免全量 JSON / 全量规则塞入上下文
- 建立 **Eval 驱动降本纪律**：以 gold 数据集 + `/eval` 对比 before/after，门禁为 input Token 显著下降且准确率/漏报率不恶化，杜绝「靠感觉砍 Prompt」制造生产风险
- 输出可迁移叙事：同一框架可挂到需求理解、纠纷判责、知识问答；并补充任务级 Token 预算编排（语义缓存 / 分层 RAG / Agent 工具失败分类）作为高频多轮场景的扩展方案

### 版本 C：突出 AI 工程 / 成本优化版（AI Infra · Agent 向岗位）

**2026 滴滴黑客松大赛 · LLM Token 成本治理** | 路由编排 · Prompt 模块化 · Eval-as-Gate

- 核心命题：**不是让模型少干活，而是少干无效活**；在告警场景禁止用「少调模型」降本（漏报约束），因此系统化做单次瘦身 + 零 LLM 旁路（路由 / drift-check / 增量 discover）
- 诊断六类浪费（上下文过长、Prompt 冗余、检索不准、模型误路由、输出失控、失败重试），按 P0/P1 排出改造清单，并设计任务级 **Token 预算编排器**（缓存短路 → 小模型 → 大模型级联）服务多轮 Agent
- 工程闭环：Token 埋点归因到 domain/category/prompt 版本；`/judge` + `/eval` 做回归；灰度与回滚策略与业务原则绑定
- 竞赛叙事：从「Prompt 技巧」升级为可度量、可验证、可跨团队复用的 **AI 工程能力**，回应赛题「通用、可迁移」要求

## 二、一句话 / 电梯演讲（30 秒）

> 大模型落地后成本往往不是任务太难，而是上下文和 Prompt 塞太多、简单判断也上大模型。我在 **2026 滴滴黑客松大赛赛题 04** 里做的是分层 Token 治理：先用规则路由决定调不调、调哪套 Prompt，再裁剪上下文、按需拼 Prompt，并用 Eval 卡死「省 Token 但不能漏报」。样板是商旅告警降噪，框架本身可以迁到问答和 Agent。
