# 页面性能分析 Skill-面试卡片

## 1. 请介绍一下你做的页面性能分析 Skill，解决什么问题？

## 答案

**定位**：面向前端业务页的源码级函数执行耗时分析助手——读页面及相关代码，按加载 / 交互 / 监听三阶段拆函数、估耗时、找瓶颈，输出可排期的 P0/P1/P2 优化建议。

**痛点**：
- 「感觉慢」但缺少函数级抓手
- 排查靠个人经验，结论难复用
- 只有 FCP/LCP 数字，对不上具体代码
- 串行请求、Watch 连锁等常见病反复出现

**目标输出**：页面概述 → 耗时三梯队 → 瓶颈分析 → 分级建议 → Web Vitals 对照。

**核心原则**：业务上下文优先；估算 + 真测双轨；建议必须可落地。

---

## 2. 它和 Lighthouse / Performance 面板有什么区别？为什么还要做 Skill？

## 答案

| 维度 | Lighthouse / Perf 面板 | 本 Skill |
|------|------------------------|----------|
| 数据来源 | 真实运行测量 | 源码静态分析 + 类型估算 |
| 输出 | 指标与资源级建议 | 函数级耗时排序 + 代码侧改法 |
| 使用门槛 | 要起环境、要会看面板 | 对话一句即可开跑 |
| 复用 | 偏个人操作 | 规程固化进 Agent Skill |

**互补关系**：Skill 负责快速收敛「改哪几个函数」；真测负责验证「改完有没有变快」。

**为什么做**：把性能复盘从个人经验产品化为团队可触发流程，尤其适合商旅多页面、多人协作场景。

## 3. 一次分析的完整流程是怎样的？

## 答案

| 步骤 | 行为 |
|------|------|
| 0 上报（可选） | `report-skill.sh` 记调用统计 |
| 1 识别 | 确认页面路径、技术栈、业务场景 |
| 2 读码 | 主文件 + mixin/hooks + store + API |
| 3 分阶段 | 加载 / 交互 / 监听函数建模 |
| 4 估耗时 | 套网络 / 数据处理 / 渲染估算表 |
| 5 找瓶颈 | 串行瀑布、连锁触发、防抖节流、重复请求 |
| 6 出建议 | P0 / P1 / P2 + 预期收益 |
| 7 写报告 | 固定五段结构 |

**入口**：自然语言（「分析酒店列表页…」）或 `analyze.sh` 先出骨架再深度补全。

## 4. 「三阶段模型」具体分析什么？为什么这样拆？

## 答案

**加载阶段**：生命周期、初始化请求、组件初始化、路由守卫 —— 对应「进页慢」。  
**交互阶段**：点击/滚动/输入、表单、导航、弹窗 —— 对应「点了卡」。  
**监听阶段**：Watch / Computed / Store 订阅 —— 对应「改一点数据整页抖」。

**为什么拆**：用户体感的「慢」不是同一种病；拆开才能对症给 P0，而不是一锅优化建议。

---

## 5. 耗时是怎么估出来的？准吗？

## 答案

**方法**：按操作类型套经验区间，再结合依赖关系合成函数耗时。

| 类型 | 区间示例 |
|------|----------|
| 简单 / 复杂 / 大数据请求 | 100–300 / 300–600 / 500–2000ms |
| 简单赋值 / 数组遍历 / 复杂计算 | 1–10 / 10–50 / 50–500ms |
| 状态更新 / 列表渲染 / 整页渲染 | 5–20 / 20–100 / 50–500ms |

**合成规则**：串行相加；可并行取最长路径。

**精度边界**：宣称约 80% 可信度，本质是优先级工具；P0 改动后必须用 DevTools / 真机校准。面试要主动说「估算不是 Profiler」。

---

## 6. 函数耗时三梯队怎么划分？怎么用？

## 答案

| 梯队 | 阈值 | 用法 |
|------|------|------|
| 🔴 第一梯队 | >500ms | 优先优化对象，通常进 P0 候选 |
| 🟡 第二梯队 | 200–500ms | 中期优化 |
| 🟢 第三梯队 | <200ms | 通常可接受，先放过 |

**用法**：先按梯队排序讲故事，再落到具体瓶颈类型（例如第一梯队里两个串行接口 → 并行化）。

---

## 7. 你会识别哪些典型性能瓶颈？各怎么治？

## 答案

| 瓶颈 | 表现 | 常见治法 |
|------|------|----------|
| 串行请求瀑布 | 无依赖却 `await` 串行 | `Promise.all` / 分批并行 |
| 频繁触发 | Watch/scroll 过密 | 合并更新、节流 |
| 防抖节流不当 | debounce 过长拖体感 | 调参；滚动用 throttle、输入用 debounce |
| 重复请求 | 同参多次打接口 | 去重、缓存、共享 in-flight Promise |

报告里要写清「关键路径」和「耗时分解」，避免只甩结论。

---

## 8. P0 / P1 / P2 怎么定？举个例子

## 答案

| 级别 | 定义 | 例子 |
|------|------|------|
| P0 | 体验关键且易落地 | 初始化请求并行、砍无效重试 |
| P1 | 收益明显，有成本 | Watch 批量更新、数据预加载 |
| P2 | 架构级 | 虚拟列表、组件懒加载、缓存体系 |

**原则**：先吃低成本高收益；不要一上来就上大重构。面试可补：P0 应能在 1–2 天内验证指标变化。

---

## 9. `analyze.sh` 做什么？为什么不让脚本直接给出最终结论？

## 答案

**脚本实际能力**：校验文件、猜技术栈、统计行数/函数数/API 文件数，生成带占位的 Markdown 骨架。

**不做**：AST 分析、真实计时、自动写 P0 方案。

**分层理由**：自动化擅长「起盘与模板」；深度结论依赖读懂业务上下文与跨文件依赖，交给 Agent 更合适。避免脚本假装成成熟 Profiler。

---

## 10. 多技术栈（MPX / Vue / React / 小程序）如何适配同一套模型？

## 答案

**同一套三阶段骨架**，映射不同钩子名：

| 栈 | 加载 | 交互 | 监听 |
|----|------|------|------|
| Vue/MPX | created/mounted | methods 事件 | watch/computed |
| React | mount effect | handlers | state/effect 依赖 |
| 小程序 | onLoad/onShow | 事件回调 | setData 触发链 |

小程序额外盯 **setData 粒度与频率**；React 额外盯 **重渲染边界（memo/依赖数组）**。

## 11. 报告结构为什么固定成五段？

## 答案

1. **概述** —— 对齐上下文（页、栈、场景）  
2. **耗时排序** —— 先给优先级感知  
3. **瓶颈分析** —— 解释因果（为什么慢）  
4. **优化建议** —— 可排期动作  
5. **指标对照** —— 连接到 FCP/LCP/TTI 目标  

固定结构方便周报、评审、面试口述复用，也方便团队横向对比多个页面。

---

## 12. Web Vitals 在这套 Skill 里起什么作用？

## 答案

Skill 主体产出是 **函数级代码建议**；Web Vitals（FCP/LCP/TTI/FID/CLS）用来：

1. 设优化目标（例如 LCP < 2.5s）  
2. 把代码改动翻译成「用户可感知指标」语言  
3. 提醒：当前值若未经真测应标「待测量/估算」

**一句话**：指标是验收尺子，函数清单是施工图纸。

---

## 13. 如果面试官问：只有静态分析会不会误判？

## 答案

**会，所以有边界与缓解：**

- 报告标明估算  
- 规程要求读全 mixin/store，降低漏依赖  
- 考虑多入口 / 返回 / 参数变化  
- P0 落地后强制真测  
- 不把脚本骨架当终稿  

**加分表述**：静态分析擅长「缩小嫌疑集合」；真测擅长「定罪与验收」。两者闭环才完整。

## 14. 这个项目里你个人贡献可以怎么讲？

## 答案

按实际参与度选用：

1. **问题定义**：把「页面慢」抽象为可复用的三阶段复盘流程  
2. **规程设计**：耗时表、瓶颈清单、报告契约、P0/P1/P2  
3. **工程化**：`skill.json` 触发词 / capabilities、QUICKSTART、场景示例  
4. **脚手架**：`analyze.sh` 骨架生成，明确与 Agent 深度分析的分工  
5. **落地验证**：酒店首页等业务页案例跑通  

**避免**：把「估算报告」说成「线上 APM 已全量采集并自动优化」。

## 15. 举一个端到端例子（面试口述用）

## 答案

**输入**：「分析酒店列表页，重点关注搜索和筛选」。

**过程**：
1. 定位 `list.mpx` + 请求/筛选/滚动 mixin + store  
2. 加载阶段标出 `loadListData`、`fetchFilterItems`  
3. 交互阶段标出 `search`、`filterChange`、`loadMore`  
4. 发现筛选参数 watch 触发连锁请求；初始化两接口串行  
5. 估时后两者落入第一梯队  

**输出（示例结论）**：
- P0：初始化请求并行；筛选触发合并/防抖调参  
- P1：列表预加载与请求去重  
- P2：长列表虚拟滚动  

**收尾**：说明需用真机滚动与 Network 面板验证。

## 18. 和纯规则性能 Lint（如禁同步 XHR）比，tradeoff 是什么？

## 答案

**Skill 优势**：
- 能结合业务页面上下文讲「关键路径」
- 输出函数级故事与排期建议，而不只是规则命中
- 适合复杂业务页（mixin / 多入口）

**代价**：
- 依赖模型读码质量，结果非确定性
- 耗时为估算，需真测
- 不如 Lint 可做硬门禁

**现阶段选择**：用 Skill 做深度复盘与知识沉淀；规则 Lint 可并行做底线防护；**PerfMonitor** 负责线上验收。三者不互斥。

## 20. 首页做过哪些性能相关改动？为什么要剥离 privacyPopList？

## 答案

**改动**：
1. 自建 LCP/FCP 自监控（环境 class 兼容 H5/星河）  
2. 接入 `getHomeData` 关键接口耗时  
3. 定位并剥离拖长 LCP 的接口（如 `privacyPopList` 的耗时累积）

**为什么剥离**：LCP 应对用户感知的最大内容；隐私弹窗类接口若串进首屏关键路径，会污染 LCP 口径，让优化方向跑偏。剥离后指标更贴近真实首屏体验，也便于单独治理非关键请求。

---

## 21. 列表页指标为什么要覆盖「接口返回」和「缓存命中直渲」两条路径？

## 答案

列表进页常见两条关键路径：

1. **等接口返回再渲** —— 冷启动 / 无缓存  
2. **缓存命中直渲** —— 有本地数据先出屏  

只打一条会产生：
- 优化了缓存路径却在「只看接口路径」的看板上看不出  
- 或平均被某一路径拉偏  

同时修正 **切日期重渲** 的统计口径，避免场景切换造成误报/漏报。  
**结果**：首屏 LCP **1400ms → 1160ms（↓17%）**。

## 22. 稳定性与卡顿方面做了什么？有什么量化结果？

## 答案

| 项 | 动作 | 结果 |
|----|------|------|
| flight-detail-refactor | 修复 `reportRender` 报错；补充最长进入耗时埋点 | 稳定性 + 可观测 |
| 星河底部菜单切换 | 排查并优化排序逻辑 | 卡顿改善约 **27%** |

口述要点：卡顿不一定是网络，**主线程排序/计算**也会拖交互；要靠埋点 + 场景复现定位。

## 23. Skill 和 PerfMonitor 如何一起讲成闭环？

## 答案

```
Skill 静态分析（估瓶颈、出 P0）
    → 改业务代码（剥离非关键接口 / 修口径 / 优化排序）
    → PerfMonitor + Omega 验数字（LCP↓、卡顿↓）
    → 再迭代
```

| 角色 | 擅长 |
|------|------|
| Skill | 函数级嫌疑集合、可排期建议、知识复用 |
| PerfMonitor | 线上/真机口径、跨页链路、优化验收 |

**一句话**：Skill 负责缩小嫌疑，PerfMonitor 负责定罪与验收。
