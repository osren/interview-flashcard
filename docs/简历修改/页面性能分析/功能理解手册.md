# 第一部分：大白话全链路科普

---

## 1. 先备一张「词小抄」

| 词 | 大白话 |
|---|---|
| **页面性能** | 用户觉得「打开慢 / 点了没反应 / 滑动卡」 |
| **函数耗时** | 某个函数从开始干到干完花了多久 |
| **首屏** | 用户进来后第一眼看到有用内容的那段时间 |
| **FCP / LCP / TTI** | 行业常用性能指标：第一次画、最大内容、可交互 |
| **串行请求** | 接口 A 完了才打 B，像单车道排队 |
| **并行请求** | 互不依赖的接口一起打，像多车道 |
| **瀑布流（请求）** | 时间轴上请求一根接一根排下来的样子 |
| **Watch / 监听** | 「数据一变就自动跑一段逻辑」 |
| **Computed** | 根据已有数据算出来的派生值 |
| **防抖 debounce** | 停手一阵子才执行（适合搜索输入） |
| **节流 throttle** | 每隔固定时间最多执行一次（适合滚动） |
| **setData** | 小程序里把数据推到视图的动作，太频繁会卡 |
| **P0 / P1 / P2** | 优化优先级：立刻做 / 中期做 / 长期架构做 |
| **Skill** | Claude Code 里可复用的标准作业流程 |
| **静态分析** | 不跑页面，只靠读代码推性能问题 |
| **真测** | Chrome DevTools / 真机上真正测时间 |
| **PerfMonitor** | 业务仓里的性能打点工具（`perf-monitor.js`） |
| **Omega** | 埋点上报通道，PerfMonitor 的数据往这儿送 |
| **星河** | 滴滴小程序运行环境（和 H5 双端都要能出指标） |
| **缓存命中直渲** | 有本地缓存时先直接渲染，不等接口 |
| **跨页链路** | 从 A 页点到 B 页整段花了多久（如 home→list） |

---

## 2. 一句话定位

> 这不是线上监控系统，是 **代码体检助手**：你告诉它「哪个页面慢」，它去读页面及相关源码，按「加载 / 交互 / 监听」拆函数，估出谁最耗时，指出串行请求、Watch 连锁这类常见病，并给出能排期的优化建议。

把它想成医院分诊：

```
用户喊「肚子疼」（页面慢）
    → 分诊问诊（确认页面、场景、技术栈）
    → 化验估算（按请求类型 / 渲染复杂度估耗时）
    → 出检查单（报告 + P0/P1/P2）
    → 真正动手术前还要再拍片（DevTools 真测）
```

---

## 3. 一次完整分析怎么走（最重要）

以「酒店列表页搜索和筛选慢」为例。

### 3.1 第 1 步：搞清楚看哪一页

- 用户说「列表页」→ Agent 用 `find` 找到 `src/pages/search/list.mpx` 之类
- 确认是 MPX / Vue / React，以及业务场景（搜酒店、筛筛选）

### 3.2 第 2 步：把相关代码凑齐

不止读主文件，还会读：

- mixin（列表请求、筛选、滚动）
- store / action
- API 封装

否则你会漏掉「真正耗时藏在 mixin 里」的情况。

### 3.3 第 3 步：按三阶段列函数

| 阶段 | 在问什么 | 例子 |
|---|---|---|
| 加载 | 进页时干了啥 | `loadListData`、`fetchFilterItems` |
| 交互 | 用户点了 / 滑了干啥 | `search`、`filterChange`、`loadMore` |
| 监听 | 数据变了自动干啥 | `filterParams` 的 watch |

### 3.4 第 4 步：套「经验耗时表」估算

例如：

- 复杂查询接口 → 估 300–600ms
- 列表渲染 → 估 20–100ms
- 多个串行 await → **总时间相加**（这就是瀑布变长的原因）

注意：这是 **估算**，不是 Profiler 读数。

### 3.5 第 5 步：找「常见病」

1. 无依赖却串行请求  
2. Watch 连锁触发  
3. 防抖太长导致「输入完半天没反应」  
4. 同参数重复打接口  

### 3.6 第 6 步：开药方（分级）

- **P0**：并行化初始化请求（改动小、收益大）  
- **P1**：合并 Watch、预加载  
- **P2**：虚拟列表、架构级缓存  

### 3.7 第 7 步：写报告

按固定模板输出，方便贴到评审 / 周报 / 面试口述。

# 第三部分：三阶段模型与估算表直觉

## 1. 为什么拆成三阶段？

因为「慢」不是一种病：

- **进页慢** → 多半是加载阶段请求 / 初始化  
- **点了卡** → 多半是交互处理太重或重复请求  
- **改个筛选项整页抖** → 多半是监听连锁  

拆开才能对症下药。

## 2. 估算表怎么用（直觉版）

把函数想成「点菜算账」：

1. 看它有没有网络请求 → 套网络表  
2. 看有没有重数组处理 → 套数据处理表  
3. 看会不会大列表 / 整页重渲染 → 套渲染表  
4. 若串行，把账 **加总**；可并行则取 **最长那笔**  

## 3. 梯队颜色记忆

- 🔴 **>500ms**：优先盯  
- 🟡 **200–500ms**：有空再削  
- 🟢 **<200ms**：通常先放过

# 第四部分：报告怎么读、怎么跟面试官讲

## 1. 报告五段速览

1. 概述：这是哪个页、什么栈  
2. 耗时排序：谁最可疑  
3. 瓶颈：为什么慢（串行？连锁？）  
4. 建议：P0/P1/P2  
5. 指标：和 FCP/LCP 目标差多少  

## 2. 30 秒电梯演讲

> 我沉淀了一个页面性能分析 Skill：针对业务页做源码级函数耗时复盘。按加载、交互、监听三阶段拆函数，用请求类型和渲染复杂度估算耗时，专门抓串行瀑布、Watch 连锁、防抖配置和重复请求，并输出 P0/P1/P2 可排期建议。它不替代真机 profiling，但能把「感觉慢」快速收敛成可执行的优化清单。

## 3. 诚实边界（面试加分）

主动说清楚：

1. 耗时是 **估算**，不是线上采样  
2. `analyze.sh` 只搭骨架  
3. P0 落地后要用 DevTools / 真机验证  
4. 价值在 **流程固化与可复用**，不是玄学测速

# 第五部分：PerfMonitor 真测轨（同事口径）

Skill 是「读代码体检」；业务仓还有一套 **PerfMonitor** 是「装仪表盘 + 看数字下降」。

## 1. 仪表盘装了啥

- **跨页**：home → list 全链路 `home_to_list_complete`
- **同页**：LCP / FCP（自己采，不靠单一端）
- **接口**：关键接口耗时（如首页 `getHomeData`）
- **上报**：统一走 Omega

环境判断封成 class，**H5 和星河**都能出同一套指标。

## 2. 首页怎么变快

发现有的接口（如 `privacyPopList`）会把耗时「糊」进 LCP——它不一定是用户首屏感知的关键内容。  
做法：定位并剥离这类请求，让 LCP 只反映真正的首屏关键路径，同时给 `getHomeData` 单独打点。

## 3. 列表页怎么验得准

列表进页有两条路：

1. 等接口返回再渲  
2. 缓存命中直接渲  

两条都要上报，否则数字会骗人。还修了「切日期重渲」时的统计口径。  
结果：**首屏 LCP 1400ms → 1160ms（↓17%）**。

## 4. 卡顿与稳定性

- 修 `flight-detail-refactor` 的 `reportRender` 报错，并补「最长进入耗时」埋点  
- 星河底部菜单切换卡顿：优化排序逻辑，卡顿约 **↓27%**

## 5. 两轨怎么一起讲（面试用）

> 我这边性能工作分两块：一块是 page-performance-analysis Skill，用静态分析快速给出函数级优化清单；一块是 PerfMonitor，把跨页、LCP/FCP、关键接口统一打到 Omega。Skill 负责缩小嫌疑，PerfMonitor 负责验收——比如列表 LCP 降 17%、菜单卡顿降 27%。

更细见 [PerfMonitor与体验优化.md](./PerfMonitor与体验优化.md)。
