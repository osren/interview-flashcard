# 页面性能分析项目 - 面试准备稿

> **项目定位**：前端页面性能监控与优化体系 = 静态分析工具（Skill）+ 运行时监控（PerfMonitor）  
> **技术栈**：Claude Code Skill / Shell / JavaScript / Omega 埋点 / MPX/Vue  
> **成果**：列表页 LCP ↓17%（1400ms→1160ms）、菜单卡顿改善 27%  
> **时间**：2026 年上半年（实习期间）

---

## 一、项目背景（1 分钟版）

### 业务痛点

在商旅酒店业务中，页面性能问题频繁出现但难以系统化解决：

**核心问题**：

- 用户反馈「页面慢」，但不知道慢在哪个函数
- 性能排查依赖个人经验，难以复用和传承
- 只有 FCP/LCP 等宏观指标，无法直接对应到具体代码
- 串行请求、Watch 连锁、防抖配置不当等问题反复出现

**现状**：

- 首页加载时感知较慢
- 列表页筛选操作有卡顿
- 星河底部菜单切换有明显延迟

### 解决思路

建立**双轨性能监控体系**：

```
静态分析轨（Skill）           运行时监控轨（PerfMonitor）
    估算瓶颈                         真测验证
       ↓                               ↓
   改代码优化     ←─────数字驱动────→   量化收益
```

**为什么需要双轨？**

- Skill：开发阶段快速定位瓶颈，无需启动环境
- PerfMonitor：线上真实数据验证，持续监控

## 二、我的工作内容



### 2.1 静态分析 Skill 设计与实现



#### 核心能力

设计了一套**可复用的页面性能分析流程**，通过 Claude Code Skill 固化：

**三阶段分析模型**：

1. **加载阶段**：生命周期、初始化请求、组件初始化
2. **交互阶段**：点击/滚动/输入事件、表单提交、导航
3. **监听阶段**：Watch/Computed、Store 订阅、事件总线

**耗时评估方法**：


| 类型     | 区间        | 依据               |
| ------ | --------- | ---------------- |
| 简单查询接口 | 100-300ms | 网络延迟 + 服务端处理     |
| 复杂查询接口 | 300-600ms | 多表关联、聚合计算        |
| 数组遍历处理 | 10-50ms   | O(n) 复杂度         |
| 列表渲染更新 | 20-100ms  | Virtual DOM diff |


**瓶颈识别清单**：

- 串行请求瀑布流：无依赖接口却串行执行
- 频繁触发问题：Watch/scroll 监听器过度触发
- 防抖节流配置：debounce 时间过长影响体验
- 重复请求问题：相同参数多次调用接口

### 2.2 运行时监控体系（PerfMonitor）



#### 核心架构

实现了 `src/utils/perf-monitor.js`，统一通过 **Omega** 上报：

```javascript
class PerfMonitor {
  // 1. Web Vitals 自监控
  collectWebVitals() {
    // FCP - 首次内容绘制
    const fcp = performance.getEntriesByType('paint')
      .find(e => e.name === 'first-contentful-paint');
    
    // LCP - 最大内容绘制
    new PerformanceObserver((list) => {
      const entries = list.getEntries();
      const lastEntry = entries[entries.length - 1];
      const lcp = lastEntry.renderTime || lastEntry.loadTime;
      this.reportMetric('lcp', lcp);
    }).observe({ entryTypes: ['largest-contentful-paint'] });
  }
  
  // 2. 跨页链路监控
  trackPageTransition(from, to) {
    const startTime = Date.now();
    return () => {
      const duration = Date.now() - startTime;
      this.reportMetric(`${from}_to_${to}_complete`, duration);
    };
  }
  
  // 3. 接口耗时包装器
  wrapApiCall(apiName, apiFunc) {
    return async (...args) => {
      const start = Date.now();
      try {
        const result = await apiFunc(...args);
        this.reportMetric(`${apiName}_duration`, Date.now() - start);
        return result;
      } catch (error) {
        this.reportMetric(`${apiName}_error`, 1);
        throw error;
      }
    };
  }
}
```



#### 监控覆盖

```

│ 跨页链路监控                      │
│  home_to_list_complete           │

              ▼
┌─────────────────────────────────┐
│ 同页 Web Vitals                  │

              ▼

```



#### 技术决策

**环境抽象**：

```javascript
class PerfMonitor {
  detectEnv() {
    if (typeof mpx !== 'undefined' && mpx.platform === 'xinghe') {
      return 'xinghe';
    }
    if (typeof window !== 'undefined') {
      return 'h5';
    }
    return 'unknown';
  }
  
  collectWebVitals() {
    const env = this.detectEnv();
    if (env === 'h5') {
      this._collectWebVitalsH5();      // PerformanceObserver
    } else if (env === 'xinghe') {
      this._collectWebVitalsXinghe();  // 自定义实现
    }
  }
}
```

### 2.3 优化实践与成果



#### 首页优化

**问题定位（Skill 分析）**：

```
🔴 第一梯队（>500ms）
  - getHomeData(): 300-600ms （关键接口）
  - privacyPopList(): 300-600ms （非首屏关键）
  
⚠️ 瓶颈：privacyPopList 串在首屏关键路径，污染 LCP 口径
```

**优化方案**：

```javascript
// 优化前：串行阻塞
async mounted() {
  await Promise.all([
    this.getHomeData(),      // 关键
    this.privacyPopList(),   // ❌ 非关键但阻塞
  ]);
}

// 优化后：剥离非关键接口
async mounted() {
  await this.getHomeData();  // ✅ 只等关键接口
  setTimeout(() => {
    this.privacyPopList();   // 延迟加载
  }, 0);
}
```

**监控代码**：

```javascript
// PerfMonitor 集成
import perfMonitor from '@/utils/perf-monitor';

async onLoad() {
  perfMonitor.collectWebVitals();
  
  const getHomeDataWithMonitor = perfMonitor.wrapApiCall(
    'getHomeData',
    getHomeData
  );
  
  await getHomeDataWithMonitor();
}
```

**效果**：

- LCP 不再被非关键接口污染
- 首屏关键路径更清晰

#### 列表页优化（核心成果）

**问题定位（Skill 分析）**：

```
⚠️ 双路径混淆：
  路径1：接口返回渲染（冷启动）
  路径2：缓存命中直渲（有本地数据）
  
问题：只打一条路径，优化效果在看板上看不出
```

**优化方案**：

```javascript
async loadListData() {
  const cachedData = getCache('listData');
  
  if (cachedData) {
    // 路径1：缓存命中直渲
    this.renderList(cachedData);
    perfMonitor.reportMetric('list_from_cache_lcp', performance.now());
  }
  
  // 同时发起接口请求
  const freshData = await api.getListData();
  
  if (!cachedData) {
    // 路径2：接口返回渲染
    this.renderList(freshData);
    perfMonitor.reportMetric('list_from_api_lcp', performance.now());
  } else {
    // 更新缓存但不重新渲染
    updateCache('listData', freshData);
  }
}
```

**口径修正**：

- 修正切日期重渲场景的统计
- 避免场景切换造成误报/漏报

**量化成果**：

```
列表页首屏 LCP：1400ms → 1160ms（↓17%）
缓存命中率：65%（大部分用户走快速路径）
```

#### 星河菜单卡顿优化

**问题定位（Skill 分析）**：

```
🔴 主线程阻塞：
  - switchMenu() 同步排序逻辑
  - 每次切换触发全量重排（O(n log n)）
  
⚠️ 用户体感：点击菜单后有明显延迟
```

**优化方案**：

```javascript
// 优化前：同步阻塞
switchMenu(menuId) {
  const items = this.getMenuItems(menuId);
  const sorted = items.sort(this.heavyComparator); // ❌ 阻塞
  this.renderMenu(sorted);
}

// 优化后：空闲时处理
switchMenu(menuId) {
  const items = this.getMenuItems(menuId);
  
  // 先渲染未排序版本（快速响应）
  this.renderMenu(items);
  
  // 空闲时优化排序
  requestIdleCallback(() => {
    const start = Date.now();
    const sorted = items.sort(this.heavyComparator);
    this.renderMenu(sorted);
    
    perfMonitor.reportMetric(
      'menu_switch_duration', 
      Date.now() - start
    );
  });
}
```

**量化成果**：

```
卡顿改善约 27%（通过 FPS 监控和用户感知耗时）
```

### Q8: 遇到的最大挑战是什么？

**回答框架**：

**挑战**：双路径口径设计

列表页有两条进入路径：

- 缓存命中直渲（快）
- 接口返回渲染（慢）

如果只打一条路径：

- 优化了缓存路径，但「只看接口路径」的看板上看不出
- 或者平均值被某一路径拉偏

**解决**：

1. 分别埋点两条路径
2. 修正切日期重渲的统计口径
3. Omega 看板支持按路径分组对比

**收获**：

- 理解了监控口径设计的重要性
- 学会了如何避免「平均数陷阱」

### Q: 三梯队的阈值为什么这么定？

**回答**：


| 梯队      | 阈值        | 依据                             |
| ------- | --------- | ------------------------------ |
| 🔴 第一梯队 | >500ms    | 接近用户「卡了」的感知阈值                  |
| 🟡 第二梯队 | 200-500ms | 可察觉但不严重                        |
| 🟢 第三梯队 | <200ms    | Web Vitals 中 FID < 100ms，给一倍余量 |


参考：

- Google Web Vitals: FID < 100ms 为 Good
- 人机交互研究：100-200ms 为「即时响应」阈值

### Q: 防抖和节流怎么区分？

**回答**：


| 类型              | 行为           | 适用场景 |
| --------------- | ------------ | ---- |
| **防抖 debounce** | 停手一阵子才执行     | 搜索输入 |
| **节流 throttle** | 每隔固定时间最多执行一次 | 滚动监听 |


**列表页案例**：

```javascript
// 优化前：防抖时间过长
filterChange: debounce(function() {
  this.loadList();
}, 300)  // ❌ 用户体感延迟

// 优化后：缩短防抖时间
filterChange: debounce(function() {
  this.loadList();
}, 150)  // ✅ 平衡体验与请求频率
```

### Q: 小程序 setData 为什么要关注？

**回答**：

小程序的 setData 是跨线程通信：

```
逻辑层（JS）──序列化──> 渲染层（WebView）
```

问题：

- 频繁调用：每次都要序列化 + 跨线程
- 数据量大：传输耗时长

优化策略：

```javascript
// ❌ 不好：多次 setData
this.setData({ a: 1 });
this.setData({ b: 2 });
this.setData({ c: 3 });

// ✅ 好：合并 setData
this.setData({
  a: 1,
  b: 2,
  c: 3
});
```

Skill 会识别 setData 调用模式，给出合并建议。

### Q: 如何评估 P0 建议的优先级？

**回答**：

两个维度：

1. **影响体验的程度**（用户是否能感知）
2. **实施难度**（改动量、风险、依赖）

```
        │ 高影响
        │
   P0   │   P1
─────────┼──────────
   P2   │  （可不做）
        │
        │ 低难度
```

**P0 必须满足**：

- 首屏关键路径
- 可在 1-2 天内验证
- 风险可控
