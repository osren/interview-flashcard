# 页面性能分析 Skill（page-performance-analysis）功能全面说明

> Skill 名：`page-performance-analysis`  
> 定位：面向前端业务页的 **源码级函数执行耗时分析助手** —— 读页面 / mixin / store，估算加载·交互·监听三阶段耗时，识别瓶颈并输出可落地的 P0/P1/P2 优化建议。  
> 文档版本：基于 skill 包 `v1.0.0`（2026-06-09）整理；案例背景为商旅酒店（`fe-eshotel`）等 MPX/Vue 业务页。  
> **双轨补充**：业务仓另有运行时 **PerfMonitor**（`src/utils/perf-monitor.js` + Omega）做真测与体验优化，详见 [PerfMonitor与体验优化.md](./PerfMonitor与体验优化.md)。

---

## 0. 性能工程双轨总览

「性能监控与体验优化」在工程上拆成两条互补轨道，勿混为一谈：

| 轨道 | 载体 | 做什么 | 典型产出 |
|---|---|---|---|
| **静态分析轨** | `page-performance-analysis` Skill | 读源码估耗时、找瓶颈、出 P0/P1/P2 | Markdown 分析报告 |
| **运行时真测轨** | PerfMonitor + Omega | 跨页/同页/接口打点，指导改代码并验数字 | LCP↓17%、卡顿↓27% 等 |

```
Skill 估瓶颈 ──▶ 改业务代码 ──▶ PerfMonitor/Omega 验数字 ──▶ 再迭代
```

本文主体仍描述 **Skill 轨**；运行时能力以第 0 节与独立文档为准。原先「运行时插桩待演进」指 **Skill 包内不内嵌 APM**，不否定业务仓已落地的 PerfMonitor。

## 1. 功能需求背景

### 1.1 痛点

商旅 / 酒店等业务页常见「感觉慢」，但排查成本高：

| 痛点 | 典型表现 | 影响 |
|---|---|---|
| 不知慢在哪 | 首屏慢、列表卡、筛选卡，缺少函数级拆解 | 优化无抓手 |
| 请求串行瀑布 | 多个初始化接口互相 `await` | 首屏被拉长 |
| Watch / setData 连锁 | 一处改状态触发多处监听与重渲染 | 交互抖动 |
| 经验靠人 | 依赖个别同学「看过这个页」 | 难复用、难交接 |
| 指标与代码脱节 | 只有 FCP/LCP 数字，对不上具体函数 | 改不动关键路径 |

结果是：**性能问题发现靠体感，定位靠人肉翻代码，优化建议难结构化沉淀**。

### 1.2 目标

用 Claude Code Skill 把「读代码 → 估耗时 → 找瓶颈 → 出方案」固化成标准作业：

1. **定位目标页**（路径 / 技术栈 / 业务场景）
2. **按三阶段拆函数**（加载 / 交互 / 监听）
3. **估算耗时并排序**（高 / 中 / 低三梯队）
4. **识别典型瓶颈**（串行瀑布、连锁触发、防抖节流、重复请求）
5. **输出分级优化建议**（P0 / P1 / P2）+ Web Vitals 对照目标

核心原则：

- **业务上下文优先**：先理解页面干什么，再谈优化
- **估算 + 真测双轨**：Skill 给出可行动的估算报告，最终以 DevTools / 真机验证为准
- **建议可落地**：每条建议对应改什么、预期收益，避免空泛「再优化一下」

### 1.3 非目标（当前阶段）

- **不是** 运行时 APM / 线上采样系统（不接 RUM、不插桩生产流量）
- **不是** 自动改代码并出 PR（默认停在分析报告）
- **不是** 精确到毫秒的 Profiler（耗时来自类型估算表 + 代码依赖关系，宣称约 80% 可信度）
- **不替代** Lighthouse / Performance 面板的真实测量

## 2. 功能概述

系统本质是 **Agent Skill + 可选脚手架脚本**：

| 部分 | 路径 | 职责 |
|---|---|---|
| **Skill 规程** | `SKILL.md` / `skill.json` | 触发词、分析流程、耗时表、报告结构、注意事项 |
| **脚手架脚本** | `scripts/analyze.sh` | 检测技术栈、统计行数/函数数，生成「待深度分析」报告骨架 |
| **使用文档** | `README` / `QUICKSTART` / `examples/` | 对话模板与场景示例 |

### 2.1 对外能力一览

| 能力 | 形态 | 说明 |
|---|---|---|
| **对话式单页分析** | 自然语言触发 | 「分析酒店首页函数执行耗时」 |
| **关注点分析** | 自然语言 + 焦点 | 「重点关注搜索 / 图片 / 滚动加载」 |
| **批量分析** | 多页汇总 | 主要页面评分表 + 共性问题 |
| **场景 / 对比** | 特定路径 | 滚动加载、H5 vs 小程序、优化前后 |
| **报告脚手架** | `analyze.sh <page>` | 生成 Markdown 骨架，再由 Claude 填满 |

```
    ▼

    ▼

    │
    ▼
输出报告 ──▶ 概述 → 耗时排序 → 瓶颈 → P0/P1/P2 → 指标对照
```

## 3. 架构与设计

### 3.1 目录结构

```
page-performance-analysis/
├── SKILL.md                 # Skill 核心规程（流程 / 估算 / 报告）
├── skill.json               # 元数据、触发词、capabilities
├── README.md                # 完整功能说明（面向使用者）
├── QUICKSTART.md            # 快速上手
├── INDEX.md                 # 包内文档索引
├── examples/
│   └── usage-examples.md    # 5 类场景示例
└── scripts/
    └── analyze.sh           # 脚手架：统计 + 报告骨架
```

### 3.2 分层理解（对照「引擎 + 配置」）

本 Skill **没有常驻服务**，可类比为：

```
┌────────────────────────────────────────────┐
│ 入口层：对话触发 /analyze.sh                 │
│   唯一职责：确定目标页 + 拉齐上下文            │
└─────────────────────┬──────────────────────┘
                      ▼
┌────────────────────────────────────────────┐
│ 分析核（Agent 执行 SKILL 规程）               │
│   读码 → 建模函数依赖 → 套用耗时表 → 找瓶颈   │
└─────────────────────┬──────────────────────┘
          ┌───────────┼───────────┐
          ▼           ▼           ▼
     加载阶段      交互阶段      监听阶段
   lifecycle     handlers     watch/computed
   init API      form/nav     store 订阅
          │           │           │
          └───────────┴───────────┘
                      ▼
              Markdown 性能报告
```

**设计要点：**

1. **入口轻**：用户一句话或脚本一行即可开跑。
2. **规程固化**：维度、估算表、瓶颈类型、报告结构写死在 Skill 里，减少每次发挥。
3. **脚本只做骨架**：`analyze.sh` 不假装测出真实耗时，深度结论留给读源码的 Agent。
4. **技术栈可适配**：同一套三阶段模型，映射到 Vue/React/小程序不同钩子名。

### 3.3 分析流程（Skill 规程）

| 步骤 | 行为 |
|---|---|
| 0 上报 | 可选调用 `report-skill.sh page-performance-analysis <工具名>` |
| 1 识别 | 确认页面路径、技术栈、业务场景、入口差异 |
| 2 读码 | 主文件 + mixin / hooks + store + API 封装 |
| 3 分阶段建模 | 加载 / 交互 / 监听函数清单与依赖边 |
| 4 估耗时 | 套用网络 / 数据处理 / 渲染估算表 |
| 5 找瓶颈 | 串行瀑布、频繁触发、防抖节流、重复请求 |
| 6 出建议 | P0 / P1 / P2 + 预期收益 |
| 7 写报告 | 固定五段结构输出 |

### 3.4 三阶段分析维度

#### 加载阶段

- `created` / `mounted` / `onLoad` / `useEffect([])` 等生命周期
- 初始化数据请求、组件初始化、路由守卫

#### 交互阶段

- 点击 / 滚动 / 输入事件处理
- 表单提交、导航跳转、弹窗开关

#### 监听阶段

- Watch / Computed / Store 订阅 / 事件总线
- 评估触发频率与连锁更新成本

### 3.5 耗时评估方法（估算契约）

**网络请求**

| 类型 | 耗时范围 |
|---|---|
| 简单查询 | 100–300ms |
| 复杂查询 | 300–600ms |
| 聚合 / 大数据 | 500–2000ms |

**数据处理**

| 类型 | 耗时范围 |
|---|---|
| 简单赋值 | 1–10ms |
| 数组遍历 | 10–50ms |
| 复杂计算 / 递归 | 50–500ms |

**渲染更新**

| 类型 | 耗时范围 |
|---|---|
| 简单状态更新 | 5–20ms |
| 列表渲染 | 20–100ms |
| 复杂组件 / 整页 | 50–500ms |

**函数梯队（报告用）**

| 梯队 | 阈值 | 含义 |
|---|---|---|
| 🔴 第一梯队 | >500ms | 优先优化对象 |
| 🟡 第二梯队 | 200–500ms | 中期优化 |
| 🟢 第三梯队 | <200ms | 通常可接受 |

### 3.6 瓶颈识别清单

| 类型 | 关注点 | 典型建议 |
|---|---|---|
| 串行请求瀑布 | 无依赖却 `await` 串行 | `Promise.all` / 分批并行 |
| 频繁触发 | Watch / scroll 过密 | 合并更新、节流 |
| 防抖节流配置 | debounce 过长拖慢体感 | 调参 + 区分节流/防抖 |
| 重复请求 | 同参多次打接口 | 去重 / 缓存 / 共享 Promise |

### 3.7 优化建议分级

| 级别 | 定义 | 例子 |
|---|---|---|
| **P0** | 体验关键且易落地 | 初始化请求并行、砍无效重试 |
| **P1** | 收益明显，有开发成本 | Watch 批量更新、预加载 |
| **P2** | 架构级 | 虚拟列表、组件懒加载、缓存体系 |

### 3.8 Web Vitals 对照基准

| 指标 | 良好 | 需优化 | 差 |
|---|---|---|---|
| FCP | <1.8s | 1.8–3.0s | >3.0s |
| LCP | <2.5s | 2.5–4.0s | >4.0s |
| TTI | <3.8s | 3.8–7.3s | >7.3s |
| FID | <100ms | 100–300ms | >300ms |
| CLS | <0.1 | 0.1–0.25 | >0.25 |

报告中「当前值」若未经真测，应标为估算或待测量，避免伪精确。

### 3.9 `analyze.sh` 行为边界

脚本实际做的事：

1. 校验页面文件存在
2. 按扩展名 / 关键字猜技术栈（mpx/vue/tsx/jsx/js）
3. 统计行数、粗算函数数、目录内 API 相关文件数
4. 写出带「待 Claude 深度分析」占位的 Markdown 骨架

**不做**：解析 AST、测量真实耗时、自动给 P0 建议。深度内容必须由 Agent 按 `SKILL.md` 补全。

### 3.10 关键设计决策

| 决策 | 理由 |
|---|---|
| 以源码静态分析为主 | 无运行环境也能在 CI/本地对话中复盘任意页 |
| 耗时用类型表估算 | 快速出优先级；再引导真测校准 |
| 三阶段固定模型 | 跨 Vue/React/小程序可映射，报告结构统一 |
| 建议强制 P0/P1/P2 | 让优化可排期，而不是一锅建议 |
| 脚本只产骨架 | 避免脚本伪造成熟 Profiler，诚实分层 |

## 5. 输出报告契约

固定五段：

1. **页面概述** — 名称/路径/技术栈/业务场景/代码统计  
2. **函数执行耗时排序** — 三梯队列表  
3. **性能瓶颈分析** — 关键路径、瀑布关系、耗时分解  
4. **优化建议** — P0/P1/P2 + 实施方案 + 预期收益  
5. **性能指标对比** — 当前（估/测）vs 目标

可选扩展：批量汇总表、H5 vs 小程序对比、优化前后 diff。

## 7. 后续演进与风险

### 7.0 已补齐的真测轨（业务仓，非 Skill 内）

详见 [PerfMonitor与体验优化.md](./PerfMonitor与体验优化.md)：

- 跨页 `home_to_list_complete`、同页 LCP/FCP、关键接口耗时 → Omega
- 首页：H5/星河双端自监控；`getHomeData`；剥离 `privacyPopList` 等拖长 LCP 的路径
- 列表：接口返回 + 缓存命中双路径；切日期重渲口径修正；LCP 1400→1160ms（↓17%）
- 稳定性：`reportRender` 修复 + 最长进入耗时；星河底部菜单排序卡顿改善约 27%

演进方向转为：**让 Skill 报告字段与 PerfMonitor/Omega 指标名对齐**，形成「估算建议 ↔ 线上口径」自动对照，而不是在 Skill 内再造一套 APM。

### 7.1 待建设项

| 项 | 说明 |
|---|---|
| Skill ↔ PerfMonitor 字段对齐 | 报告中的函数/接口名映射到 Omega 事件 |
| 与 Lighthouse / Performance trace | 本地真测补充线上采样 |
| AST / 调用图 | 替代 grep 级函数统计，提高依赖识别准确度 |
| 插桩建议代码块 | 一键生成对接 PerfMonitor 的打点片段 |
| 批量 CI | 对 `src/pages/**` 出汇总门禁（仍偏静态） |
| HTML/JSON 稳定导出 | 把「宣称格式」落成固定模板脚本 |

### 7.2 已知风险与缓解

| 风险 | 缓解 |
|---|---|
| 估算偏离真机 | 报告标明「估算」；P0 改动后强制 DevTools 复测 |
| 漏读 mixin/store | 规程要求递归读相关文件，不只看单文件 |
| 业务入口差异 | 注意事项要求覆盖不同入口 / 返回 / 参数变化 |
| 脚本骨架被误当终稿 | README 明确「需 Claude 深度分析后完善」 |
| 优化建议过大 | 用 P0/P1/P2 强制拆阶段，先吃低成本高收益 |
