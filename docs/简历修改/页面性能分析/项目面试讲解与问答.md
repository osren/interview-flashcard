# 商旅 H5 / 小程序性能监控与体验优化：面试讲解与问答

> 依据用户简历 PDF 和本目录项目材料整理。个人贡献、统计口径须按实际情况校准。

## 30 秒项目介绍

这个项目解决的是商旅 H5 和星河小程序页面“用户觉得慢，但缺少同一口径的数据定位”的问题。我做的工作分两层：先在业务仓建设 `perf-monitor.js`，把 H5 和星河的采集差异收敛起来，监控跨页链路、LCP/FCP 和关键接口耗时；再根据数据和链路排查结果优化列表页和底部菜单，包括缓存命中后跳过重复请求、把 fetch/render/paint 分桶、延后非首屏逻辑，以及优化菜单排序。项目材料记录列表 LCP 从约 1400ms 降到 1160ms，下降约 17%，星河底部菜单切换卡顿改善约 27%。此外我把静态分析步骤沉淀成性能分析 Skill，让定位、改造、验收形成复用流程。

## 项目拆解

### 背景和目标

商旅列表页承载日期选择、查看产品和继续预订。简历给出的基线是列表 LCP 约 1400ms，星河底部菜单切换有卡顿反馈。原先只有粗粒度耗时，网络、业务计算和渲染混在一起，无法判断究竟是接口慢、重复请求、重渲染还是非关键逻辑阻塞首屏。

目标有三点：建立跨端可比的监控；把端到端耗时拆成可定位的阶段；按数据优化并用同一口径验收。

### 监控方案：Adapter 与分层指标

H5 可使用 `PerformanceObserver` 等 Web Performance 能力，小程序侧使用 `wx.getPerformance`。项目在采集层封装环境 Adapter，让业务埋点尽量使用统一接口，底层按运行环境选择数据源。它减少业务代码中的平台判断，也降低只覆盖 H5、遗漏小程序的风险。不同平台能力并不完全相同，因此要处理缺失指标，不能假设数据天然等价。

监控分三层：

1. **跨页链路**：例如首页到列表的 `home_to_list_complete`，衡量用户从入口到目标页完成的总体验。
2. **页面指标**：LCP/FCP。LCP 关注视口内最大内容元素出现时间，FCP 关注首次内容绘制。
3. **关键接口**：例如首页 `getHomeData`，观察关键数据依赖。

数据统一经 Omega 上报。LCP/FCP 是页面指标；跨页耗时和接口耗时属于业务自定义监控维度，不要统称为 Web Vitals。

### 页面上的三项改造

**切换日期时复用已加载的数据。** 按简历中的项目描述，用户切到一个已经加载过的日期时，页面直接使用该日期已有的数据渲染，跳过重复请求；切到还没有数据的日期时，仍通过接口获取数据。这样减少的是用户来回切日期时重复发出的请求和等待时间。监控需要区分“缓存数据直渲”和“接口返回后渲染”两条路径，否则两种体验会混在同一个耗时数据里。

面试时可以这样说：“列表会复用已加载日期的数据。用户切回访问过的日期时直接渲染缓存，不再重复请求；第一次访问某日期仍走接口。我们分别统计缓存直渲和接口返回两条路径，并修正了切日期重渲时的统计口径。”

**缓存和竞态的具体口径：** 项目问答资料进一步明确，缓存是同一页面会话内的内存 `Map`（或页面级 store），以日期作为 key；刷新页面后缓存清空，再访问时正常请求。命中日期缓存时进入 `cacheHit → skipFetch → directRender`，因此缓存路径的 fetch 耗时为 0，主要耗时是渲染。快速切换日期时，每次变更递增 `requestId`，异步响应落地前检查它仍是最新请求；只有当前选中日期对应的最新响应可以更新页面。运行环境支持时可以再取消旧请求，但核心正确性条件是旧响应不能覆盖当前日期。项目材料没有说筛选条件也纳入 key，所以除非业务代码确认，不要自行添加这一点。材料也明确刷新不持久化缓存；TTL、最近 N 天淘汰、版本失效是可能的后续增强，不是已实现能力。

旧版《面试准备稿.md》和《PerfMonitor使用与Skill配合指南.md》里有一段固定键 `listData`、命中后仍请求的示例，与上述项目问答资料和简历中的状态机口径冲突。结合项目专属问答和简历，应以“内存 Map 按日期缓存、命中跳过请求”为当前面试口径；那段 `listData` 代码只能作为双路径埋点的旧示意，不要拿来描述实际策略。仓库没有商旅业务页面的原始实现文件，因此如果面试官要求看具体代码，仍需以实习仓库中的实现为准。

**修正耗时上报口径。** 原先的问题是一个“接口耗时”统计混入了切日期后页面重渲染的时间。看板上数值变长时，无法判断是网络响应慢，还是接口已返回、页面还在更新。整改方向是把一轮列表展示拆成三个独立阶段：

1. `fetch`：从请求发出到响应/数据可用，回答“数据等了多久”。
2. `render`：从数据交给页面到框架完成本轮视图更新，回答“页面更新花了多久”。
3. `paint`：从视图更新后到内容实际可见，回答“用户何时看到结果”。

分析时先分别看这三段，避免把 render/paint 算到接口上；同时保留从用户切换日期到新列表可见的端到端耗时，才能判断用户实际等待。首次进页的 LCP 与后续切日期是不同场景：切日期属于页内交互，应单独记交互耗时/渲染耗时，不应把每次切换都当作一次新的页面 LCP。目录材料只确认了“拆分 render/fetch/paint”和“修正切日期重渲口径”，没有给出埋点代码与精确时间戳定义；上面的阶段边界是复盘时应讲清的口径，实际名称和起止点需与当时代码、Omega 指标定义核对。

**延后非关键逻辑。** `getHomeData` 决定首页主体数据；`privacyPopList` 是隐私弹窗相关数据，不是首屏主体内容的依赖。旧流程把两者一起放在首屏初始化等待链路中；调整后保持 `getHomeData` 在关键路径，将 `privacyPopList` 移出首屏 `Promise.all`，通过封装的 `defer(fn)` 延后执行。项目问答资料给出的策略是优先使用 `requestIdleCallback` 并设置 timeout，确保长时间繁忙时任务不会一直饿死；不支持时退回 `setTimeout(fn, 0)`（资料也提到可用 `queueMicrotask`，但它会在当前任务后的微任务阶段执行，不等同于等待浏览器空闲）。因此面试口径讲 `defer` 封装及空闲回调优先、定时器 fallback，不把 `setTimeout(0)` 说成唯一实现。

目的不是丢弃隐私弹窗数据，而是先让首屏主要内容就绪，减少非关键逻辑对首屏完成路径的影响。网络等待本身不会自动阻塞浏览器绘制；问题在于初始化是否等待该 Promise，以及它的回调/状态更新是否影响主线程或首屏统计。验证时观察 LCP、首屏可交互和错误率，确保核心选日期/预订交互仍可用。隐私弹窗仍需按业务要求展示；若属于必须在首屏前展示的合规确认，就不能简单延后。项目准备资料明确给了 defer 的策略，但仓库中没有商旅业务源代码，无法核验实际 helper 是否完全按该策略实现。

### 星河底部菜单卡顿

问题不是“菜单数据量大到排序算法复杂度不够”，而是切换时反复对同一份菜单数据排序并触发重渲染。项目快问快答资料明确给出的实际优化是用 `useMemo` 缓存排序结果：排序输入未变化时复用上一次结果，只有依赖数据变化时才重新计算。这样菜单切换不再因为重复计算排序而多做一遍工作，减少主线程任务和不必要的渲染。

旧版《面试准备稿.md》曾给出 `requestIdleCallback` 的“先渲染未排序列表，再空闲时排序并二次渲染”示例；这与项目快问快答及当前简历明确写的 `useMemo` 不同。综合项目专属问答和当前简历，本次复盘以 `useMemo` 作为实际方案；旧示例属于过时/泛化方案，不应继续拿来讲这次菜单优化。面试追问 `useMemo` 时说明依赖数组必须包含排序输入，且缓存只在依赖未变时复用；若依赖每次 render 都创建新引用，缓存仍会失效。`useMemo` 是减少重复计算，不是把排序移出主线程，也不能保证跳过组件本身的所有渲染。

项目材料记录菜单切换卡顿改善约 27%。现有资料描述结果来自用户行为埋点对比，但没有展示指标公式、样本量和设备分层；因此可以说“菜单切换卡顿指标改善约 27%（项目埋点对比）”，不要进一步编造 FPS、P95 或固定毫秒数。

### 静态分析 Skill 的定位

`page-performance-analysis` Skill 按加载、交互、数据监听三个阶段读源码，排查请求瀑布、重复请求、watch/computed 连锁、渲染和防抖节流等风险，输出函数风险排序及 P0/P1/P2 建议。它帮助缩小排查范围，但静态估算不是线上实测，最终仍需 PerfMonitor/Omega 或平台 profiler 验证。

```text
静态分析找嫌疑点 → PerfMonitor 建基线 → 改业务链路 → Omega 对比 → 继续迭代
```

简历写 `perf-debug-loop`，本地材料叫 `page-performance-analysis`。面试前要核实这是同一 Skill 的新旧名称还是不同产物，确认前不要混用。

## 面试问题与参考回答

### Q1：项目的核心难点是什么？

**答：** 多端性能数据来源不同，原统计又把请求和重渲染混在一起。我用 Adapter 收敛 H5/星河采集方式，再按跨页、页面指标、接口分层；列表内部拆 fetch/render/paint。这样能先判断问题在哪段，再选择缓存、请求或渲染优化。

### Q2：为什么封装 Adapter？分别调用平台 API 不行吗？

**答：** 分别调用可行，但会把环境判断散落在业务埋点里，指标命名、缺失处理和上报格式也容易不一致。Adapter 将平台差异限制在采集层，业务侧关注采什么、何时采。仍要承认平台能力不同，需要处理不支持或口径不等价的指标。

### Q3：LCP 怎么测，为什么适合这个页面？

**答：** LCP 描述视口内最大内容元素呈现时间，能反映用户等待主要内容出现的感受。H5 通过 Web Performance 能力采集，小程序侧适配其性能 API，再统一上报。要再核对实际观察对象、结束时机和页面切换处理，避免把自定义结束点说成标准 LCP。

### Q4：缓存直渲怎样避免错数据？

**答：** 核心是让数据和日期一一对应，并且只让当前日期的请求结果更新页面。

1. **缓存命中时**：列表数据放在同会话内的内存 `Map`，日期作为 key。用户选中某日期后，只读取该日期对应的数据，再直接渲染；不能拿“最近一次数据”不看日期就展示。
2. **缓存未命中时**：发起该日期的请求，并记录本次请求的 `requestId`。用户再次切换日期就递增序号；响应返回时，只有 `requestId` 仍是最新值、且请求日期仍等于当前选中日期，才允许更新页面。这样 A 日期的慢响应不会覆盖用户已经切到的 B 日期。
3. **缓存范围**：这是页面会话内按日期复用，刷新后内存缓存清空，再访问时重新请求。项目材料没有说明筛选条件也参与 key；如果列表结果会受筛选影响，实际代码就必须把筛选条件纳入 key 或在筛选变化时清缓存，面试时先核实，不要自行声称已经这么做。

一句话总结：**命中时按当前日期取对应缓存；未命中时请求带上日期身份，回包只接受最新且仍匹配当前选择的结果。** 这就是避免日期串数据和异步竞态的关键。

目录里的旧 `loadListData()` 示例使用固定键 `listData`，且命中后仍请求，与项目问答资料里的“按日期缓存、命中跳过请求”不一致；它只能作为双路径埋点示意，不代表实际缓存策略。项目问答资料明确了 `requestId` 校验；取消旧请求可以作为补充优化，但不要说成必须依赖它才能保证正确性。

### Q5：为什么拆 fetch、render、paint？怎么理解每一段？

**答：** 原因是 `measure` 的起止点划错了：若从 `fetchStart` 一直量到 `renderEnd`，接口耗时就把等待响应、数据处理和页面重渲都包含进来，容易误以为后端慢。修正后在 fetch 结束、render 开始/结束等节点分别打 mark，上报 fetch、render、paint 三桶；缓存命中路径单独标记，不计 fetch。切日期属于页内交互，单独看交互到列表可见耗时，不把它当成一次新页面 LCP。接口耗时应只覆盖请求到数据可用，不包含 Vue/MPX 的视图更新。项目材料没有给出各 mark 的实际名称和代码，但这就是项目复盘资料明确的口径。

面试追问时可补充：mark 是时间轴上的时间点，measure 计算两个 mark 之间的 duration。每段都要有明确起止点，成功、失败和缓存命中分支都要走到正确的结束/上报逻辑，否则会出现悬挂或错误统计。浏览器 LCP 仍通过性能 API 采集；业务自定义的 fetch/render/paint measure 用来定位链路阶段，不冒充原生 LCP。

### Q6：为什么延后 privacyPopList？它真的会阻塞浏览器绘制吗？

**答：** `getHomeData` 是首页主体内容依赖，`privacyPopList` 是隐私弹窗相关数据。原流程把它们一起放进首屏初始化等待；改造是让 `getHomeData` 先完成，并把 `privacyPopList` 从首屏 `Promise.all` 中移出，通过 `defer(fn)` 延后。项目问答资料给出的封装策略是优先 `requestIdleCallback`（设置 timeout，避免任务一直等不到空闲），不支持时用 `setTimeout(fn, 0)` 兜底。这样缩短首屏关键等待，但不是不展示隐私提示。网络请求不会天然阻塞绘制，关键是去掉了初始化等待依赖；仍要验证首页内容和核心交互优先可用，并遵守隐私提示时序。具体原始 helper 不在当前仓库，面试按项目问答资料描述实现策略，不说目录示例中的 setTimeout 是线上唯一代码。

### Q7：切日期的 render/fetch/paint 与首页 privacyPopList 延后有什么关系？

**答：** 它们是两个页面场景、解决两类问题。列表切日期时拆阶段，是为了知道等待来自接口还是视图更新，并修正交互重渲的统计口径；首页延后 `privacyPopList` 是调整非关键请求相对 `getHomeData` 的执行时机。两者都围绕关键路径和指标口径，但不能说是同一个改动，也不要把列表的三桶指标套到首页接口上。

### Q8：星河底部菜单卡在哪里，优化思路是什么？

**答：** 菜单切换时重复进行排序并引起重渲染，增加了主线程工作。项目采用 `useMemo` 缓存排序结果：排序依赖没变就复用结果，依赖变化才重新排序，减少切换时的重复计算。要保证依赖数组包含参与排序的菜单数据和排序条件；如果依赖每次都生成新对象，缓存就会失效。`useMemo` 只缓存计算结果，不会把排序放到后台，也不代表整个组件完全不渲染。

项目材料记录菜单切换卡顿改善约 27%，数据来自用户行为埋点对比；当前材料没有给指标公式、样本量和设备分层，因此不把它扩展成 FPS、P95 或固定毫秒数。

### Q9：17% 怎么算？

**答：** 绝对减少 240ms，`240 / 1400 ≈ 17.1%`，所以约 17%。我会说明这是项目复盘使用的统计口径，并补充看板时间范围、样本量和环境；不能提供的细节不会包装成 A/B 结论。

### Q10：卡顿改善 27% 的统计方式是什么？

**答：** 项目快问快答和简历修改版都明确是用 `useMemo` 缓存排序结果，减少菜单切换时的重复排序。旧版准备稿里的 `requestIdleCallback` 是另一种曾写入示例的方案，不是这次优化的当前口径。27% 来自项目材料中的用户行为埋点对比，但未提供公式和样本细节，所以我只按“卡顿指标改善约 27%”描述。

### Q11：Skill 能直接测函数耗时吗？

**答：** 主要做源码静态分析与风险评估，给潜在瓶颈和优先级，不等于运行时 profiler。真实耗时需用 PerfMonitor、浏览器或小程序性能工具验证。

### Q12：Skill 的输入输出是什么？

**答：** 输入目标页面、业务场景和源码；流程覆盖加载、交互、监听；输出页面概述、函数耗时风险、关键路径和 P0/P1/P2 建议。可复用性来自分析维度与报告结构，不代表对所有框架自动测量准确。

### Q13：延后逻辑会不会影响 TTI 或 SEO？

**答：** 需要一起观察。延后非关键逻辑可能改善 LCP，但若延后必要交互初始化会影响可用时间；SEO 还取决于渲染方式和爬虫可见内容。项目材料只有 LCP 收益，没有 SEO/TTI 数据，所以不声称它们提升。

### Q14：如果继续做，你会补什么？

**答：** 补齐指标定义、版本、机型/网络分层和样本量；增加缓存命中、请求失败和快速切换的边界观测；把静态建议与运行时热点关联。优先级由真实用户数据决定。
