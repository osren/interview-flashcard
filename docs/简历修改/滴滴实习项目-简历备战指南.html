项目一：性能监控与体验优化

1.1 一句话概括

在商旅 H5/小程序搭建函数级性能监控体系，定位并优化列表页 LCP 和星河底部菜单卡顿，沉淀为可复用 Agent Skill。

1.2 问题背景（面试必讲）

  • 痛点：列表页 LCP 约 1400ms，星河底部菜单切换卡顿，用户反馈体验差

  • 缺少抓手：此前只有 FCP/LCP 数字，缺少函数级、接口级的性能数据

  • 排查困难：不知道慢在网络、渲染还是计算；优化没有优先级

1.4 具体优化案例（面试重点）

案例 A：列表页 LCP 优化

问题定位：

  1. 接入 getHomeData 接口耗时埋点

  2. 发现 privacyPopList 等非关键接口串在首屏关键路径

  3. 切日期场景会重复请求，缓存命中时仍触发网络请求

优化动作：

  • 剥离非关键路径：把隐私弹窗接口移出 LCP 统计链路，defer 延后加载

  • 缓存命中直渲：增加状态机 cacheHit → skipFetch → directRender，避免白等

  • 修正口径：切日期重渲时，区分「接口返回」和「缓存命中」两条路径分别上报

结果：LCP 1400ms → 1160ms（↓17%）

技术细节（面试追问）：

  • Q: 为什么要剥离 privacyPopList？

  • A: LCP 应对应用户感知的最大内容渲染，隐私弹窗不是首屏关键内容，串进来会污染口径，让优化方向跑偏。

案例 B：星河底部菜单卡顿

问题定位：

  • 用户切换底部 tab 时有明显卡顿

  • 通过 PerfMonitor 定位到排序计算开销大

优化动作：

  • 用 useMemo 缓存已排序结果，避免每次切换重复计算

结果：卡顿改善约 27%

技术细节（面试追问）：

  • Q: 为什么排序会导致卡顿？

  • A: 底部菜单数据量不大，但每次切换都触发排序 + 重渲染，累积起来拖主线程；缓存后只在数据变化时才重算。

1.5 工程化沉淀

perf-monitor.js 设计要点

Agent Skill 固化

把「定位 → 诊断 → 优化 → 验收」闭环固化为 page-performance-analysis Skill，后续性能问题可复用分析流程。

Skill 核心能力：

  • 读页面源码，按加载/交互/监听三阶段拆函数

  • 估算耗时并排序（第一梯队 >500ms / 第二梯队 200-500ms / 第三梯队 <200ms）

  • 识别瓶颈（串行瀑布、频繁触发、防抖节流、重复请求）

  • 输出 P0/P1/P2 分级优化建议

项目二：AI 智能监控降噪

2.1 一句话概括

基于 LLM 的接口告警智能判定系统，每条告警走一次模型判断「该不该报、定什么级」，把噪音挡在派发之前。

2.2 问题背景（面试必讲）

  • 痛点：机酒火线上接口告警量大，噪音占比高

    • 业务正常拒绝（无票、已退改、超时未支付）占大多数

    • 低价值展示类错误（NPS、公告、分享页）刷屏

    • 真故障被淹没，值班容易漏看

  • 核心矛盾：不能用简单规则过滤（会误杀真故障），需要理解业务语义

2.5 架构理解（面试加分项）

为什么每条都走 LLM？

决策：不做规则预过滤，每条都走 LLM。

理由：

  1. 业务拒绝语义复杂（同码不同场景），硬规则容易误杀

  2. 调策略不改代码（改 Prompt = 调阈值）

  3. 性能用别的手段补（缓存、聚合、异步）

可插拔 Domain 的价值

换团队 = 换配置不动引擎：

  • 机票：DOMAIN=flight + domains/flight/

  • 酒店：DOMAIN=hotel + domains/hotel/

  • 火车票：DOMAIN=train + domains/train/

引擎代码（router/triage/llm/pipeline）对所有团队通用。

路由引擎设计

四步判定：

  1. pathname 归一化（去 host/query）

  2. 归属判别优先（非自有前缀 → non-core）

  3. 有序匹配（特例排在宽松规则前）

  4. 未命中兜底（fallbackKey 保守上报）

火车票示例：

  • 自有前缀：/esapp/

  • 分类：payment / order / refund-change / query / user-auth / order-detail / display / non-core

  • 兜底：未匹配到规则 → order（P1 保守上报）

2.6 面试高频问题

Q1: 你具体做了什么？

诚实对齐：

  • 我做了火车票 Domain 的路由表和 Prompt 配置

  • 比如 /railway/train/transferLeftTicket 这个接口，我把它路由到 query 分类，定义为下单主流程入口，参数错误判 P1

Q2: 工程理念怎么落地的？

讲具体例子：

  1. 业务正常拒绝识别：我去源码里找 errorCode 对应的业务场景，把"无票/已退改"写成 Prompt 里的 business_reject 清单

  2. 兜底策略：有一次模型解析 JSON 失败了，我加了个 fallback 直接保守上报 P2，保证不漏告警

  3. 评测纪律：用漏报率 FN 作为头号指标，宁愿多报噪音也不能漏真故障

Q3: 你觉得这个项目难在哪？

三个难点：

  1. 业务知识沉淀：哪些是业务正常拒绝、哪些是真故障，这个边界要产品+研发一起定义

  2. 宁可误报不可误杀：宁愿多报噪音也不能漏真故障，所以调 Prompt 要保守

  3. 接口清单要准：漏掉的接口可能漏报，所以后来加了 drift-check 盯清单漂移

Q4: 为什么余票查询异常判 P1？

回答要点：

  • 火车票主流程链：查询(余票) → 填单/校验 → 下单占座 → 支付 → 出票 → 退改

  • 余票查询是下单主流程入口，挂了等于阻塞下单

  • 不能因为名义上是「查询」就降级成 P2/P3

Q5: 接口清单过期会不会漏报？

诚实回答：

  • 不会漏报：自有前缀内未命中 → fallbackKey 保守上报；非自有 → non-core 兜底

  • 清单过期只降低 severity 精度，不会造成漏报

  • 后续加了 drift-check.sh 纯 grep 盯漂移，可挂 CI

Q6: LLM 方案 vs 纯规则方案？

为何选 LLM：噪音形态多、业务语义重，规则预过滤误杀成本高；先用 LLM 保证召回与可解释 reason。

Q7: 当前落地到哪一步？

诚实现状：

  • ✅ 通用引擎（HTTP / Kafka）

  • ✅ 火车票 Domain（business_reject 已回源核验）

  • ✅ 机酒 url 清单已摘取（Domain 待 onboard）

  • ⏳ 真实派发通道（接 IM / 电话 / 工单，当前为日志占位）

  • ⏳ 频次统计、告警聚合、结果缓存

面试建议：主动说清「判定链路已通、派发与缓存是下一阶段」，体现演进意识而不夸大上线范围。

  • ❌ "Skill 已经精确测出所有函数耗时"
