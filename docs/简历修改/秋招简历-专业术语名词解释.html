RESTful API 详解

面试向深讲 · 附商旅实例

REST（Representational State Transfer，表述性状态转移）是 Roy Fielding 2000 年博士论文提出的架构风格。RESTful API 即遵循该约束、以“资源”为中心的 HTTP API 设计：用 URI 标识资源、用 HTTP 方法表达操作、用状态码表达结果、服务端不保存客户端状态。

核心约束（面试常考 5 条）

  • 资源化（统一接口）：一切皆资源，URI 用名词复数、禁动词 —— /api/v1/orders 而非 /api/v1/getOrders。
  • 无状态（Stateless）：请求自带完整信息、服务端不存会话；鉴权靠 Token（如 JWT），任意节点可处理请求，方便水平扩展。
  • 可缓存（Cacheable）：GET 响应可声明缓存，减少重复请求。
  • 分层（Layered System）：客户端不感知网关、负载均衡、下游服务。
  • 统一接口语义：方法 + 状态码 + 内容协商（JSON/XML），接口自描述。

URL 设计规范

  • 名词复数 + 层级嵌套表达从属：/api/v1/orders/{id}/items
  • 过滤 / 分页 / 排序走 query：?status=paid&page=2&page_size=20&sort=-created_at
  • 版本号放路径：/v1/
  • 动作语义用 POST 表达（退款更 REST 的做法是 PATCH /orders/{id} 改 status，而非 POST /orders/{id}/refund）

常见状态码速记

  • 2xx（成功）：200 成功 · 201 创建成功 · 204 无内容（删除）
  • 4xx（客户端问题）：400 参数格式错 · 401 未认证 · 403 无权限 · 404 资源不存在 · 409 冲突（重复下单 / 无票） · 422 业务校验不通过 · 429 限流
  • 5xx（服务端问题）：500 内部错误 · 502 网关错误 · 503 服务不可用 · 504 超时

完整例子：商旅机票下单链路（对应简历业务）

步骤请求与结果说明
1. 查余票GET /api/v1/flights?from=CTU&to=PEK&date=2026-10-01 → 200返回航班列表
2. 下单占座POST /api/v1/orders，body 带航班 + 乘客 → 201 Created，Location 指向新订单创建资源
3. 无票失败同 2，但余票不足 → 409 Conflict {code:"NO_TICKET"}即 business_reject 里的“无票”
4. 查订单GET /api/v1/orders/20261001-001 → 200按 id 读资源

项目二里的 POST /api/v1/alarms/triage、/judge、/eval 同样是标准 RESTful 风格：资源是“告警 / 评测用例”，动作靠 POST 触发。

面试高频追问速答

  • REST vs RPC？REST 面向资源、语义来自 HTTP，适合对外 / 跨团队开放接口；RPC（gRPC、JSON-RPC）面向“方法调用”，强类型、性能好，常见于内部服务间。
  • PUT vs PATCH？PUT 整体替换（缺字段会被清空），PATCH 只改传入字段；PUT 幂等，PATCH 通常不幂等。
  • 为什么无状态？任意节点可处理请求 → 易水平扩展、易缓存、故障恢复简单；代价是每次请求携带更多信息。
  • 幂等性怎么理解？GET/PUT/DELETE 幂等（重试结果一致），POST 不幂等 —— 所以“重复提交”要用幂等键（Idempotency-Key）或数据库唯一约束兜住，正好对应 business_reject 里的“重复提交”场景。
  • 400 和 422 怎么选？400 是语法 / 格式错误，422 是语义 / 业务校验不通过（如无票）。
  • 鉴权怎么做？JWT Bearer Token：放 Authorization 头，服务端验签；401 未认证、403 无权限。
