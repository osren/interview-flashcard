## 实习经历（修改后）

**滴滴出行 · 企业版商旅** | 前端开发实习生 | 2026.01 — 2026.07

### 项目一：商旅 H5/小程序性能监控与体验优化

- **问题背景**：商旅列表页 LCP 约 1400ms，星河底部菜单切换卡顿，用户反馈体验差，但此前缺少函数级性能数据
- **我的工作**：
  - 在业务仓搭建 `perf-monitor.js`，在 H5 和星河（双端技术栈不同）环境抽象统一上报，监控跨页链路、LCP/FCP 和关键接口耗时
  - 接入 `getHomeData` 接口耗时，定位并剥离 `privacyPopList` 等拖长 LCP 的非关键路径
  - 列表页优化：分析发现切日期会重复请求，改为缓存命中时直渲不做请求；修正重渲口径
  - 星河底部菜单：排查切换时排序计算开销大，优化排序逻辑
- **结果**：列表页 LCP **1400→1160ms（↓17%）**；星河底部菜单切换卡顿约 **↓27%**
- **沉淀**：把「定位慢 → 找瓶颈 → 改造 → 验收」的闭环固化为可复用 Agent Skill，让后续性能问题有函数级抓手

### 项目二：商旅机酒火接口告警智能降噪

- **问题背景**：机酒火线上接口告警量大，业务正常拒绝（无票/已退改/超时未支付）占比高，真故障被淹没，值班容易漏看
- **我的工作**：
  - **接口发现**：用 Claude Code 分析业务代码仓库，自动摘取各品类的核心接口清单，避免手工枚举遗漏
  - **火车票 Domain 配置**：根据接口清单，配置 url → 分类（query/payment/order/refund-change/non-core）的路由规则；为每类定义 severity 基线（如余票查询异常判 P1，因为是下单主流程入口）
  - **Prompt 编写**：写 `business_reject` 业务正常拒绝清单（如"无票/已退改/重复提交"），避免把真故障当噪音过滤掉
  - **兜底策略**：模型超时/解析失败时统一保守上报 P2，永不吞告警
  - **评测闭环**：搭 `/judge`（只判定）+ `/eval`（批量 vs gold 打分）接口，用漏报率 FN 作为头号指标，防止降噪过度
- **架构理解**：引擎领域无关，业务知识全在 `domains/<team>/` 配置，换团队只换配置不动引擎

## 面试时怎么讲

### 第一个项目（性能监控）

面试官可能会问：
- "这个 Skill 是你写的吗？"
  - 不美化：**Skill 是团队搭的**，但我参与了监控体系搭建和性能优化
  - 重点：**具体问题是我定位的**——接口耗时、缓存逻辑、星河端兼容
  - 亮点：H5/星河双端环境抽象、统一上报链路

- "项目难点是什么？"
  - 难点1：星河和 H5 技术栈不同，上报逻辑要兼容两套
  - 难点2：列表页"切日期"场景，原来每次都发请求但白屏，通过 PerfMonitor 数据发现后改成缓存命中直渲
  - 难点3：隐私弹窗接口 `privacyPopList` 拖了 LCP，但这个接口是后加的，没人注意

### 第二个项目（AI 监控）

面试官可能会问：
- "你具体做了什么？"
  - 我做了**火车票 Domain 的路由表和 Prompt 配置**
  - 比如 `/railway/train/transferLeftTicket` 这个接口，我把它路由到 `query` 分类，定义为下单主流程入口，参数错误判 P1

- "工程理念怎么落地的？"
  - 讲具体例子：
    - 比如"业务正常拒绝"怎么识别：我去源码里找 errorCode 对应的业务场景，把"无票/已退改"写成 Prompt 里的 business_reject 清单
    - 比如兜底：有一次模型解析 JSON 失败了，我加了个 fallback 直接保守上报 P2，保证不漏告警

- "你觉得这个项目难在哪？"
  - 难点1：**业务知识沉淀**：哪些是业务正常拒绝、哪些是真故障，这个边界要产品+研发一起定义
  - 难点2：**宁可误报不可误杀**：宁愿多报噪音也不能漏真故障，所以调 Prompt 要保守
  - 难点3：**接口清单要准**：漏掉的接口可能漏报，所以后来加了 drift-check 盯清单漂移
