# 第一部分：大白话全链路科普

按「办手续 → 上岗安检」理解整套系统。术语尽量换成大白话，中间遇到专业词会随手解释。

---

## 1. 先备一张「词小抄」

后面会反复出现，先混个脸熟：

| 词 | 大白话 |
|---|---|
| **告警** | 系统出错时，自动往群里 / 电话里「喊人」 |
| **值班** | 轮流盯线上问题的人，被喊多了会麻木 |
| **噪音** | 其实不重要、不该喊人的告警（比如「无票」） |
| **降噪** | 把不该喊的滤掉，只留该看的 |
| **接口 / API / url** | 前端请求后端的那个地址，比如 `/esapp/.../queryLeftTicket` |
| **Domain** | 某一业务自己的「说明书文件夹」（路由表 + 判定话术） |
| **Prompt** | 写给大模型看的说明书 / 题干 |
| **LLM / 大模型** | ChatGPT 那类 AI，这里用来「帮人判断」 |
| **路由** | 根据 url，决定这条错误属于哪一类业务（这里不是 Vue Router） |
| **severity / P0–P3** | 严重等级：P0/P1 很急，P3 不太急 |
| **should_report** | 要不要真的喊人：true=报，false=当噪音扔掉 |
| **business_reject** | 「业务正常拒绝」：看起来像报错，其实是正常业务结果（无票、已退改） |
| **Kafka** | 一种「消息队列」，告警可以先进队列再被服务一条条消费（像快递柜） |
| **HTTP API** | 别人用请求调你服务，比如 `POST /triage` |
| **Skill** | Claude Code 里可复用的「标准作业流程」，像自动化小助手 |
| **漏报 FN** | 该喊人却没喊（最危险） |
| **误报 FP** | 不该喊却喊了（吵，但比漏报好） |
| **兜底** | 出意外时的保底策略：搞不定就保守上报，绝不闷声扔掉 |
| **评测 / eval / gold** | 用「标准答案卷子」考模型判得对不对；gold=标准答案 |
| **ownedPrefixes** | 「自家接口」的路径前缀，如火车票 `/esapp/`；不在里头的当外人 |
| **fallbackKey** | 自家域内没匹配到具体规则时的兜底分类，倾向上报 |
| **drift-check** | 检查「代码里的接口」和「清单里登记的」有没有对不上（漂移） |

## 2. 全景：其实就两段时间

把整个系统想成：**先办入驻手续，再上岗安检**。

```
【接入期 · 办手续，偶尔做一次】
扫业务代码 → 列出有哪些接口 → 人确认 → 生成「说明书」→ 启动服务

【运行期 · 上岗，每条错误都走一遍】
监控发现接口报错 → 问 AI 该不该喊人 → 该喊才推送，不该喊就扔掉
```

- **Skill** 主要在「办手续」阶段帮忙
- **引擎（error-triage 服务）** 在「上岗安检」阶段干活
- Skill **不**参与每条告警的实时判定，它负责：怎么把火车票 / 机票业务接进来

一句话定位：

> 这不是「监控系统」，是告警门口的智能安检员——每条接口错误进来，先问大模型「该不该喊人、喊多大声」，噪音挡在外面，真故障才推给值班。

## 3. 运行期：一条错误告警怎么走完（最重要）

用一个具体例子：  
用户查中转余票，接口返回「参数错误」。

### 3.1 第 1 步：收包（有人把错误塞进来）

来源可以是两种（知道有两条入口就行）：

1. **HTTP**：别的系统直接 POST 一条 JSON 过来
2. **Kafka**：错误先丢进消息队列，服务再一条条捞出来（像快递柜，先存后取，高峰不堵死）

收到大概长这样：

```json
{
  "url": "/esapp/railway/train/transferLeftTicket",
  "errorCode": "1",
  "errorMsg": "参数错误"
}
```

- **url**：哪个接口挂了（最关键，后面靠它分类）
- **errorCode / errorMsg**：错误码和错误文案（给 AI 看的材料）
- 字段不全也没关系——搞不清就倾向「还是报一下」，别偷偷放过

两个入口最终都只调同一个 `handleAlarm`，判定逻辑不重复写两套。

### 3.2 第 2 步：路由（先给错误贴标签）

「路由」不是 Vue Router，这里是：**看 url，判断这条错误属于哪一类**。

比如：

- 路径里有支付相关 → 贴「支付」
- 有余票查询 → 贴「查询」
- 不是自己家前缀（比如外部营销域名）→ 贴「非自有 / non-core」

火车票自己家前缀一般是 `/esapp/`：

- **在自家前缀里**：按规则细分类
- **不在**：当外人接口，默认很轻（不太喊人）——「三方挂了别让咱们值班背锅」
- **自家但没匹配到具体规则**：走兜底类（偏保守，倾向上报）——「新接口还没登记，先别漏报」

例子里 `LeftTicket` → 归到「查询」类。

### 3.3 第 3 步：拼 Prompt（把说明书 + 案情交给 AI）

给大模型的内容分两块：

1. **system（说明书）**
   - 全局规则：什么叫该报、什么叫正常拒绝、信息不全怎么办……
   - 本类细则：查询类接口怎么定级、哪些码是正常拒绝……
2. **user（案情）**
   - 就是这条告警的 JSON：哪个 url、啥码、啥文案

你可以把它想成：

> 「你是值班助手。规则如下……  
> 现在有一条：中转余票接口返回参数错误。请判断：报不报？几级？为什么？」

### 3.4 第 4 步：问大模型 + 读答案

- 调公司内部的大模型网关一次（像调一个 AI 接口）
- `temperature=0`：让它尽量稳定，别今天 P1 明天 P2 乱飘
- 要求它回固定 JSON，比如：

```json
{
  "should_report": true,
  "severity": "P1",
  "error_type": "param_validate_failed",
  "reason": "这是下单主流程入口，参数错误也要喊人"
}
```

**万一 AI 挂了 / 超时 / 回的不是合法 JSON？**  
→ 统一保守处理：**还是报，按 P2**。  
原则：降噪服务自己挂了，也不能把真故障闷掉。

### 3.5 第 5 步：派发（真的喊不喊人）

- `should_report = false` → 当噪音扔掉
- `true` → 按严重等级推到群 / 电话 / 工单

（当前代码里真实推送还没接完，先打日志占位——面试别说已经稳定打电话了。）

**为什么余票查询也能是 P1？**  
名字叫「查询」，但它是买票流程第一步；这一步全挂 = 用户买不了票，所以可以很严重。别被「查询」俩字骗了。

**反例：** 如果返回的是「无票」——这是正常业务结果，用户换个车次就行，一般**不该喊值班**。

## 4. 接入期：两个 Skill 干啥（办手续流水线）

把 Skill 想成：**写好的「标准作业手册」**，让 Claude 按步骤帮你干脏活累活。

### 4.1 Skill A：discover（从代码里把接口「挖」出来）

**问题：** 前端项目里接口到处写——有的在 `urls.js`，有的直接写在页面 `axios.post('/xxx')`，新人根本摸不清有哪些。

**Skill A 做的事：**

1. 先看这是啥技术栈（前端 / 小程序 / 后端……），用不同挖法
2. 尽量多挖接口（宁可多，别漏）
3. 顺便记下：这个接口干啥的、哪些错误码其实是「正常拒绝」，并带上「文件:行号」证据
4. 给接口打两个标签：
   - **自家还是外人**（看路径前缀）
   - **核心还是边缘**（挂了用户还能不能走完主流程：搜→下单→支付→出票……）
5. 吐出一份清单文件，比如 `train-urls.js`

**人要做啥：** 看一眼清单，确认「核心链路划得对不对、前缀对不对、死代码别误收」。

它**不**直接生成最终配置，只产「中间表」，坏味道先拦在这。

### 4.2 Skill B：onboard（根据清单生成「说明书文件夹」）

吃掉确认过的清单，生成：

```
domains/train/
├── rules.js     # url 怎么分类（路由表）
└── prompts/     # 各类判定说明书
    ├── _base.md
    ├── query.md
    ├── payment.md
    └── ...
```

- **rules.js**：告诉引擎「这个 url 归哪一类」
- **prompts/*.md**：告诉大模型「这类错误怎么判」

生成的是**草稿**，上线前还要人核对：  
哪些错误码真的是正常拒绝、各级严重度基线对不对。

### 4.3 维护：项目后来又加了新接口怎么办？

有个小脚本叫 **drift-check（漂移检查）**：

- 对比「代码里现在的接口」和「清单里登记的」
- 发现多了 / 少了就报警（可挂到 CI：每次提交自动查）
- 再跑一次 discover 的增量模式：只处理新增那几条，省钱省时间

清单暂时没更新也**不会漏报**：新接口没匹配到规则 → 走兜底，倾向上报。过期只影响「定级准不准」，不影响「会不会丢」。

## 5. 和传统做法比，到底方便在哪

### 5.1 传统常见三种

1. **人盯群**：噪音一多，眼睛花了，真故障漏掉
2. **写死 if-else**：`如果错误码是 2023 就不报`——业务一复杂就写炸，还容易误杀
3. **每个业务改一套代码**：机票一套、酒店一套，引擎被改得越来越脏

### 5.2 这套方案的便利

| 痛点 | 传统 | 现在 |
|---|---|---|
| 接口散落难找 | 人肉翻仓库 | Skill A 帮你广挖 + 带证据 |
| 接新业务慢 | 改服务代码 | 加一个 Domain 文件夹就行 |
| 「正常拒绝」难判 | 硬码表又脆又漏 | 让 AI 看语义 + Prompt 说明书 |
| 调松紧要发版 | 改代码上线 | 改 md 说明书（重启生效） |
| 不知道改好没改坏 | 靠值班吐槽 | 用标准答案卷子打分（尤其盯「漏报」） |
| AI / 服务挂了 | 可能悄悄丢告警 | 搞不定就保守上报 |

**一句话：**  
Skill 让「接业务」从手工作坊变成流水线；引擎让「判告警」从人肉/脆规则变成「说明书 + AI」，同时用兜底保证安全。

## 6. 用前端 intern 视角再串一遍

你熟悉的世界：

> 页面调接口 → 接口返回 errcode/errmsg → 有时弹 toast「无票」

监控世界多一步：

> 同样这些错误，也会被上报到监控 → 可能喊值班

本项目卡在中间：

> 错误要喊人之前，先过一道 AI 安检：  
> 「这是无票这种正常业务，还是真把下单链路搞挂了？」

你作为前端，最相关的点：

- 告警材料往往来自前端 / BFF 的接口错误上报
- Skill 扫的常常是前端仓库里散落的 url
- 以后可能在 BFF 统一调这个判定服务，业务侧接入更轻

## 7. 电梯版（留给面试 / 自己消化）

> 商旅接口一报错就告警，但很多是「无票」这种正常情况，值班被刷屏。  
> 我们在喊人之前，用大模型判断：报不报、多严重。  
> 工程负责收告警、按 url 分类、拼说明书、调 AI；业务知识放在可替换的文件夹里。  
> 两个 Skill 帮我们从代码里挖接口、生成说明书，接新业务不用改引擎。  
> 原则是：宁可多喊一声，也不能漏掉真故障。

### 核心原则（必须记住）

1. **宁可误报，不可误杀**（漏报优先压到接近 0）
2. **判定交给模型，工程只做路由与编排**
3. **引擎领域无关，业务知识全在可插拔 Domain**

### 诚实边界（防面试翻车）

| 可以说 | 不要夸大 |
|---|---|
| 判定链路、火车票 Domain、评测与 Skill 已就绪 | 不要说「已全量覆盖机酒火并显著降噪 X%」 |
| 派发层接口已留，当前为日志占位 | 不要说「已对接电话告警 / 已稳定生产值班」 |
| 频次统计、聚合、缓存「接缝已留、待建设」 | 不要说「已有缓存大幅降低成本」 |
| 阶段一试点内嵌，阶段二中心化是演进路线 | 不要说「已中心化多租户上线」 |

# 第二部分：目录结构 ↔ 功能对照

先说清楚一件事：仓库里真正叫 **Skill** 的，只有 `.claude/skills/` 下面两个文件夹；但它们产出的文件会写到外面（`*-urls.js`、`domains/train/`）。所以要对照「办手续 / 上岗安检」链路，得看**整个 `ai-monitor-deposer` 目录**，不能只看 Skill 文件夹。

路径根：`docs/简历修改/ai 智能监控/ai-monitor-deposer/`

## 8. 整棵树：四大区

```
ai-monitor-deposer/
│
├── .claude/skills/              ←【区 A】办手续的「作业手册」（Skill）
│   ├── discover-triage-urls/    ← Skill A：挖接口
│   └── onboard-triage-domain/   ← Skill B：生成说明书
│
├── *-urls.js                    ←【区 B】中间产物：接口清单
│   train-urls.js / flight-urls.js / hotel-urls.js / urls.js
│
├── src/plugins/error-triage/    ←【区 C】上岗安检的「引擎」（运行时）
│   ├── server.js / consumer.js  ← 收包入口
│   ├── pipeline.js / router.js / triage.js / llm.js
│   ├── domains/train/           ← 业务说明书（Skill B 生成）
│   └── eval/                    ← 考卷与打分
│
└── docs/ / README.md ...        ←【区 D】给人看的文档（不参与运行）
```

对应两段时间：

| 区 | 对应哪段 | 大白话 |
|---|---|---|
| A Skill | 接入期 | 告诉 Claude「按什么步骤干活」 |
| B urls 清单 | 接入期中间物 | 挖出来的接口表，等人确认 |
| C 引擎 + Domain | 运行期 | 真正每条告警走的服务 |
| D 文档 | 不运行 | 说明书写给人看 |

## 9. 区 A：Skill 目录（真正的「Skill」）

Skill 目录很「瘦」：主要是规程文档 + 一个小脚本，**没有**复杂业务代码。

```
.claude/skills/
├── discover-triage-urls/
│   ├── SKILL.md                 ← 挖接口的完整步骤说明书
│   └── scripts/
│       └── drift-check.sh       ← 检查清单是否过期（零 AI）
│
└── onboard-triage-domain/
    └── SKILL.md                 ← 根据清单生成 Domain 的步骤说明书
```

### 9.1 `discover-triage-urls/SKILL.md` → Skill A

| 文件里写的步骤 | 对应第一部分说的功能 |
|---|---|
| 先探技术栈再套 playbook | 「先看这是前端还是后端，再用不同挖法」 |
| 广召回摘取 | 「尽量多挖接口，宁可多别漏」 |
| 抓业务码证据 `(文件:行)` | 「记下哪些是正常拒绝，并带出处」 |
| 两维打标（归属 × 核心/边缘） | 「自家/外人」+「核心/边缘」 |
| 产出 `<team>-urls.js` | 写出区 B 的清单文件 |
| sync 增量模式 | 「只处理新增接口，省 token」 |

**注意：** 这个目录**自己不存**挖出来的接口；产出写到项目根的 `train-urls.js` 等。

### 9.2 `drift-check.sh` → 维护期哨兵

| 它干什么 | 对应哪句 |
|---|---|
| 对比「代码里的 url」vs「清单里的 url」 | 「清单过期了没有」 |
| 退出码 1 = 有漂移 | 「该不该再跑一次增量同步」 |
| 纯 grep，不调 AI | 「便宜、可挂 CI」 |

它**不是** Skill 的主流程，是 Skill A 的配套小工具。

### 9.3 `onboard-triage-domain/SKILL.md` → Skill B

| 文件里写的步骤 | 对应哪句 |
|---|---|
| 读确认过的 urls 清单 | 吃区 B 的中间物 |
| 生成 `rules.js` | 「url 怎么分类」的路由表 |
| 生成 `prompts/_base.md` + 各类 `.md` | 「给 AI 看的说明书」 |
| 标 `<!-- TODO -->` 等人拍板 | 「草稿，人要确认严重度/正常拒绝码」 |
| **不改** `router.js` / `triage.js` 等 | 「引擎零改动，只加 Domain 文件夹」 |

**注意：** 产出写到 `src/plugins/error-triage/domains/<team>/`，不写在 Skill 目录里。

## 10. 区 B：接口清单（Skill A 的产出）

```
ai-monitor-deposer/
├── train-urls.js     ✅ 已挖完，且已拿去生成 Domain
├── flight-urls.js    ✅ 已挖完，Domain 还没接
├── hotel-urls.js     ✅ 已挖完，Domain 还没接
└── urls.js           范本 / 手工参考清单
```

打开 `train-urls.js` 你会看到它长这样（简化）：

```js
/* ownedPrefixes: ['/esapp/']
 * 主流程链：查询 → 填单 → 下单 → 支付 → 出票 → 退改
 */

// 一、查询（核心）
// 正常拒绝：无票……（依据 xxx.mpx:211）
export const GET_TRANSFER_LIST = '/esapp/railway/train/transferLeftTicket';

// 二、下单（核心）
// 正常拒绝：2023 距发车太近……（依据 make-order/index.mpx:2687）
export const MAKE_ORDER = '...';
```

对应关系：

| 清单里有什么 | 后面谁用 |
|---|---|
| 每条 url + 中文注释 | onboard 生成「涉及哪些接口」 |
| 链路分组（查询/下单/支付…） | onboard 决定有哪些 category |
| 正常拒绝码 + 文件行号 | onboard 写进各分类 Prompt（带证据） |
| ownedPrefixes | 写进 `rules.js` 的归属边界 |

**位置：** 卡在「Skill A 做完」和「Skill B 开始」之间，中间必须**人工确认**。

## 11. 区 C：运行时引擎（上岗安检）

这是每条告警真正经过的地方。再拆成四层：

### 11.1 入口（收包）

```
error-triage/
├── server.js      ← HTTP：POST /triage、/judge、/eval
└── consumer.js    ← Kafka：从消息队列捞告警
```

| 文件 | 对应前面步骤 |
|---|---|
| `server.js` | 「别人用请求把错误塞进来」 |
| `consumer.js` | 「错误先进快递柜，再一条条取」 |
| `/triage` | 判定 + 派发（生产） |
| `/judge` | 只判定不派发（练手/攒答案） |
| `/eval` | 批量考试打分 |

两者最后都调 `pipeline.js` 的 `handleAlarm`（或评测用的 `triage`）。

### 11.2 处理核（安检流水线本体）

```
error-triage/
├── pipeline.js    ← 总编排：判定 → 派发
├── router.js      ← 按 url 贴分类标签
├── triage.js      ← 拼说明书 + 调 AI + 解析答案
└── llm.js         ← 对接公司大模型网关
```

| 文件 | 对应第几步 | 大白话 |
|---|---|---|
| `pipeline.js` | 总指挥 | 串起「判 → 派」；`dispatch` 目前还是打日志 |
| `router.js` | 第 2 步路由 | 读 Domain 的 `rules.js`，url → `query`/`payment`/… |
| `triage.js` | 第 3～4 步 | 拼 `_base`+分类 Prompt，调模型，解析 JSON；失败则保守上报 |
| `llm.js` | 第 4 步里的「打电话给 AI」 | 鉴权、请求体、取返回文本 |

**这些文件不懂火车票业务**——业务知识全在下面的 Domain。

### 11.3 Domain（业务说明书 = Skill B 的产出）

```
domains/train/                    ← 目前只有火车票接好了
├── rules.js                      ← 路由表
└── prompts/
    ├── _base.md                  ← 全局规则（所有分类共用）
    ├── non-core.md               ← 外人接口
    ├── query.md                  ← 查询类
    ├── order.md                  ← 下单类
    ├── payment.md                ← 支付类
    ├── refund-change.md          ← 退改类
    ├── user-auth.md              ← 登录鉴权类
    ├── order-detail.md           ← 订单详情类
    └── display.md                ← 展示/弱业务类
```

| 文件 | 运行时谁读 | 对应哪句 |
|---|---|---|
| `rules.js` 的 `ownedPrefixes` | `router.js` | 「是不是 `/esapp/` 自家」 |
| `rules.js` 的 `rules` 有序列表 | `router.js` | 「LeftTicket → query」 |
| `rules.js` 的 `fallbackKey` | `router.js` | 「没匹配到 → 保守按 order」 |
| `_base.md` | `triage.js` 拼 system | 「信息不足默认上报、正常拒绝不上报…」 |
| `query.md` 等 | `triage.js` 拼 system | 「这一类具体怎么定级」 |
| `non-core.md` | 外人接口分类 | 「三方不背锅，基线很轻」 |

**启动时：** `DOMAIN=train` → `pipeline.js` 加载 `domains/train/`，引擎其他文件不用改。

### 11.4 eval（考卷，不参与生产喊人）

```
eval/
├── datasets/train.jsonl   ← 考题 + 标准答案（gold）
├── run.js                 ← 用真实判定跑一遍（不派发）
├── score.js / score-lib.js← 对比答案打分（漏报/误报等）
└── README.md
```

对应：「改 Prompt 不能靠感觉，要用卷子回归。」

```
业务前端仓库 fe-estrain
        │
        │  人触发 /discover-triage-urls
        │  （读 .claude/skills/discover-triage-urls/SKILL.md）
        ▼

└─────────┬─────────┘

          │  （读 onboard-triage-domain/SKILL.md）
          ▼
┌───────────────────────────────┐
│  domains/train/               │  ← Skill B 写入
│   rules.js + prompts/*.md     │
└─────────┬─────────────────────┘
          │  DOMAIN=train 启动
          │  pipeline 加载 Domain
          ▼
  监控抛来一条错误
          │
   server / consumer 收包
          │

    → drift-check.sh 对比 train-urls.js
    → 有漂移再跑 discover（sync）
    → 必要时再跑 onboard / 手改 rules
```

## 13. 「目录 ↔ 功能」总对照表

| 路径 | 角色 | 对应功能（大白话） |
|---|---|---|
| `.claude/skills/discover-*/SKILL.md` | Skill A 手册 | 怎么从代码挖接口 |
| `.claude/skills/discover-*/scripts/drift-check.sh` | 哨兵 | 清单过期没 |
| `.claude/skills/onboard-*/SKILL.md` | Skill B 手册 | 怎么生成 Domain |
| `train-urls.js` 等 | 中间物 | 挖出来的接口表 |
| `server.js` / `consumer.js` | 入口 | 收告警 |
| `pipeline.js` | 编排 | 判完决定喊不喊 |
| `router.js` | 贴标签 | url → 分类 |
| `triage.js` | 问 AI | 拼说明书 + 解析 |
| `llm.js` | AI 网关适配 | 真正调大模型 |
| `domains/train/rules.js` | 路由配置 | 自家前缀 + 匹配规则 |
| `domains/train/prompts/*` | 判定说明书 | 告诉 AI 怎么判 |
| `eval/*` | 考场 | 验证改 Prompt 有没有改坏 |
| `docs/*` / `README.md` | 文档 | 给人看，不参与运行 |

### 帮你记住的一句话

> **Skill 目录 = 教 Claude 怎么干活的说明书；**  
> **`*-urls.js` = 挖出来的原料表；**  
> **`domains/` = 上岗用的业务配置；**  
> **`router/triage/llm/pipeline` = 真正跑告警的机器。**

Skill 很「轻」（几乎只有 `SKILL.md`），重活体现在它**写出**的那些文件上——所以对照功能时，一定要把产出目录一起看。
