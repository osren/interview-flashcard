# 第一部分：大白话全链路科普

按「办手续 → 上岗安检」理解整套系统。术语尽量换成大白话，中间遇到专业词会随手解释。

---

## 1. 先备一张「词小抄」

后面会反复出现，先混个脸熟：

| 词 | 大白话 |
|---|---|
| **告警** | 系统出错时，自动往群里 / 电话里「喊人」 |
| **值班** | 轮流盯线上问题的人，被喊多了会麻木 |
| **噪音** | 其实不重要、不该喊人的告警（比如「无票」） |
| **降噪** | 把不该喊的滤掉，只留该看的 |
| **接口 / API / url** | 前端请求后端的那个地址，比如 `/esapp/.../queryLeftTicket` |
| **Domain** | 某一业务自己的「说明书文件夹」（路由表 + 判定话术） |
| **Prompt** | 写给大模型看的说明书 / 题干 |
| **LLM / 大模型** | ChatGPT 那类 AI，这里用来「帮人判断」 |
| **路由** | 根据 url，决定这条错误属于哪一类业务（这里不是 Vue Router） |
| **severity / P0–P3** | 严重等级：P0/P1 很急，P3 不太急 |
| **should_report** | 要不要真的喊人：true=报，false=当噪音扔掉 |
| **business_reject** | 「业务正常拒绝」：看起来像报错，其实是正常业务结果（无票、已退改） |
| **Kafka** | 一种「消息队列」，告警可以先进队列再被服务一条条消费（像快递柜） |
| **HTTP API** | 别人用请求调你服务，比如 `POST /triage` |
| **Skill** | Claude Code 里可复用的「标准作业流程」，像自动化小助手 |
| **漏报 FN** | 该喊人却没喊（最危险） |
| **误报 FP** | 不该喊却喊了（吵，但比漏报好） |
| **兜底** | 出意外时的保底策略：搞不定就保守上报，绝不闷声扔掉 |
| **评测 / eval / gold** | 用「标准答案卷子」考模型判得对不对；gold=标准答案 |
| **ownedPrefixes** | 「自家接口」的路径前缀，如火车票 `/esapp/`；不在里头的当外人 |
| **fallbackKey** | 自家域内没匹配到具体规则时的兜底分类，倾向上报 |
| **drift-check** | 检查「代码里的接口」和「清单里登记的」有没有对不上（漂移） |

## 2. 全景：其实就两段时间

把整个系统想成：**先办入驻手续，再上岗安检**。

```
【接入期 · 办手续，偶尔做一次】
扫业务代码 → 列出有哪些接口 → 人确认 → 生成「说明书」→ 启动服务

【运行期 · 上岗，每条错误都走一遍】
监控发现接口报错 → 问 AI 该不该喊人 → 该喊才推送，不该喊就扔掉
```

- **Skill** 主要在「办手续」阶段帮忙
- **引擎（error-triage 服务）** 在「上岗安检」阶段干活
- Skill **不**参与每条告警的实时判定，它负责：怎么把火车票 / 机票业务接进来

一句话定位：

> 这不是「监控系统」，是告警门口的智能安检员——每条接口错误进来，先问大模型「该不该喊人、喊多大声」，噪音挡在外面，真故障才推给值班。

## 3. 运行期：一条错误告警怎么走完（最重要）

用一个具体例子：  
用户查中转余票，接口返回「参数错误」。

### 3.1 第 1 步：收包（有人把错误塞进来）

来源可以是两种（知道有两条入口就行）：

1. **HTTP**：别的系统直接 POST 一条 JSON 过来
2. **Kafka**：错误先丢进消息队列，服务再一条条捞出来（像快递柜，先存后取，高峰不堵死）

收到大概长这样：

```json
{
  "url": "/esapp/railway/train/transferLeftTicket",
  "errorCode": "1",
  "errorMsg": "参数错误"
}
```

- **url**：哪个接口挂了（最关键，后面靠它分类）
- **errorCode / errorMsg**：错误码和错误文案（给 AI 看的材料）
- 字段不全也没关系——搞不清就倾向「还是报一下」，别偷偷放过

两个入口最终都只调同一个 `handleAlarm`，判定逻辑不重复写两套。

### 3.2 第 2 步：路由（先给错误贴标签）

「路由」不是 Vue Router，这里是：**看 url，判断这条错误属于哪一类**。

比如：

- 路径里有支付相关 → 贴「支付」
- 有余票查询 → 贴「查询」
- 不是自己家前缀（比如外部营销域名）→ 贴「非自有 / non-core」

火车票自己家前缀一般是 `/esapp/`：

- **在自家前缀里**：按规则细分类
- **不在**：当外人接口，默认很轻（不太喊人）——「三方挂了别让咱们值班背锅」
- **自家但没匹配到具体规则**：走兜底类（偏保守，倾向上报）——「新接口还没登记，先别漏报」

例子里 `LeftTicket` → 归到「查询」类。

### 3.3 第 3 步：拼 Prompt（把说明书 + 案情交给 AI）

给大模型的内容分两块：

1. **system（说明书）**
   - 全局规则：什么叫该报、什么叫正常拒绝、信息不全怎么办……
   - 本类细则：查询类接口怎么定级、哪些码是正常拒绝……
2. **user（案情）**
   - 就是这条告警的 JSON：哪个 url、啥码、啥文案

你可以把它想成：

> 「你是值班助手。规则如下……  
> 现在有一条：中转余票接口返回参数错误。请判断：报不报？几级？为什么？」

### 3.4 第 4 步：问大模型 + 读答案

- 调公司内部的大模型网关一次（像调一个 AI 接口）
- `temperature=0`：让它尽量稳定，别今天 P1 明天 P2 乱飘
- 要求它回固定 JSON，比如：

```json
{
  "should_report": true,
  "severity": "P1",
  "error_type": "param_validate_failed",
  "reason": "这是下单主流程入口，参数错误也要喊人"
}
```

**万一 AI 挂了 / 超时 / 回的不是合法 JSON？**  
→ 统一保守处理：**还是报，按 P2**。  
原则：降噪服务自己挂了，也不能把真故障闷掉。

### 3.5 第 5 步：派发（真的喊不喊人）

- `should_report = false` → 当噪音扔掉
- `true` → 按严重等级推到群 / 电话 / 工单

（当前代码里真实推送还没接完，先打日志占位——面试别说已经稳定打电话了。）

**为什么余票查询也能是 P1？**  
名字叫「查询」，但它是买票流程第一步；这一步全挂 = 用户买不了票，所以可以很严重。别被「查询」俩字骗了。

**反例：** 如果返回的是「无票」——这是正常业务结果，用户换个车次就行，一般**不该喊值班**。

## 4. 接入期：两个 Skill 干啥（办手续流水线）

把 Skill 想成：**写好的「标准作业手册」**，让 Claude 按步骤帮你干脏活累活。

### 4.1 Skill A：discover（从代码里把接口「挖」出来）

**问题：** 前端项目里接口到处写——有的在 `urls.js`，有的直接写在页面 `axios.post('/xxx')`，新人根本摸不清有哪些。

**Skill A 做的事：**

1. 先看这是啥技术栈（前端 / 小程序 / 后端……），用不同挖法
2. 尽量多挖接口（宁可多，别漏）
3. 顺便记下：这个接口干啥的、哪些错误码其实是「正常拒绝」，并带上「文件:行号」证据
4. 给接口打两个标签：
   - **自家还是外人**（看路径前缀）
   - **核心还是边缘**（挂了用户还能不能走完主流程：搜→下单→支付→出票……）
5. 吐出一份清单文件，比如 `train-urls.js`

**人要做啥：** 看一眼清单，确认「核心链路划得对不对、前缀对不对、死代码别误收」。

它**不**直接生成最终配置，只产「中间表」，坏味道先拦在这。

### 4.2 Skill B：onboard（根据清单生成「说明书文件夹」）

吃掉确认过的清单，生成：

```
domains/train/
├── rules.js     # url 怎么分类（路由表）
└── prompts/     # 各类判定说明书
    ├── _base.md
    ├── query.md
    ├── payment.md
    └── ...
```

- **rules.js**：告诉引擎「这个 url 归哪一类」
- **prompts/*.md**：告诉大模型「这类错误怎么判」

生成的是**草稿**，上线前还要人核对：  
哪些错误码真的是正常拒绝、各级严重度基线对不对。

### 4.3 维护：项目后来又加了新接口怎么办？

有个小脚本叫 **drift-check（漂移检查）**：

- 对比「代码里现在的接口」和「清单里登记的」
- 发现多了 / 少了就报警（可挂到 CI：每次提交自动查）
- 再跑一次 discover 的增量模式：只处理新增那几条，省钱省时间

清单暂时没更新也**不会漏报**：新接口没匹配到规则 → 走兜底，倾向上报。过期只影响「定级准不准」，不影响「会不会丢」。

## 5. 和传统做法比，到底方便在哪

### 5.1 传统常见三种

1. **人盯群**：噪音一多，眼睛花了，真故障漏掉
2. **写死 if-else**：`如果错误码是 2023 就不报`——业务一复杂就写炸，还容易误杀
3. **每个业务改一套代码**：机票一套、酒店一套，引擎被改得越来越脏

### 5.2 这套方案的便利

| 痛点 | 传统 | 现在 |
|---|---|---|
| 接口散落难找 | 人肉翻仓库 | Skill A 帮你广挖 + 带证据 |
| 接新业务慢 | 改服务代码 | 加一个 Domain 文件夹就行 |
| 「正常拒绝」难判 | 硬码表又脆又漏 | 让 AI 看语义 + Prompt 说明书 |
| 调松紧要发版 | 改代码上线 | 改 md 说明书（重启生效） |
| 不知道改好没改坏 | 靠值班吐槽 | 用标准答案卷子打分（尤其盯「漏报」） |
| AI / 服务挂了 | 可能悄悄丢告警 | 搞不定就保守上报 |

**一句话：**  
Skill 让「接业务」从手工作坊变成流水线；引擎让「判告警」从人肉/脆规则变成「说明书 + AI」，同时用兜底保证安全。

## 6. 用前端 intern 视角再串一遍

你熟悉的世界：

> 页面调接口 → 接口返回 errcode/errmsg → 有时弹 toast「无票」

监控世界多一步：

> 同样这些错误，也会被上报到监控 → 可能喊值班

本项目卡在中间：

> 错误要喊人之前，先过一道 AI 安检：  
> 「这是无票这种正常业务，还是真把下单链路搞挂了？」

你作为前端，最相关的点：

- 告警材料往往来自前端 / BFF 的接口错误上报
- Skill 扫的常常是前端仓库里散落的 url
- 以后可能在 BFF 统一调这个判定服务，业务侧接入更轻

## 7. 电梯版（留给面试 / 自己消化）

> 商旅接口一报错就告警，但很多是「无票」这种正常情况，值班被刷屏。  
> 我们在喊人之前，用大模型判断：报不报、多严重。  
> 工程负责收告警、按 url 分类、拼说明书、调 AI；业务知识放在可替换的文件夹里。  
> 两个 Skill 帮我们从代码里挖接口、生成说明书，接新业务不用改引擎。  
> 原则是：宁可多喊一声，也不能漏掉真故障。

### 核心原则（必须记住）

1. **宁可误报，不可误杀**（漏报优先压到接近 0）
2. **判定交给模型，工程只做路由与编排**
3. **引擎领域无关，业务知识全在可插拔 Domain**

### 诚实边界（防面试翻车）

| 可以说 | 不要夸大 |
|---|---|
| 判定链路、火车票 Domain、评测与 Skill 已就绪 | 不要说「已全量覆盖机酒火并显著降噪 X%」 |
| 派发层接口已留，当前为日志占位 | 不要说「已对接电话告警 / 已稳定生产值班」 |
| 频次统计、聚合、缓存「接缝已留、待建设」 | 不要说「已有缓存大幅降低成本」 |
| 阶段一试点内嵌，阶段二中心化是演进路线 | 不要说「已中心化多租户上线」 |

# 第二部分：目录结构 ↔ 功能对照

先说清楚一件事：仓库里真正叫 **Skill** 的，只有 `.claude/skills/` 下面两个文件夹；但它们产出的文件会写到外面（`*-urls.js`、`domains/train/`）。所以要对照「办手续 / 上岗安检」链路，得看**整个 `ai-monitor-deposer` 目录**，不能只看 Skill 文件夹。

路径根：`docs/简历修改/ai 智能监控/ai-monitor-deposer/`

## 8. 整棵树：四大区

```
ai-monitor-deposer/
│
├── .claude/skills/              ←【区 A】办手续的「作业手册」（Skill）
│   ├── discover-triage-urls/    ← Skill A：挖接口
│   └── onboard-triage-domain/   ← Skill B：生成说明书
│
├── *-urls.js                    ←【区 B】中间产物：接口清单
│   train-urls.js / flight-urls.js / hotel-urls.js / urls.js
│
├── src/plugins/error-triage/    ←【区 C】上岗安检的「引擎」（运行时）
│   ├── server.js / consumer.js  ← 收包入口
│   ├── pipeline.js / router.js / triage.js / llm.js
│   ├── domains/train/           ← 业务说明书（Skill B 生成）
│   └── eval/                    ← 考卷与打分
│
└── docs/ / README.md ...        ←【区 D】给人看的文档（不参与运行）
```

对应两段时间：

| 区 | 对应哪段 | 大白话 |
|---|---|---|
| A Skill | 接入期 | 告诉 Claude「按什么步骤干活」 |
| B urls 清单 | 接入期中间物 | 挖出来的接口表，等人确认 |
| C 引擎 + Domain | 运行期 | 真正每条告警走的服务 |
| D 文档 | 不运行 | 说明书写给人看 |

## 9. 区 A：Skill 目录（真正的「Skill」）

Skill 目录很「瘦」：主要是规程文档 + 一个小脚本，**没有**复杂业务代码。

```
.claude/skills/
├── discover-triage-urls/
│   ├── SKILL.md                 ← 挖接口的完整步骤说明书
│   └── scripts/
│       └── drift-check.sh       ← 检查清单是否过期（零 AI）
│
└── onboard-triage-domain/
    └── SKILL.md                 ← 根据清单生成 Domain 的步骤说明书
```

### 9.1 `discover-triage-urls/SKILL.md` → Skill A

| 文件里写的步骤 | 对应第一部分说的功能 |
|---|---|
| 先探技术栈再套 playbook | 「先看这是前端还是后端，再用不同挖法」 |
| 广召回摘取 | 「尽量多挖接口，宁可多别漏」 |
| 抓业务码证据 `(文件:行)` | 「记下哪些是正常拒绝，并带出处」 |
| 两维打标（归属 × 核心/边缘） | 「自家/外人」+「核心/边缘」 |
| 产出 `<team>-urls.js` | 写出区 B 的清单文件 |
| sync 增量模式 | 「只处理新增接口，省 token」 |

**注意：** 这个目录**自己不存**挖出来的接口；产出写到项目根的 `train-urls.js` 等。

### 9.2 `drift-check.sh` → 维护期哨兵

| 它干什么 | 对应哪句 |
|---|---|
| 对比「代码里的 url」vs「清单里的 url」 | 「清单过期了没有」 |
| 退出码 1 = 有漂移 | 「该不该再跑一次增量同步」 |
| 纯 grep，不调 AI | 「便宜、可挂 CI」 |

它**不是** Skill 的主流程，是 Skill A 的配套小工具。

### 9.3 `onboard-triage-domain/SKILL.md` → Skill B

| 文件里写的步骤 | 对应哪句 |
|---|---|
| 读确认过的 urls 清单 | 吃区 B 的中间物 |
| 生成 `rules.js` | 「url 怎么分类」的路由表 |
| 生成 `prompts/_base.md` + 各类 `.md` | 「给 AI 看的说明书」 |
| 标 `<!-- TODO -->` 等人拍板 | 「草稿，人要确认严重度/正常拒绝码」 |
| **不改** `router.js` / `triage.js` 等 | 「引擎零改动，只加 Domain 文件夹」 |

**注意：** 产出写到 `src/plugins/error-triage/domains/<team>/`，不写在 Skill 目录里。

## 10. 区 B：接口清单（Skill A 的产出）

```
ai-monitor-deposer/
├── train-urls.js     ✅ 已挖完，且已拿去生成 Domain
├── flight-urls.js    ✅ 已挖完，Domain 还没接
├── hotel-urls.js     ✅ 已挖完，Domain 还没接
```

## 11. 区 C：运行时引擎（上岗安检）

这是每条告警真正经过的地方。再拆成四层：

### 11.1 入口（收包）

```
error-triage/
├── server.js      ← HTTP：POST /triage、/judge、/eval
└── consumer.js    ← Kafka：从消息队列捞告警
```

| 文件 | 对应前面步骤 |
|---|---|
| `server.js` | 「别人用请求把错误塞进来」 |
| `consumer.js` | 「错误先进快递柜，再一条条取」 |
| `/triage` | 判定 + 派发（生产） |
| `/judge` | 只判定不派发（练手/攒答案） |
| `/eval` | 批量考试打分 |

两者最后都调 `pipeline.js` 的 `handleAlarm`（或评测用的 `triage`）。

### 11.2 处理核（安检流水线本体）

```
error-triage/
├── pipeline.js    ← 总编排：判定 → 派发
├── router.js      ← 按 url 贴分类标签
├── triage.js      ← 拼说明书 + 调 AI + 解析答案
└── llm.js         ← 对接公司大模型网关
```

| 文件 | 对应第几步 | 大白话 |
|---|---|---|
| `pipeline.js` | 总指挥 | 串起「判 → 派」；`dispatch` 目前还是打日志 |
| `router.js` | 第 2 步路由 | 读 Domain 的 `rules.js`，url → `query`/`payment`/… |
| `triage.js` | 第 3～4 步 | 拼 `_base`+分类 Prompt，调模型，解析 JSON；失败则保守上报 |
| `llm.js` | 第 4 步里的「打电话给 AI」 | 鉴权、请求体、取返回文本 |

**这些文件不懂火车票业务**——业务知识全在下面的 Domain。

### 11.3 Domain（业务说明书 = Skill B 的产出）

```
domains/train/                    ← 目前只有火车票接好了
├── rules.js                      ← 路由表
└── prompts/
    ├── _base.md                  ← 全局规则（所有分类共用）
    ├── non-core.md               ← 外人接口
    ├── query.md                  ← 查询类
    ├── order.md                  ← 下单类
    ├── payment.md                ← 支付类
    ├── refund-change.md          ← 退改类
    ├── user-auth.md              ← 登录鉴权类
    ├── order-detail.md           ← 订单详情类
    └── display.md                ← 展示/弱业务类
```

|---|---|---|
| `rules.js` 的 `ownedPrefixes` | `router.js` | 「是不是 `/esapp/` 自家」 |

## 14. Domain 是什么？用一个类比记住

把 **error-triage 引擎**想成一台**通用安检机**：

- 安检机本身（`router.js` / `triage.js` / `llm.js` / `pipeline.js`）**不懂**火车票、机票、酒店
- 每个业务带一本**操作手册**插进机器里 → 这本手册就是 **Domain**
- 换业务 = **换手册（换 Domain 文件夹）**，机器不用改

```
通用引擎（永远不变）          Domain（按业务换）
┌─────────────────┐          ┌──────────────────────┐
│ router  贴标签   │  读取    │ rules.js  路由表      │
│ triage  拼说明书 │ ◀────── │ prompts/  判定话术     │
│ llm     调 AI    │          └──────────────────────┘
└─────────────────┘
        ▲
   DOMAIN=train 决定加载 domains/train/
   DOMAIN=flight 决定加载 domains/flight/（待接）
```

**Domain 在系统里的位置（承上启下）：**

```
Skill A 产出 urls 清单 → Skill B 生成 Domain → 引擎启动时加载 Domain → 每条告警消费 Domain
     （原料）              （配置）              （pipeline.js）           （router + triage）
```

## 15. Domain 的物理构成：就两样东西

一个完整 Domain = **`rules.js` + `prompts/` 文件夹**，不多不少。

```
domains/train/                    ← 一个 Domain = 一个业务线（火车票）
├── rules.js                      ← ① 路由表：url 贴什么标签
└── prompts/
    ├── _base.md                  ← ② 全局说明书（所有分类共用）
    ├── non-core.md               ← ③ 外人/三方接口专用
    ├── query.md                  ← ④ 各业务分类的细则
    ├── order.md
    ├── payment.md
    ├── refund-change.md
    ├── user-auth.md
    ├── order-detail.md
    └── display.md
```

| 组成部分 | 格式 | 谁写 | 谁读 | 一句话职责 |
|---------|------|------|------|-----------|
| `rules.js` | JavaScript | Skill B 生成 + 人工改 | `router.js` | **决定这条告警归哪一类** |
| `prompts/_base.md` | Markdown | Skill B 生成 + 人工改 | `triage.js` | **所有分类共用的判定总则** |
| `prompts/<key>.md` | Markdown | Skill B 生成 + 人工改 | `triage.js` | **某一类的具体定级细则** |
| `prompts/non-core.md` | Markdown | 同上 | `triage.js` | **非自有接口的降噪策略** |

**没有别的了。** Domain 里不放引擎代码、不放 HTTP 逻辑、不放 LLM 网关配置——那些全在引擎层。

## 16. `rules.js`：路由表，给 url 贴标签

### 16.1 导出三个东西

火车票 `rules.js` 固定导出三个字段：

```js
export const fallbackKey = 'order';           // 兜底分类
export const ownedPrefixes = ['/esapp/'];     // 自家接口前缀
export const rules = [                        // 有序匹配规则
  { pattern: 'LeftTicket', key: 'query' },
  { pattern: '/makeOrder', key: 'order' },
  // ...
];
```

| 字段 | 作用 | 大白话 |
|-----|------|--------|
| **`ownedPrefixes`** | 归属边界 | 「`/esapp/` 开头的是咱家的，别的当外人」 |
| **`rules`** | 有序 pattern → key 列表 | 「自家 url 里，谁像谁，就贴哪个标签」 |
| **`fallbackKey`** | 自家但未命中任何 rule 时的兜底 | 「新接口还没登记？先当核心下单类，保守上报」 |

### 16.2 路由三步（引擎 `router.js` 执行）

```
告警 url
  │
  ├─ 1. pathname 归一化（去 host、去 query）
  │
  ├─ 2. 归属判别：不在 ownedPrefixes 内？
  │      └─ 是 → 直接返回 non-core（后面的 rules 救不回来）
  │
  └─ 3. 有序匹配 rules：从第一条扫到最后
         ├─ 命中 → 返回对应 key（如 query / payment）
         └─ 全未命中 → 返回 fallbackKey（如 order）
```

**为什么要「有序」？** 因为 pattern 有宽有窄，**特例必须排在宽松规则前面**，否则会被吞。

真实例子（来自 `rules.js` 注释）：

```js
// 特例必须排在宽松规则之前
{ pattern: '/change/stopTraffic/', key: 'order' },      // 停运核验，先于 /change/
{ pattern: '/estimate/change', key: 'refund-change' },  // 改签预估，先于 /estimate/
// ...
{ pattern: '/change/', key: 'refund-change' },          // 宽松的 /change/ 放后面
{ pattern: '/estimate/', key: 'query' },                // 宽松的 /estimate/ 放后面
```

如果顺序反了：`/estimate/change` 会先被 `/estimate/` 命中成 `query`，改签场景就判错了。

### 16.3 两个「兜底」别搞混

| 兜底 | 触发条件 | 返回 key | 设计意图 |
|-----|---------|---------|---------|
| **归属兜底** | url 不在 `ownedPrefixes` 内 | `non-core` | 三方接口不让值班背锅 |
| **规则兜底** | 在自家前缀内，但 rules 没命中 | `fallbackKey`（如 `order`） | 新接口/清单过期也不漏报 |

清单过期**不会漏报**，只会定级没那么准——这是 Domain 设计里很重要的安全保证。

## 17. `prompts/`：给 AI 看的判定说明书

### 17.1 两类文件：全局 vs 分类

```
prompts/
├── _base.md          ← 「总则」：输出格式、error_type 枚举、全局规则
├── non-core.md       ← 「外人专用」：三方接口降噪策略
└── <key>.md          ← 「分则」：某一类的 severity 基线 + business_reject 清单
    query.md
    order.md
    payment.md
    ...
```

**`<key>` 必须和 `rules.js` 里 rules 的 key 一一对应。**  
router 贴标签 `query` → triage 就读 `query.md`；贴 `non-core` → 读 `non-core.md`。

### 17.2 `_base.md` 管什么（所有分类共用）

`_base.md` 是 **Prompt 的「宪法」**，每条告警都会加载，内容包括：

| 块 | 内容 | 为什么放全局 |
|----|------|------------|
| 角色定义 | 「你是火车票告警降噪判定助手」 | 统一身份 |
| 输出 JSON schema | `should_report` / `severity` / `error_type` / `reason` / `confidence` | 引擎要能解析 |
| `error_type` 枚举 | `business_reject` / `param_validate_failed` / `server_error` / … | 全部分类共用同一套类型 |
| 全局规则 1 | **信息不足 → 默认上报** | 宁可误报不可误杀 |
| 全局规则 2 | **业务正常拒绝 → 降噪** | 总原则 |
| 全局规则 3 | **同指纹高频 → 升级** | count 高要喊人 |
| 全局规则 4 | 只判正式环境 | env 恒 prod |
| 全局规则 5 | severity 看主流程链 | 查询→填单→下单→支付→出票→退改 |

**调「全局松紧」改 `_base.md`**，比如「confidence 低于多少算信息不足」。

### 17.3 分类 `<key>.md` 管什么（某一类专用）

以 `query.md` 为例，它只服务「查询类」接口：

| 块 | 内容 |
|----|------|
| 涉及接口列表 | 哪些 url 属于这一类（从 urls 清单来） |
| severity 基线 | 余票查询异常 → **一律 P1**（名义是查询，实际是下单入口） |
| business_reject | 无票、售罄等 → `should_report=false` |
| 升级/降级条件 | 辅助查询（经停站）基线 P3；阻断下单则升 P1 |

**调「某一类业务的松紧」改对应的 `<key>.md`**，比如「支付类哪些码算正常拒绝」。

### 17.4 `non-core.md` 的特殊地位

`non-core` 不是业务分类，是**归属边界的产物**——url 不在 `/esapp/` 里就自动到这里。

核心策略：

- 基线 **P3**，单点错误默认 **不上报**
- 只有 **同指纹高频** 才升到 P2
- reason 里注明「非自有接口，转对应团队」

这实现了「三方挂了别让火车票值班背锅」。

## 18. 引擎怎么加载和使用 Domain

### 18.1 启动时：pipeline 装配

```js
// pipeline.js（简化理解）
const DOMAIN = process.env.DOMAIN || 'train';          // 环境变量选业务
const domainDir = `domains/${DOMAIN}/`;

// 1. 读 rules.js → 构造 router
const { rules, fallbackKey, ownedPrefixes } = await import(domainDir + 'rules.js');
const route = createRouter(rules, { fallbackKey, ownedPrefixes });

// 2. 读 prompts/ → 构造 triage
const triage = createTriage({
  route,
  promptsDir: domainDir + 'prompts/',
  llm: createGatewayLLM(),
});
```

**换业务只改 `DOMAIN=flight`，引擎代码零改动。**

### 18.2 运行时：每条告警的消费路径

```
alarm.url
    │
    ▼
route(alarm.url)  ──读 rules.js──▶  key = "query"
    │
    ▼
system = _base.md + "\n---\n" + query.md   ← triage.js 拼装
user   = JSON.stringify(alarm)
    │
    ▼
llm({ system, user })  ──▶  JSON 判定结果
    │
    ▼
{ should_report, severity, error_type, reason, _category: "query" }
```

对应 `triage.js` 源码：

```js
const key = route(alarm.url);
const system = `${base}\n\n---\n\n${loadPrompt(key)}`;
const user = `待判定告警：\n${JSON.stringify(alarm, null, 2)}`;
```

**关键点：**

- 每次只加载 **`_base` + 当前 category 的一个 md**，不是全量加载 9 个文件
- Prompt 启动时读入 **内存缓存**（`cache Map`），改 md 后需 **重启服务**
- 每条告警 = **恰好一次 LLM 调用**

## 19. 走读一例：从 url 到 Prompt 到判定

**输入告警：**

```json
{
  "url": "/esapp/railway/train/transferLeftTicket",
  "errorCode": "1",
  "errorMsg": "参数错误",
  "count": 12
}
```

**Step 1 · router 读 `rules.js`：**

| 步骤 | 动作 | 结果 |
|-----|------|------|
| 归一化 | `/esapp/railway/train/transferLeftTicket` | pathname 不变 |
| 归属 | 以 `/esapp/` 开头 | 自家接口 ✓ |
| 匹配 | `LeftTicket` pattern 命中 | **key = `query`** |

**Step 2 · triage 拼 Prompt：**

```
system = _base.md 全文
       + "---"
       + query.md 全文
       （包含「余票查询异常一律 P1，含 param_validate_failed」）

user = 待判定告警：{ url, errorCode, errorMsg, count... }
```

**Step 3 · LLM 输出：**

```json
{
  "should_report": true,
  "severity": "P1",
  "error_type": "param_validate_failed",
  "reason": "transferLeftTicket 属下单主流程入口，参数错误判 P1"
}
```

**如果换成「无票」：** 同一 `query` 分类，但 `query.md` 里写了「预期内空结果 → business_reject，不上报」→ `should_report=false`。

**如果 url 是营销中台：** 归属判别 → `non-core` → 读 `non-core.md` → 基线 P3，单点不上报。

## 20. Domain 和各模块的分工边界

| 问题 | 谁负责 | 不在 Domain 里 |
|-----|--------|--------------|
| url 归哪一类？ | `rules.js` → router | — |
| 这一类怎么定级？ | `prompts/<key>.md` → triage | — |
| 输出格式 / 全局原则？ | `prompts/_base.md` → triage | — |
| 调 LLM 网关？ | `llm.js`（引擎） | ✗ |
| 解析 JSON / 失败兜底？ | `triage.js`（引擎） | ✗ |
| 报还是不报之后推送到哪？ | `pipeline.js` 的 `dispatch`（引擎） | ✗ |
| 从代码挖接口？ | Skill A | ✗ |
| 生成 Domain 草稿？ | Skill B | ✗ |

**面试一句话：** Domain 只管「**贴什么标签**」和「**这个标签下怎么判**」；收包、调模型、解析、派发全是引擎的事。

---

## 21. 怎么新增 / 维护一个 Domain

### 21.1 新业务首次接入（如机票 flight）

```
1. discover-triage-urls  →  flight-urls.js（挖接口 + 证据）
2. 人工确认              →  主流程链、ownedPrefixes、正常拒绝码
3. onboard-triage-domain →  domains/flight/{rules.js, prompts/}
4. 人工回源核验          →  business_reject 码逐条对源码
5. DOMAIN=flight 启动    →  跑 /judge / /eval 验证
```

### 21.2 日常维护（项目加了新接口）

| 场景 | 改什么 | 要不要重跑 onboard |
|-----|--------|-------------------|
| 新接口落在已有 category | 在 `rules.js` 补一条 pattern | 通常不用 |
| 新接口属于全新 category | 补 rule + 新建 `<key>.md` | 建议跑 onboard |
| 调整 severity 基线 | 改对应 `<key>.md` 或 `_base.md` | 不用 |
| 新增 business_reject 码 | 改对应 `<key>.md` | 不用 |
| 清单和代码对不上 | 先 `drift-check.sh`，再 discover sync | 视情况 |

**改完 Prompt 必须重启服务**（启动时缓存进内存）。

### 21.3 调松紧速查表

| 想调什么 | 改 Domain 哪里 | 举例 |
|---------|---------------|------|
| 三方接口默认报不报 | `non-core.md` | 营销中台单点降噪 |
| 余票查询要不要 P1 | `query.md` | 「查询入口阻塞下单」 |
| 全局「信息不足」策略 | `_base.md` | confidence 阈值 |
| 新接口没进清单会不会漏 | `rules.js` 的 `fallbackKey` | 兜底到 order |
| 哪些 url 算自家 | `rules.js` 的 `ownedPrefixes` | `/esapp/` 边界 |
| 只派发 P0/P1 | **不在 Domain**，改 `pipeline.js` dispatch | severity 闸门 |

## 22. Domain 设计背后的三个「为什么」

### 22.1 为什么 rules 和 prompts 要分开？

| 如果合在一起 | 分开的好处 |
|------------|-----------|
| 改定级话术也要动路由逻辑 | **路由（工程）** 和 **判定（语义）** 解耦 |
| 一个文件几千行难维护 | rules.js 管「贴标签」，md 管「怎么判」 |
| 引擎难以缓存 Prompt | triage 按 key 按需加载，Token 更省 |

### 22.2 为什么用 md 而不是写在代码里？

- **调松紧 = 改文档**，不需要改引擎、不需要发版引擎代码
- 业务同学 / 值班同学也能 review Prompt  diff
- onboard Skill 可以半自动生成，人只改 `-- TODO --` 部分
- eval 回归可以直接对比「改 md 前后」的指标变化

### 22.3 为什么每个业务一个 Domain 文件夹？

- **引擎领域无关**：`router.js` / `triage.js` 永远不改
- **团队自治**：机酒火各维护各的 Domain，互不污染
- **渐进接入**：火车票已接、机票清单已挖，hotel/flight Domain 待 onboard 不影响 train 运行
- **阶段二中心化**：未来 Domain 可以整体搬到配置中心，形态不变

## 23. Domain 相关的面试口述模板

**30 秒版：**

> Domain 就是某一业务的「路由表 + 判定说明书」。`rules.js` 根据 url 贴分类标签，`prompts/` 告诉 AI 这个分类怎么定级。引擎启动时用 `DOMAIN` 环境变量加载对应文件夹，换业务只换 Domain，不改引擎。火车票 Domain 已接入并回源核验，机票酒店清单已摘、Domain 待 onboard。

**追问「rules 和 prompts 怎么配合」：**

> router 先读 rules.js 把 url 映射成 key，比如 `LeftTicket` → `query`；triage 再拼 `_base.md + query.md` 作为 system prompt，加上告警 JSON 调 LLM。rules 解决「找哪本细则」，prompts 解决「细则怎么写」。

**追问「清单过期会漏报吗」：**

> 不会。自家前缀内 rules 没命中走 fallbackKey 保守上报；非自有走 non-core。清单过期只影响 severity 精度，不影响 should_report 的召回。
