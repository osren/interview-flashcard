# 商旅 AI 告警智能降噪判定服务：面试讲解与问答

> 依据简历 PDF 与 `ai-monitor-deposer` 当前代码/文档交叉整理。请特别留意简历与实现材料不一致处，并按实际参与度调整个人贡献。

## 30 秒项目介绍

商旅接口告警里有大量正常业务拒绝，例如无票、已退改、重复提交，容易让真实故障被噪音淹没。这个项目是在告警派发前做智能判定：接收告警，根据 URL 归一化并路由到业务 Domain，组合公共 Prompt 和类别 Prompt，调用 LLM 输出是否上报、严重级别、错误类型、原因和置信度。架构采用通用引擎加可插拔 Domain；模型超时或结果无法解析时保守上报 P2，避免降噪链路吞掉告警。项目还设计 judge/eval 和本地回归评测，以漏报为重点调优 Prompt。当前材料显示 train Domain 已接入，flight/hotel 仍是接口清单；真实派发还是日志占位，因此不能说已经全量生产降噪。

## 项目完整讲解

### 业务问题与目标

商旅接口错误中，业务正常拒绝和技术故障都会产生告警。无票、订单状态不允许退改、支付超时后重复操作等，有些是预期业务结果；若都按技术故障升级，值班会被噪音淹没。相反，过滤规则太激进又可能吞掉真正故障。

目标是在派发前判断：`should_report`（是否值得上报）、`severity`（P0-P3）、`error_type`、判定 `reason` 与 `confidence`。核心取舍是宁可误报不可误杀：误报增加值班噪音，漏报可能让主链路故障无人处理。

### 架构与数据流

```text
HTTP POST /triage ─┐
                   ├→ handleAlarm → URL 路由 → Domain Prompt → LLM → 兜底 → dispatch
Kafka consumer ────┘
```

- **入口**：`server.js` 提供 HTTP；`consumer.js` 消费 Kafka。两者复用 `handleAlarm`，避免判定逻辑分叉。
- **Router**：`router.js` 将 URL 归一成 pathname，剥离 host/query；可用 `ownedPrefixes` 判断接口归属，再按有序规则匹配 category。自有接口未命中规则时进入 fallback。
- **判定编排**：`triage.js` 选择类别 Prompt，将公共 `_base.md` 与类别 Prompt 拼起来，调用一次 LLM。
- **模型适配**：`llm.js` 封装 LLM Gateway，具体网关接入细节不侵入业务判定。
- **业务配置**：`domains/<team>/` 中保存路由和 prompts。新团队原则上增加配置，不修改通用引擎。
- **派发**：`should_report=true` 才进入 dispatch。当前代码只是 `console.log` 占位，尚未连接真实 IM/电话/工单。

一条告警从 HTTP 或 Kafka 进入后，经过 `handleAlarm()` 调用 `triage(alarm)`；Router 按 pathname 得到 category；程序读取公共与类别 Prompt（启动时缓存），把告警 JSON 作为输入发给模型；解析结果并补 `_category`；异常或格式不合法则生成保守 P2 上报结果；最后交给 dispatch。评测路径调用只判定函数，不应该触发真实派发。

### Domain：通用引擎与业务知识分离

- `rules.js`：URL 到 category 的有序规则、`fallbackKey`、可选 `ownedPrefixes`。
- `prompts/_base.md`：共用输出 schema、错误类型枚举和全局安全规则。
- `prompts/<category>.md`：业务语义、正常拒绝场景、严重度基线和升级条件。
- `prompts/non-core.md`：非自有或三方接口判定策略。

引擎只做接入、路由、Prompt 组合、模型调用和兜底。新增业务的主要成本是确认业务真值和编写/验证类别 Prompt。**URL 路由到类别不等于路由表直接决定最终 severity**；severity 是 Prompt 提供依据后由 LLM 返回。

Router 先用完整 URL 解析 pathname，失败时对相对路径剥离 query。这样 token、签名等参数不会影响路由。若配置 `ownedPrefixes`，不属于自有前缀的路径进入 `non-core`；自有路径按顺序匹配，特例应置于宽泛规则之前；未命中走 fallback，避免新接口完全失去判定策略。当前实现支持字符串包含和正则；带 `g`/`y` 标志的正则有 `lastIndex` 状态问题，配置时应避免或显式处理。

### Prompt 判定与安全兜底

Prompt 告诉模型类别背景、错误类型、已确认的正常拒绝、等级基线、频次升级条件和信息不足时的策略。`errorCode` 可支持匹配业务拒绝清单，`count` 可支持高频升级；上游缺少这些字段时，对应规则就无法可靠生效。Prompt 在服务启动时读入缓存，修改后需重启。

LLM 超时、网关报错、输出无法解析或结构不符合最低要求时，fallback 为 `should_report=true`、`severity=P2`、`error_type=unknown`。这条原则避免降噪服务故障导致告警被静默丢弃。注意当前解析校验是基础版，代码检查 `should_report` 为布尔值且 `severity` 存在；不应夸大为完整 JSON Schema/枚举校验。Kafka 的位移与异常处理目标是避免失败消息无限重投，但当前材料不足以证明重试、死信、持久化等端到端治理都已完善。

### Eval 闭环：为什么重点看 FN

`eval/` 把 Prompt 调优变成可回归流程：真实告警归一并按指纹去重成 case；人工确认 gold；切分 train/holdout 并冻结数据；`run.js` 用真实 triage 路径调用模型但不派发；`score.js` 对比 gold，输出 FN、误报、severity、error_type 和失败清单；针对失败归因修改 Prompt，再在同数据集重跑。

FN（False Negative）是真故障应上报却被判为不报。项目优先压 FN，因为这是告警降噪的主要安全风险。不能只看 accuracy：正常业务拒绝占比高时，“全部不报”也可能得到表面不错的准确率，却漏掉所有真故障。train 用来调，holdout 用来发现过拟合；冻结数据集确保不同 Prompt 版本可比。

文档描述 `/judge` 做单条 case 判定，`/eval` 批量判定并对 gold 打分；本地 `run.js`/`score.js` 也承担评测。面试前要核实两个 HTTP endpoint 在当前分支是否都已实现并运行，不能把设计文档自动等同于已部署 API。

### 接入工具链和当前状态

仓库描述了 `discover-triage-urls` 探针与 `onboard-triage-domain` 生成器：先发现接口并整理清单，人工核对核心链路、归属、动态路径和死代码，再生成 Domain 的路由与 Prompt 草稿，最后回源码核实业务错误码和规则。drift-check 可发现接口变化，增量处理比每次重扫全量更经济。

简历写“以 api/ 目录及 axios 实例声明为线索做 AST 扫描”；仓库探针说明还包括按技术栈选择来源、grep/源码探索和人工确认。需要区分个人实际实现与通用探针能力，说明 AST 能覆盖什么、动态拼接和共享组件调用可能漏什么。

当前材料给出的进度：train Domain 已接入；flight/hotel 清单已摘取但 Domain 待接入；真实派发仍是日志占位；没有线上降噪百分比。应按此边界讲项目，不宣称已全量上线。

## 约 2 分钟口述稿

这个项目要解决商旅接口告警里的正常业务拒绝很多，比如无票、已退改和重复提交，真正的服务故障容易被噪音淹没。我参与的重点是把智能判定链路工程化，同时控制漏报风险。

服务有 HTTP 和 Kafka 两种入口，但都复用同一个 handleAlarm。引擎先把 URL 归一成 pathname，根据 Domain 的有序规则路由到业务类别，再组合公共 Prompt 和类别 Prompt 调用 LLM。模型输出是否上报、P0 到 P3 等级、错误类型、原因和置信度。通用引擎不写死团队业务规则，新团队通过 domains 下的路由和 Prompt 配置接入。

安全策略是模型不可用、超时或返回格式无法解析时保守上报 P2；信息不足也不应轻易过滤。为了调 Prompt 不靠感觉，项目有 judge/eval 路径和离线数据集，按 gold 对比，并优先关注 FN，也就是把真故障错误过滤掉。当前 train Domain 已接入，机酒还在清单阶段，真实派发目前是日志占位，所以我会把它描述为判定服务和评测链路建设阶段，不声称已经全量生产降噪。

## 面试问题与参考回答

### Q1：为什么用 LLM，而不是纯规则？

**答：** 业务拒绝语义依赖接口类别、错误码、错误文案、订单状态和频次等上下文，纯规则会不断膨胀，也难维护跨业务差异。LLM 可结合 Prompt 业务知识判断；代价是不确定性，因此要有结构化输出约束、失败兜底、gold 数据和回归评测。稳定的 URL 路由仍用代码规则。

### Q2：每条告警一次调用，成本和延迟怎么办？

**答：** 当前每条一次，先验证判定质量；指纹去重、缓存和聚合是后续方向。需结合 QPS、token、延迟和并发评估。相同指纹缓存也要考虑告警上下文、count、时间窗和 Prompt 版本，不能无条件复用。当前没有已上线降本数据。

### Q3：模型超时为什么固定 P2 上报？

**答：** 模型失败时缺少证据把告警判为噪音，丢弃可能漏掉真故障，所以保守设置 `should_report=true`。P2 是兜底等级，不代表模型给出了可靠分类。接真实通道前仍需业务确认 P2 是否符合值班策略。

### Q4：怎样保证 LLM 输出 JSON 可用？

**答：** Prompt 约束 schema，解析器尝试提取 JSON 并检查最低必需字段；解析失败就 fallback，不把原始文本送去派发。生产上还应校验 severity/error_type 枚举、字段范围并统计解析失败率。当前代码校验较基础，不是完整 JSON Schema 校验。

### Q5：`should_report` 和 severity 有什么区别？

**答：** `should_report` 决定是否进入派发，severity 表示需要上报时的紧急程度。降噪不等于直接过滤低级别。当前 dispatch 只按 should_report 决定是否打印日志；P 级到不同真实通道的映射还未接入。

### Q6：简历写“Severity 路由”，代码里实际是什么？

**答：** 需要澄清：Router 把 URL 路由到业务 category，Prompt 给出等级判断依据，LLM 返回最终 severity。不是静态 `severity[routes[url]]='P1'` 映射，也没有由该路由直接触发真实告警通道。简历建议改成“URL 分类路由 + Prompt 驱动的等级判定”。

### Q7：如何定义和降低漏报？

**答：** gold 标记哪些 case 应上报；模型判不报而 gold 要报就是 FN。冻结数据集，按 train/holdout 分开，先分析 FN，再处理误报和等级偏差。还要保证真故障正例充足，并按业务类别、错误类型和频次切片，避免总体指标掩盖局部漏报。

### Q8：为什么不能只看 accuracy？

**答：** 正常拒绝可能占多数，“全部不报”也能获得不错 accuracy，但会漏掉全部真故障。因此至少单独看 FN/漏报率、误报率、召回以及不同 severity/category 的表现，并结合业务代价设定策略。

### Q9：Prompt 调优怎样避免过拟合？

**答：** 调优期间冻结数据；train 用于分析失败和改 Prompt，holdout 独立验证。固定模型、Prompt 和数据版本留报告快照。train 提升而 holdout 下降可能过拟合，应回退或补充代表样本。最终评测尽量用生产模型。

### Q10：URL 为什么先去掉 query？

**答：** Query 常带 token、签名或动态参数，不适合接口分类；去掉后路径更稳定。规则按顺序匹配，特例放前；未命中走 fallback，避免新接口失去判定策略。

### Q11：`ownedPrefixes` 和 `non-core` 有什么用？

**答：** 区分自有接口与其他业务/三方接口。非自有路径走 non-core Prompt，避免把自有业务的高严重度基线套到不掌控的接口。前缀要审核准确，否则会造成误分类。

### Q12：为什么支持 HTTP 和 Kafka？

**答：** HTTP 便于单条同步调用、调试和 judge；Kafka 适合异步告警流并能通过并发参数控制处理量。两者复用 `handleAlarm` 避免核心行为分叉。Kafka 仍要关注幂等、位移、重试和死信；不能据现有材料宣称完整生产治理已就绪。

### Q13：为什么拆 `_base.md` 和类别 Prompt？

**答：** schema、错误类型和全局保守规则放公共文件；业务类别规则放各自文件。新团队可复用公共规则，业务知识也不进引擎代码。需检查公共和类别规则不冲突，并确保路由 key 与文件名一致。

### Q14：`/judge` 和 `/eval` 有何区别？

**答：** `/judge` 单条判定便于复现；`/eval` 批量判定并与 gold 打分。评测必须走只判定路径，不能触发真实派发。需确认当前版本两条 HTTP API 是否都真实实现；本地 run/score 脚本是另一条明确的评测路径。

### Q15：接口清单怎么发现，AST 扫描解决什么？

**答：** 简历描述从 api 目录和 axios 实例声明做 AST 扫描来提取 URL，减少人工维护。仓库通用探针说明还组合按技术栈选取的接口源、grep/源码探索和人工确认。回答时要区分个人实现与通用能力，并说明动态 URL、封装请求函数、死代码和共享组件调用可能漏检。

### Q16：当前做到什么程度？

**答：** 仓库材料显示通用 HTTP/Kafka 引擎和 train Domain 已接入；flight/hotel URL 清单已整理，Domain 待接入；dispatch 仍打印日志，没有真实 IM/电话/工单通道。没有线上降噪百分比，不能称全量生产覆盖。

### Q17：最有挑战的业务对齐是什么？

**答：** 模型会混淆正常拒绝和技术故障，尤其同一错误码在不同订单状态下含义不同。需回到源码、错误码和状态枚举确认真值，把规则写入 Prompt，再给真实 case 标 gold、跑回归。只要求模型“再想想”解决不了业务事实缺失。

### Q18：新团队怎么接入？

**答：** 发现接口并整理清单；人工确认核心链路、自有前缀和动态路径；生成 Domain 路由与 Prompt 草稿；回源码核验错误码和等级基线；建 gold 数据并评测；通过后再部署。生成配置不等于判定质量已验证。

### Q19：主要风险和下一步是什么？

**答：** 风险包括 Prompt 与业务事实不符、清单漂移、模型延迟/成本、格式异常和误过滤。先完善 schema 校验、超时限流、指标审计和真实派发前的故障策略；补齐机酒 Domain 与代表性评测集；之后才依据流量评估缓存和告警聚合。全过程以 FN 安全边界为先。
