## 1. 你是数据科学与大数据技术本科跨考到计算机技术硕士，为什么选择跨考？本科的数据科学背景对你做前端有什么实际帮助？

## 答案

**跨考动机**：本科做数据分析、可视化类项目时，我发现「数据算出来」和「用户真正用起来」之间差的是交互与工程化——报表再准，加载慢、路径绕、移动端体验差，业务价值就打折。后来在课程和竞赛里系统写了 Web 前端，发现自己更享受把复杂信息做成可感知、可操作的界面，于是考研转到计算机技术，把方向定在前端工程。

**对前端的帮助**（结合实习，可举例）：

1. **指标与口径**：性能监控里强调先定义基线、按分位（P75/P95）看 LCP/接口耗时，而不是只看均值——这和做数据分析时的分布思维一致。
2. **归因习惯**：列表页把耗时拆成 `fetch / render / paint` 三桶，本质是「维度拆解 + 对照实验」，和做特征分析、漏斗分析是同一套方法论。
3. **告警降噪评测**：以漏报率 FN 为核心指标，本质是在极度不平衡样本（噪音远多于真故障）下选业务代价最小的决策边界，和数据科学里「代价敏感分类」一致。

**面试表达**：跨考不是「跟风计算机」，而是把「数据洞察 + 工程交付」合成一条能力线；前端是我选择的交付界面，不是放弃数据背景。

## 2. 你说数据背景有帮助，那你做滴滴性能监控时，是怎么用数据思维来设计监控指标体系的？

## 答案

**诚实边界**：商旅侧 Omega 上已有 FCP/LCP、业务埋点等大盘；我主要负责 **采集层（perf-monitor）+ 关键页面优化 + 口径修正**，不是从零设计公司级指标体系。数据思维体现在我参与的部分：

| 环节 | 做法 |
|------|------|
| 定义问题 | 用户说「慢」，先区分是 **网络、渲染还是计算**；没有函数级/接口级数据时不盲目改代码 |
| 分层指标 | 跨页链路（home→list）、同页 Vitals（LCP/FCP）、接口维度（getHomeData 等）三层对齐 |
| 口径一致 | 修正「重渲染误计入接口耗时」；缓存命中与真实请求分路径上报 |
| 验收 | 本地 DevTools → 灰度 → Omega 看板对比；1160ms、卡顿 ↓27% 均来自线上统计 |

**可补充**：看板对比时更关注 **发布前后同版本用户分位** 和 **关键路径子指标**（如 list_fetch_ms vs list_render_ms），避免被全局均值掩盖回归。

## 3. 在你们搭建 perf-monitor 之前，团队是怎么做性能监控的？只有 Lighthouse 吗？Lighthouse 的局限是什么？

## 答案

**之前状态**（备战指南口径）：有 **Omega 等平台级埋点** 和宏观 Web Vitals（FCP/LCP 等），但 **缺少运行时、函数级、接口级的细粒度数据**；排查常依赖 DevTools Performance 和个人经验，难以在 H5/星河双端统一对比。

**Lighthouse 局限**（实验室 vs RUM）：

- **环境**：本地/CI 模拟，弱网、真机 WebView、小程序运行时与线上不一致。
- **粒度**：到资源、主线程长任务层级，难对应到 **具体业务函数、具体接口、切日期缓存** 等业务逻辑。
- **频率**：不能代表真实用户分布（P95 慢用户、特定机型）。

**我们补的能力**：RUM 向的 `mark / measure / report` + 双端 Adapter + 关键接口包装耗时，形成「线上可连续观测 + 可定位到代码路径」的抓手，与 Skill 静态分析形成双轨。

## 4. 函数级性能数据的采集方案是什么？手动埋点还是自动化？如何尽量不侵入业务？

## 答案

**方案**：以 **手动/半手动埋点为主**（在关键路径打 mark、对接口做 wrap），不是全量 AST 自动插桩——商旅仓体量大，全量自动化成本高、回归风险大。

**实现要点**（`perf-monitor.js`）：

- **三段式 API**：`mark(label)` → `measure(from, to)` → `report()`，业务在列表加载、切日期、菜单切换等节点显式调用。
- **接口维度**：`wrapApiCall(apiName, fn)` 统一包一层计时与错误计数，减少每个 axios 调用重复写逻辑。
- **Vit als**：H5 用 `PerformanceObserver` 订阅 `paint`、`largest-contentful-paint` 等；星河走 `wx.getPerformance` 或等价能力，经 Adapter 输出 **统一 schema**。

**侵入性控制**：监控模块单文件引入；上报异步、批量；不在热路径做重计算。粒度是「关键函数/关键接口」，而非每个函数——在 **定位成本 vs 性能开销** 之间取平衡。

## 5. PerformanceObserver 能监听哪些 entryType？你实际用到了哪几种？longtask 的触发阈值是多少？为什么是 50ms？

## 答案

**常见 entryType**（H5）：`navigation`、`resource`、`paint`、`largest-contentful-paint`、`layout-shift`、`longtask`、`element`（部分浏览器）、`mark`/`measure`（通过 PerformanceTimeline）。

**项目实际**：以 **`paint`（FCP）**、**`largest-contentful-paint`（LCP）** 为主；接口耗时主要靠 **自定义 mark/measure**，而非依赖 longtask 反推。若做交互卡顿分析，会订阅 **`longtask`**。

**longtask**：主线程连续占用 **≥ 50ms** 记一条。依据 **RAIL 模型**：50ms 内完成响应用户感觉流畅；超过则可能掉帧（60fps 下约一帧 16.7ms，50ms 已明显可感知卡顿）。

## 6. H5 的 PerformanceObserver 与星河 wx.getPerformance 的差异体现在哪些维度？

## 答案

| 维度 | H5 | 星河小程序 |
|------|-----|------------|
| API 形态 | 标准 W3C Performance + Observer | 小程序性能 API，字段与能力子集不同 |
| 指标覆盖 | LCP/FCP/CLS 等较完整 | 部分 Web Vitals 无直接等价，需自定义打点 |
| 触发时机 | 与浏览器渲染管道一致 | 与小程序 setData、页面栈生命周期绑定 |
| 跨页链路 | navigation、SPA 路由 | 小程序页面跳转、组件化差异 |

**Adapter 职责**：统一 **时间单位（ms）**、统一 **上报字段名**（如 `lcp_ms`、`api_getHomeData_ms`）、统一 **环境 tag（h5/xinghe）**；对拿不到的标准指标填 `null` 或降级指标，并在看板注明 **不可跨端直接比绝对值，可比趋势与相对优化幅度**。

## 7. 如果小程序端只能拿到粗粒度数据，怎么保证双端上报可对比？

## 答案

1. **语义对齐，数值分级**：双端上报同一套 **事件名与维度**（如 `list_load_complete`），小程序缺 LCP 则用「首屏数据 ready 时间」等 **业务等价点** 自定义 measure，看板标注为 proxy 指标。
2. **分析层分端看**：Omega 按 `env` 分面，对比「优化前后同端 delta」，避免 H5 1160ms 与小程序某粗指标硬比绝对值。
3. **自定义打点补齐**：在两端相同业务节点（请求开始/结束、setData 前后）打 mark，保证 **fetch/render 拆分** 可对比。
4. **风险意识**：明确告知产品/leader 哪些指标仅 H5 可信；小程序以 **交互耗时、接口 P95** 为主决策依据。

## 8. 商旅场景下 SEO 和 TTI 相对 LCP 的优先级怎么判断？列表页对 SEO 依赖多大？

## 答案

**商旅实际**：大量流量在 **App 内 WebView、企业 SSO、小程序**，列表页多为 **登录后预订链路**，**SEO 权重低**；优先级一般是 **核心转化路径体验（LCP + 首屏可订）> 交互就绪（TTI/INP）> SEO**。

**简历表述修正**：「平衡 LCP 与 SEO/TTI」是通用方法论；在商旅应说成 **「首屏可见与可订优先，非关键 JS/隐私弹窗延后，且不阻塞下单主按钮可用」**。

**判断框架**：是否被搜索引擎直接收录、是否承载营销落地页——否，则 SEO 让位于 LCP；若是外投 H5 落地页，再单独做 SSR/预渲染与 meta，不与内嵌列表页混为一谈。

## 9. LCP 优化与 TTI 冲突（例如延后非关键 JS）时怎么取舍？

## 答案

**原则**：**用户第一眼看到的内容 + 核心交互** 优先于完整 TTI。

**商旅列表具体**：

- `privacyPopList` 等非首屏逻辑 **defer**，缩短 LCP 窗口内主线程占用；首屏列表与日期切换依赖的 JS **保留在关键路径**。
- 若延后某脚本导致「下单/选日期」按钮长时间不可点，则该脚本 **不能 defer**，应改为 **拆包、缓存、减体积** 而非简单推迟。

**决策过程**：PerfMonitor 看 LCP 改善同时监控 **首屏可交互时间** 与 **错误率**；灰度若 INP/点击延迟上升则回滚 defer 范围。用 **一条具体例子**（privacyPopList 延后 + getHomeData 保持同步）说明取舍，比抽象讨论更有说服力。

## 10. perf-monitor.js 是单例还是多实例？多页面/组件同时使用如何避免冲突？

## 答案

**设计**：**全局单例收集器** + **命名空间化的 mark/measure 名**（如 `list_${date}_fetch_start`），避免多实例重复注册 Observer。

**防冲突**：

- mark 名称带 **页面/场景前缀**，防止不同页面 measure 同名串线。
- `report()` 前 **聚合当前页面批次**，上报后 `clearMarks`（或等价清理），避免 Performance 条目无限增长。
- 跨页链路用 **session 级 correlation id**（如从 home 跳转 list 时写入 storage，list 上报时带上）。

**组件级**：组件不各自 new Monitor，只调共享 API；高频组件用 **节流上报**，防止刷屏。

## 11. 上报如何保证不阻塞主线程？sendBeacon 还是 fetch？

## 答案

**策略分场景**：

| 场景 | 方式 |
|------|------|
| 页面卸载、跳转 | `navigator.sendBeacon`（或 `fetch(..., { keepalive: true })`） |
| 运行中批量上报 | 微任务/宏任务异步；可用 `requestIdleCallback` 在空闲发送 |
| 小程序 | 平台埋点 SDK 异步队列 |

**为何不用同步 XHR**：阻塞主线程，恶化 LCP/INP。

**sendBeacon 注意**：payload 约 **64KB** 上限；超大包需采样或拆分。失败时 **降级本地 queue + 下次启动补发**（若业务允许）。

## 12. cacheHit → skipFetch → directRender 为什么用状态机？状态与转移？

## 答案

**为何不用裸 if-else**：切日期存在 **idle / fetching / cacheHit / error / stale** 等多种组合，if-else 易出现 **隐式状态**（例如 fetching 时又切日期导致旧响应覆盖）。状态机让 **当前状态显式、转移可单测、扩展新状态不破坏旧逻辑**。

**简化状态（4+1）**：

```
idle --(选日期,无缓存)--> fetching --(成功)--> rendered
idle --(选日期,有缓存)--> cacheHit --(directRender)--> rendered
fetching --(失败)--> error
任意 --(用户改日期)--> 取消/忽略过期请求 --> idle 或 fetching
```

**收益**：缓存命中 **跳过网络**，Perf 数据上 `fetch` 桶为 0、`render` 桶主导，与优化目标一致；埋点也能区分 **cache 路径 vs network 路径**。

## 13. 缓存是内存还是持久化？刷新后失效怎么办？

## 答案

**列表按日期缓存**：以 **内存 Map（或页面级 store）** 为主， keyed by `date`，满足 **同会话内来回切日期** 的场景——这是 LCP 优化里收益最大的路径。

**刷新后**：内存清空，**正常走 network**，不强行持久化大列表（存储成本与 stale 风险高）。

**若需增强**：可对 **最近 N 个日期** 用 sessionStorage 存轻量摘要（非全量列表），或 **SWR**：先渲染 stale 缓存同时后台 revalidate。过期策略：**TTL（如 5–10 分钟）** 或 **版本号/业务事件失效**（如下单成功后 invalidate）。

## 14. 快速来回切日期，缓存会不会渲染旧日期？如何防竞态？

## 答案

**会，若不做请求序控制**。防护组合拳：

1. **请求代数**：每次日期变更 `requestId++`，响应落地前校验 `requestId === latest`。
2. **AbortController**：新日期发起请求时 abort 旧 fetch（若运行时支持）。
3. **状态机**：`fetching` 状态下仅 **最新 date** 的响应允许进入 `rendered`。
4. **UI 层**：loading 与当前选中 date 绑定，避免闪旧数据。

这是典型 **异步竞态** 题，答出 **序号/取消/校验** 任两种即可体现工程经验。

## 15. 「重渲染耗时误计入接口耗时」怎么发生的？埋点还是定义问题？

## 答案

**根因**：`measure` 的 **起止 mark 划界错误**——例如从 `fetchStart` 一直量到 `renderEnd`，把 **等待 JSON + setData/重渲染** 全算进「接口耗时」，导致误以为要优化后端或 CDN，实际瓶颈在 **前端渲染或重复请求**。

**修正**：在 **fetch 结束**、**render 开始/结束** 分别打 mark，上报 **fetch / render / paint** 三桶；切日期场景 **cache 路径单独标记**，不再调用 fetch 计时。

**结论**：既是 **埋点位置问题**，也反映 **指标定义未与业务语义对齐**——「接口耗时」应仅覆盖网络+解析，不含 Vue/MPX 更新 DOM 的时间。

## 16. Performance API 中 mark 和 measure 的区别？忘记 end mark 会怎样？

## 答案

- **mark**：在时间轴上打 **命名时间点**（`performance.mark('a')`）。
- **measure**：计算 **两个 mark 之间 duration**（`performance.measure('x', 'a', 'b')`），也可指定起止为 navigation 等。

**缺 end mark**：`measure` 可能 **抛异常或得不到有效 duration**；DevTools 中显示不完整。生产代码应在 `try/finally` 中保证成对 mark，或在失败分支打 `abort` mark 避免悬挂。

## 17. 如何定位到 privacyPopList 拖长 LCP？用什么工具？

## 答案

**双轨定位**：

1. **PerfMonitor + 接口埋点**：首屏并行请求中，`privacyPopList` 与 `getHomeData` 串行或占 LCP 窗口；按耗时排序发现 **非关键接口排在关键路径**。
2. **Chrome Performance**：Main 线程火焰图在 LCP 候选时间窗内出现 **privacyPopList 相关栈**，且 LCP 元素并不依赖该数据。

## 18. defer() 如何实现？requestIdleCallback 还是 setTimeout？

## 答案

**实现**：封装 `defer(fn)`：**优先 `requestIdleCallback`（带 timeout 兜底）**，不支持时 **`setTimeout(fn, 0)`** 或 `queueMicrotask` 让出首屏关键任务。

**选型理由**：

- `rIC`：浏览器空闲执行，对 LCP 友好；但 **触发不确定**，需 `timeout: 2000` 等防止饿死。
- `setTimeout(0)`：简单可预期，但仍可能在 busy 主线程上排队。

**业务约束**：仅 defer **纯 UI 增强/非合规弹窗数据**；合规必须的隐私确认若法律要求「首屏前展示」，则 **不能 defer**，需产品/legal 另议方案。

## 19. defer 延后的逻辑含埋点/错误处理，用户离开页面会丢上报怎么办？

## 答案

**分类处理**：

- **纯 UI**（弹窗列表渲染）：可 defer。
- **关键监控/错误**： **不 defer** 或 **同步入队**；页面 `visibilitychange` / `pagehide` 时 **flush 上报队列**（sendBeacon）。
- **错误处理**：用户可见错误即时提示；日志异步但带 **持久化 queue**。

核心：**延后的是体验非关键路径，不是观测与安全的最后机会**。

## 20. 星河底部菜单排序开销具体是什么？复杂度？useMemo 优化了什么？

## 答案

**真实情况**（简历口径）：菜单项 **数量不大**，瓶颈不是 O(n log n) vs O(n²)，而是 **每次 tab 切换都重新 sort + 触发重渲染**，主线程重复劳动 **叠加 setData/MPX 更新** 造成可感知卡顿。

**优化**：对 **排序结果 useMemo**（依赖菜单数据源），仅在数据变化时重算；切换 tab 只读缓存数组。

**若追问复杂度**：JS `Array.sort` 平均 O(n log n)，n≈5 时纯算法耗时可忽略，**.memo 的价值在避免重复执行 + 减少下游渲染**，应诚实说明 **瓶颈在重复计算链而非大数据排序**。

## 21. Array.prototype.sort 在 V8 中用什么算法？短数组与长数组区别？

## 答案

**V8（现代版本）**：长度 **≤ 10** 常用 **插入排序**；更长数组用 **Timsort**（稳定，O(n log n) 最坏）。

**稳定性**：相等元素相对顺序不变；菜单若按「固定权重+名称」排序，稳定性可避免 UI 抖动。

**与项目关系**：菜单 n 很小，引擎走插入排序；面试考点是 **知道 useMemo 解决的是调用次数，不是换排序算法**。

## 22. LCP 1400→1160（约 17%）够吗？良好标准？如何继续优化到 800ms？

## 答案

**标准**：Core Web Vitals 中 LCP **≤ 2.5s 为 Good**；1160ms **已达标**。17% 在 **已有基线不差的列表页** 上属于 **可验证的业务收益**（约 240ms，用户可感知）。

**是否够**：对实习项目应强调 **方法论可复用 + 线上验证**；若面试官要更大降幅，主动给 **路线图**：

1. 预加载 LCP 图片/字体（`fetchpriority="high"`、preload）。
2. 缩小首屏 JS（路由级拆包、延迟非首屏组件）。
3. CDN/HTTP2、接口聚合（需后端配合）。
4. 星河端 setData 频率与数据量治理。

**态度**：达标不是终点，**PerfMonitor 持续监控防回归**。

## 23. 如何用 LCP entry 找到 LCP 元素并预加载？

## 答案

```javascript
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  const el = last.element; // 可能是 img、video、文本块
  // 上报 lcp_ms、lcp_url（资源 URL）等
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

**预加载**：若 LCP 是图片，首屏已知 URL 时在 HTML 加 `<link rel="preload" as="image" href="...">`；若是文本，优化 **字体加载**（`font-display: swap` + preload 字体）。**注意**：LCP 元素随视口变化，移动端与 WebView 要分端验证。

**追问「不可见是否计入」**：LCP 取视口内 **最大可见内容**；off-screen 通常不是 LCP 候选。

## 25. Agent Skill 和普通 Prompt 模板有什么区别？

## 答案

| | Prompt 模板 | Agent Skill |

## 26. AST 扫描接口清单的具体实现？Babel 还是 Acorn？如何识别核心接口？

## 答案

**工程实践**（与简历「api/ + axios 声明」一致）：以 **`@babel/parser` + `@babel/traverse`**（或 ESLint 同源 AST）遍历 **CallExpression**，匹配 `axios.get/post`、`request({ url })` 等模式，提取 **字符串字面量 URL**；结合 **api 目录结构** 做广召回。

**核心接口识别**（discover Skill 思路，不仅 AST）：

- **grep 广召回 + Agent 补读** 动态拼接、内联 url。
- **正交打标**：归属（是否 non-core 前缀） vs 业务核心（挂了能否走完主流程）。
- **带证据**：`码/URL → 源码 (file:line)` 供人工核验。

**动态 URL**：AST **无法静态确定** 的标记为 TODO，靠 **fallbackKey 保守上报** + 人工补清单 + `drift-check` 防漂移。

## 27. AST 扫描原理？词法分析与语法分析的边界？

## 答案

**流水线**：源码 → **词法分析（Lexer）** → Token 流 → **语法分析（Parser）** → AST → **遍历/转换**（Babel/ESLint/Webpack）。

**边界**：

- **词法**：字符流 → `{ keyword, identifier, string, punctuator }`，不关心结构。
- **语法**：Token 流 → 树结构（语句、表达式、函数调用），才能回答「这个 CallExpression 是不是 axios.get」。

前端工程链 **Babel、ESLint、Prettier、打包 tree-shaking** 都建立在 AST 之上。

## 28. 若项目用 fetch 或封装 request，AST 还能覆盖吗？

## 答案

**默认规则只覆盖 axios 模式时，不能全自动覆盖**。扩展方式：

1. 增加 **fetch(url)**、**request(config)** 的 AST 访问器。
2. 在 **统一 request 封装层** 做 **运行时 url 日志**（采样）反哺清单。
3. 语义上扫描「**发出 HTTP 请求**」而非「某个库名」。

**兜底**：路由 **fallbackKey** + **non-core** 规则保证 **不漏报**；清单不全只影响 **severity 精度**。面试强调 **知道边界 + 有运维手段（drift-check、sync 增量）**。

## 29. severity 配置硬编码还是动态？接口路径变了怎么更新？

## 答案

**落地形态**：`domains/train/rules.js` + Prompt 中的 **category 基线**；severity 与 **category 绑定**（如 query/payment/order），而非逐 URL 硬编码 thousands 条。

**路径变更**：

1. **discover-triage-urls** 重新扫描或 **sync 增量** 发现新 URL。
2. **drift-check.sh**（纯 grep）CI 对比源码与清单 diff。
3. 人工确认后更新 **rules 有序匹配**（特例放宽松规则前）。

**P1/P2/P3 划分**（火车票例）：阻断 **查询→下单→支付→出票** 主链 → P0/P1；单用户可兜底 → P2；展示/NPS → P3 或不上报。

## 30. business_reject 在 Prompt 里怎么写？如何防止真故障被误杀？

## 答案

**写法**（各 category 的 `.md`）：枚举 **场景 + errorCode/语义 + 必须同时满足的条件**，例如「余票查询 + 明确无票码 + 无堆栈/超时字样 → 可降噪」。

**防误杀**：

1. **全局硬约束**（`_base.md`）：信息不足 **默认上报**；出现 **超时、5xx、未知码、堆栈** 时 **不得** 仅因模糊匹配 business_reject 而丢弃。
2. **证据链**：discover 只转抄 **带 (file:line) 证据** 的码，上线前 **回源码核验**。
3. **评测**：gold 集保留足够 **真故障正样本**；**FN 优先 ≈ 0**，再降 FP。

---

## 31. LLM 判定不稳定，如何保证降噪链路稳定？

## 答案

1. **temperature=0**，固定模型版本；结构化 JSON 输出 + schema 校验。
2. **链路兜底**：超时/解析失败 → `should_report=true, severity=P2`（**永不 silent drop**）。
3. **可选增强**：关键 case 多次采样投票；结果缓存（同 url+errorCode 指纹）降抖动与成本。
4. **temperature=0 非绝对确定**：仍依赖 **评测回归** 与 **保守 Prompt**。

**原则**：稳定性靠 **工程兜底 + 评测纪律**，不靠「模型永远一致」的假设。

---

## 32. 兜底为什么是 P2 不是 P1？不够保守怎么办？

## 答案

**P2 含义**：确认 **要上报**，但 **不必然触发最高级值班**（避免模型全体故障时 **告警风暴**）；与「信息不足默认上报、severity≥P2」一致。

**若业务要求更保守**：兜底可改为 **P1**，或在 dispatch 层对 **fallback 原因** 单独计数告警。核心原则是 **宁可多报不可漏报**——若 P2 在组织内等于「无人看」，应 **上调 severity 或单独通道**。

**诚实**：我们选型是 **成本与信噪比平衡**；真故障漏报代价更高，所以 **fallback 永远 should_report=true**。

---

## 33. 为什么 FN_rate 是核心指标？与召回率关系？

## 答案

**告警场景代价不对称**：漏报真故障 → 线上事故；多报噪音 → 值班多看几眼。

- **FN_rate** = 漏报数 / 真实故障总数  
- **Recall（召回率）** = TP / (TP+FN) = **1 − FN_rate**（在「应报」为正类定义下）

**不看笼统 Accuracy**：样本里噪音占绝大多数，「全部不报」Accuracy 仍高但 **Recall≈0**。因此评测 **先压 FN**，再降 FP，再看 severity 分级精度。

---

## 34. /judge 与 /eval 如何设计？评测集与 gold 质量如何保证？

## 答案

| 接口 | 作用 |
|------|------|
| `POST /judge` | **单条判定**，走 triage **不派发**，用于回放、调 Prompt、Demo |
| `POST /eval` | **批量**跑数据集，对比 gold，输出 FN/FP、severity 偏差、失败清单 |

**评测集构建**：

1. 从 **历史告警** 抽样（指纹去重：url+errorCode+msg 哈希）。
2. **正负样本平衡**，防止「一律不报/一律报」刷分。
3. **train 调参 / holdout 验**，冻结 gold 后重跑；上线数字用 **生产模型** 复验。

**gold 质量**：研发+值班 **双人标注** 争议 case；business_reject 类必须 **回源码核对**；diff case **反哺 Prompt** 并进入回归集。

**工程位置**：`error-triage/eval/`（run.js、score.js、datasets）；与 Hackathon 赛题04 **Token 治理** 共用 `/eval` 做 before/after 门禁（**漏报不升**）。

## 43. GResume 的项目定位？与 InterviewFlash 的关系？

## 44. 为什么选 TipTap？为什么离线优先？

## 答案

**TipTap**：基于 ProseMirror，**Headless 可扩展**；输出稳定 HTML 供预览/PDF/ATS/历史；可挂 **Yjs 协作、BubbleMenu 划词 AI**；比 textarea 无法满足后续协作与 AI 写回。

**离线优先**：写作场景常断网；**IndexedDB 先行**保证「打开就能写」；登录后批量同步 `resume_config`，未登录与已登录 **同一套抽象**，降低账号绑架。

**纠偏**：侧边栏 **模块拖拽排序** 驱动 `order[]`，与 TipTap 内富文本编辑是 **两套能力**。

## 45. Automerge CRDT 协作如何实现「不冲突」？

## 答案

**结构化字段**（工作经历、项目列表等）：Automerge 文档 **并发编辑自动合并**，无 central lock；本地 IndexedDB 持久化 + Supabase Realtime 同步。

**富文本深化**：文档层 Automerge 存 **HTML 镜像**（预览/导出）；会话内 TipTap 字段走 **Yjs 字符级 CRDT**，避免 HTML 整段 LWW **后写覆盖**；再桥回 Automerge。

**能力**：分享链接、在线成员、远程光标、离线编辑后 **自动 merge**。

**面试一句**：字段级 Automerge + 富文本 Yjs，是「结构化」与「字符级」两种冲突模型各取所长。

## 46. ATS 优化引擎如何设计？如何避免「只打分不落地」？

## 答案

**五维评分**：解析度/可读性/完整度/量化/职位匹配等（结构化 JSON）。

**可执行修复**：每条 finding 带 **字段 path**（如 `work[0].description`）+ suggestion 类型（替换/填充/日期规范化）；用户 **确认后** Schema 驱动写回表单——**扫描与写入分离**。

**划词改写**：5 动作、多候选；`DOMPurify` 后再 `insertContentAt` 写回选区。

**AI 通道**：DeepSeek 经 Edge Function `llm-proxy`，密钥不出前端。

## 47. JD 派生简历（v1.2）的流程与「事实保护」？

## 49. PDF/Word 导出如何保证所见即所得？
